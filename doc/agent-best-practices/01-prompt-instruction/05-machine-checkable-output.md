# 输出格式要机器可校验

[返回全局摘要](../README.md) · [返回本组：提示词与指令](README.md)

## Rule
面向系统集成的输出应使用可解析、可校验的结构化格式。

## Why
自由文本难以稳定接入下游系统，格式漂移会造成解析失败和隐性业务错误。

Agent 的输出通常不是只给人看的答案，还会进入数据库、前端页面、工作流、工具调用或下一个 Agent。只要下游系统要消费输出，就必须把输出当成接口，而不是作文。

自由文本有几个典型风险：

| 风险 | 表现 | 后果 |
| --- | --- | --- |
| 字段漂移 | 今天叫 `summary`，明天叫 `result` | 下游解析失败 |
| 类型漂移 | 金额一会儿是数字，一会儿是字符串 | 计算、排序或校验出错 |
| 枚举漂移 | `high`、`严重`、`P1` 混用 | 风险分级不可比较 |
| 额外文本 | JSON 前后追加解释 | 解析器报错 |
| 隐性空值 | 没有答案时直接省略字段 | 下游误判为成功 |
| 证据缺失 | 结论没有来源字段 | 无法审计和回归 |

## Optimize
- 使用 JSON Schema、枚举值和必填字段。
- 明确空值、错误和多结果的表达方式。
- 禁止在结构化输出外追加解释文本。

输出 schema 要覆盖四类信息：

```json
{
  "status": "success | partial | blocked | failed",
  "data": {},
  "evidence": [],
  "errors": []
}
```

其中 `status` 让系统知道是否能继续；`data` 放业务结果；`evidence` 绑定来源；`errors` 表示缺失、冲突或失败原因。不要让模型用“看起来像成功”的自然语言掩盖失败状态。

设计 schema 时要注意：

- 必填字段要少而关键。过多必填字段会提高格式失败率。
- 枚举要稳定。不要让模型自由创造状态名、风险等级或错误类型。
- 空结果要显式表达，例如 `items: []` 和 `status: success`，不要省略字段。
- 部分成功要有结构，例如哪些条目成功、哪些失败、失败原因是什么。
- 数值要定义单位和范围，例如金额是分还是元，时间是 UTC 还是本地时区。
- 证据字段要能回到 trace、文件行号、chunk_id、工具结果或数据库记录。

如果输出要给用户阅读，可以让应用层把结构化结果渲染成自然语言，而不是让模型同时输出 JSON 和解释长文。系统接口追求稳定，人类展示追求清楚，二者不要混在一个不可控文本里。

## Engineering Notes

- Schema 校验失败时，不要直接把坏 JSON 传给下游。应进入修复、重试或失败路径。
- 结构化输出不等于绝对正确。它只能保证格式可消费，事实正确性仍要靠证据、工具结果和 verifier。
- 对高风险任务，输出中的 `confidence` 不应只来自模型自评，应结合检索分数、证据覆盖率和业务校验。
- 多模型、多版本共用下游时，要维护 schema 版本，并支持兼容迁移。
- 不要用正则解析自然语言当协议。能用结构化输出、tool call 或 schema 的地方，优先使用结构化机制。

## Verify
- 用解析器和 schema 校验每次输出。
- 覆盖空结果、异常结果和边界字段。
- 统计格式错误率并纳入回归测试。
- 测试模型是否会在 JSON 外追加说明、Markdown 代码块或多余前缀。
- 测试缺证据、部分失败、权限不足和低置信场景能否输出正确状态。
- 检查下游系统是否只在 `status` 和 schema 校验都通过后继续执行。
