# 给模型明确退出路径

[返回全局摘要](../README.md) · [返回本组：提示词与指令](README.md)

## Rule
告诉模型在信息不足、权限不足、风险过高或无法判断时如何停止并返回。

## Why
没有退出路径时，模型可能猜测、编造或继续执行不该执行的动作。

Agent 系统里，“停下来”是一种能力。很多失败不是模型不会回答，而是它不知道什么时候不该继续：证据不够时编造依据，权限不够时绕过流程，工具失败时假装成功，高风险动作没确认时继续执行。

退出路径要解决三个问题：

| 场景 | 不好的行为 | 正确退出 |
| --- | --- | --- |
| 信息不足 | 自行补字段、猜测用户意图 | 返回缺失字段和可选补充方式 |
| 证据不足 | 用常识替代知识库 | 明确未找到证据，建议检索范围或转人工 |
| 权限不足 | 继续生成可执行参数 | 拒绝执行，并说明需要什么权限或确认 |
| 风险过高 | 用一句“请谨慎”后继续 | 暂停任务，请求人工确认 |
| 工具失败 | 编造工具结果 | 返回结构化错误和下一步选择 |

## Optimize
- 定义“不知道”“需要人工确认”“无法执行”的固定输出。
- 列出应停止的条件。
- 要求说明缺失信息和下一步建议。

退出输出应机器可读，不能只靠自由文本。一个实用结构如下：

```json
{
  "status": "blocked",
  "reason": "missing_required_information",
  "missing_fields": ["order_id", "refund_reason"],
  "can_continue_automatically": false,
  "next_actions": [
    "请用户提供订单号",
    "请用户选择退款原因"
  ]
}
```

常见退出类型可以固定成枚举：

| 退出类型 | 触发条件 | 后续处理 |
| --- | --- | --- |
| `need_more_info` | 任务必需字段缺失或用户目标有歧义 | 向用户澄清 |
| `insufficient_evidence` | 检索为空、证据低置信或证据冲突 | 扩大检索、说明不确定或转人工 |
| `permission_required` | 动作越权或缺少授权 | 请求授权或拒绝执行 |
| `confirmation_required` | 写入、删除、付款、发送、发布等高风险动作 | 暂停并展示具体确认内容 |
| `tool_failed` | 工具超时、报错、限流、参数非法 | 重试、换策略或转人工 |
| `budget_exceeded` | token、轮次、时间或成本超限 | 停止自动执行，输出已完成和未完成事项 |

退出路径不是让模型变保守，而是让系统把“不确定性”显式暴露出来。只要退出结果可解析，应用层就能接住：重新提问、调工具、转人工、保存任务状态或安排重试。

## Engineering Notes

- 不要把退出写成“如果你不确定，请说明”。这太弱。应该明确“哪些条件必须停止”。
- 退出不能丢失上下文。长任务暂停时，要同时保存 `task_id`、当前状态、阻塞原因、已完成步骤和下一步动作。
- 退出要区分用户可补充和系统不可恢复。缺字段可以澄清，权限不足需要授权，外部服务故障需要重试或降级。
- 高风险动作的退出应由应用层 enforce。模型说“需要确认”不等于执行器真的停下。
- 退出文案要面向用户，但退出数据要面向系统。二者可以同时存在。

## Verify
- 构造缺字段、冲突信息和越权请求样例。
- 检查模型是否停止而不是补猜。
- 确认退出输出能被系统或人工接住。
- 对工具超时、空检索、低置信证据和预算超限做回归测试。
- 检查高风险工具调用在未确认时是否进入 `confirmation_required`，且工具没有被执行。
- 中断恢复后，确认系统能根据退出状态继续，而不是让模型重新猜上次停在哪里。
