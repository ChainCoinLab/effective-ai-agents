# 把业务 SOP 转成可执行步骤

[返回全局摘要](../README.md) · [返回本组：提示词与指令](README.md)

## Rule
把业务 SOP 写成模型可逐步执行的动作、判断条件和产物要求；不要把这类详细步骤塞进 `CLAUDE.md` 或全局系统提示词。

## Why
自然语言 SOP 往往含有隐含经验。模型需要明确步骤，否则会跳步、合并步骤或自行补全。

但 SOP 和全局规则不是同一种东西。全局规则负责约束行为和边界，SOP 负责执行流程。如果把每个任务的详细步骤都写进全局规则，规则会越来越长，也会让模型在不相关任务里误用流程。

业务 SOP 常见的问题不是“没写流程”，而是流程对人类默认成立、对模型并不成立。例如“审核后发布”里隐含了谁审核、审核什么、审核不通过怎么办、发布到哪里、是否需要回滚、发布后如何验证。人类员工能凭经验补齐这些空白，Agent 会把空白变成猜测。

把 SOP 转成 Agent 可执行步骤，本质上是把“经验文本”改造成“任务协议”：

| SOP 中的表达 | Agent 需要的表达 |
| --- | --- |
| 先检查资料是否完整 | 列出必填资料字段，缺少任一字段时返回 `need_more_info` |
| 审核通过后发送邮件 | 明确审核人、审核标准、邮件模板、收件人来源和发送前确认 |
| 异常情况转人工 | 定义异常类型、触发条件、转人工时携带的结构化上下文 |
| 处理完成后记录结果 | 定义写入哪个状态字段、记录哪些证据、是否需要幂等键 |

## Optimize
- 用编号步骤表达执行顺序。
- 为每个分支写清触发条件。
- 指定每一步的输入、输出和检查点。
- 把稳定重复的流程放到 Skill、workflow 或独立 SOP 文件中。
- 在 `CLAUDE.md` 中只写何时使用该 SOP、何时不要使用、需要人工确认的边界。
- 对“不要做什么”单独列禁区，例如不跳过审核、不擅自发布、不覆盖原文件。

推荐把 SOP 拆成下面的结构：

```text
SOP 名称
适用场景
不适用场景
输入字段
前置条件
步骤列表
分支条件
每步产物
验证方式
失败出口
人工确认点
审计记录
```

其中最容易被忽略的是“不适用场景”和“失败出口”。没有不适用场景，模型会把流程套到不该处理的任务上；没有失败出口，模型会在缺字段、权限不足或工具失败时继续猜。

一个更工程化的步骤应该像这样写：

```text
步骤 3：检查发票信息
输入：invoice_title、tax_id、amount、currency、invoice_date
动作：校验字段完整性和金额范围
通过条件：字段齐全，金额和订单金额一致，日期在允许范围内
失败条件：字段缺失、金额不一致、日期超限
失败处理：返回 need_more_info，并列出缺失或冲突字段
禁止动作：不得自行补全 tax_id，不得猜测金额
```

如果 SOP 会触发外部动作，例如付款、发邮件、删除文件或发布内容，还要把步骤拆成“生成建议”和“执行动作”两段。模型可以参与整理参数和解释理由，但真正执行必须经过权限、确认和审计。

## Engineering Notes

- SOP 不是 Prompt 越长越好。流程越长，越应该进入 Skill、workflow 或代码状态机，由 Prompt 只加载当前步骤所需片段。
- 步骤产物要能被程序读取。只写“检查完成”没有意义，应写成 `status: passed | failed | needs_review`，并附带证据。
- 分支条件要互斥。多个条件同时成立时要有优先级，否则 Agent 会在分支间摇摆。
- 高风险动作要有确认令牌。自然语言“请谨慎”不能替代确认流程。
- SOP 改动要跑回归。流程文字变动会改变模型执行路径，不能只当文案修改。

## Verify
- 用真实工单或业务样例逐步回放。
- 检查模型是否按顺序执行且没有漏掉关键判断。
- 让业务负责人确认步骤没有改变规则含义。
- 检查全局规则是否只保留触发条件和边界，详细步骤是否已经迁到 SOP 或 Skill。
- 故意构造缺字段、冲突字段、越权动作和工具失败样例，检查 Agent 是否进入正确分支。
- 回放 trace，确认每一步的输入、输出、证据和状态更新都能对应到 SOP。
- 检查 SOP 中每个“人工确认点”是否真的由应用层拦截，而不是只写在提示词里。
