# 把 Prompt 当作代码管理

[返回全局摘要](../README.md) · [返回本组：提示词与指令](README.md)


## Rule
Prompt 应进入版本管理，经过评审、测试、发布和回滚流程。像 `CLAUDE.md` 这类长期规则文件还应控制长度和作用域，只写稳定约定、边界和禁区，不写临时任务和每一步操作细节。

## Why
Prompt 会直接改变系统行为。缺少版本和测试时，线上质量回退难以定位。

长期规则文件如果过长，模型更难抓住真正优先级，缓存和上下文成本也会变高。更大的问题是：把“怎么做每一步”写进全局规则，会让模型在不同任务中机械套用旧流程。全局规则应强调“不应做什么、必须守住什么边界、默认偏好是什么”；具体步骤应放到 SOP、Skill、工作流或本次任务提示里。

当 Skill 数量很大时，System Prompt 不应内联全部 Skill 说明；具体实现见 [大规模 Skill 工程实现](../04-tools-agents/large-scale-skill-engineering.md)。

## Optimize
- 使用独立文件保存 Prompt，不散落在业务代码中。
- 为每次修改写明原因、影响范围和预期收益。
- 将 Prompt 版本和模型版本一起记录。
- 为 `CLAUDE.md`、系统提示词等长期规则设置长度预算，删除重复、临时、任务专属和过期内容。
- 优先写约束和边界，例如“不自行发布”“不覆盖用户文件”“信息不足先澄清”，少写逐步操作教程。
- 把详细流程放入专门 Skill、SOP 文档或任务提示；全局规则只引用这些能力的触发条件和边界。
- 用“规则文件约束行为，Skill 执行流程”的分层方式管理提示词。

## Flow

```text
长期规则文件: CLAUDE.md / system prompt
  - 身份和目标
  - 稳定偏好
  - 禁区和权限边界
  - 输出约束
  - Skill 选择原则
        |
        v
可执行流程: Skill / SOP / workflow
  - 具体步骤
  - 分支条件
  - 工具调用
  - 检查点
        |
        v
单次任务提示
  - 本次目标
  - 本次输入
  - 本次例外和临时约束
  - 按需加载的少量 Skill 和示例
```

## Verify
- 修改前后运行固定评测集。
- 检查发布记录能追溯到具体 Prompt 版本。
- 确认异常时可快速回滚。
- 审查 `CLAUDE.md` 是否能在几分钟内读完，并能明确区分稳定规则和临时任务。
- 抽查规则是否以边界和禁区为主，而不是把具体操作步骤写成长篇教程。
- 检查详细流程是否能在对应 Skill、SOP 或 workflow 中找到，而不是散落在全局规则里。
- 检查 System Prompt 中是否内联了大量 Skill 全文；如果有，迁移到大规模 Skill 工程方案。
