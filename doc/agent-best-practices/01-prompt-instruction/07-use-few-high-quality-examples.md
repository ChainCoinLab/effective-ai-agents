# 少量高质量示例

[返回全局摘要](../README.md) · [返回本组：提示词与指令](README.md)

## Rule
优先提供少量覆盖关键模式的高质量示例，而不是大量重复或噪声示例。

## Why
示例会强烈影响模型输出。低质量示例会传播错误格式、错误推理和过时业务规则。

Few-shot 示例的价值不是“多给模型看几个答案”，而是用最少样例告诉模型：任务边界在哪里，输出格式是什么，遇到分支时如何判断，什么时候应该拒绝或澄清。示例越多，未必越好；如果示例重复、过时或互相矛盾，模型反而会学到错误模式。

示例应该覆盖“决策结构”，而不只是覆盖“表面文案”：

| 示例类型 | 作用 |
| --- | --- |
| 标准成功样例 | 说明正常输入如何得到合格输出 |
| 边界样例 | 说明缺字段、低置信、冲突信息如何处理 |
| 反例样例 | 说明什么请求不应执行或不应调用工具 |
| 格式样例 | 固定字段、枚举、证据引用和错误表达 |
| 高风险样例 | 展示何时必须请求确认或转人工 |

## Optimize
- 选择最能代表边界、格式和决策逻辑的示例。
- 示例保持短小，避免引入无关字段。
- 定期移除过时示例。

选择示例时可以用下面的标准：

- 代表高频任务，而不是只挑最漂亮的成功案例。
- 覆盖关键分支，而不是多个样例都走同一条路径。
- 输入和输出都真实，避免为了演示而写出生产中不会出现的数据。
- 输出符合当前 schema，不包含旧字段、旧枚举和旧话术。
- 示例中的证据、工具结果和结论能对上，不制造“看起来合理但无证据”的坏习惯。

示例数量要受 token 预算约束。通常 2 到 5 个高质量示例比 20 个松散示例更稳定。复杂任务可以按阶段拆示例：意图识别给一组，工具选择给一组，最终输出给一组，不要把所有示例塞进同一个 Prompt。

示例也应版本化。业务规则、输出 schema、工具接口或风险策略变化后，示例必须同步更新。过时示例比没有示例更危险，因为模型会优先模仿它们的格式和判断方式。

## Engineering Notes

- 示例不是评测集。示例用于引导行为，评测集用于检验行为。不要把所有测试答案都塞进 Prompt。
- 示例要避免泄露真实敏感数据。生产日志转示例前应脱敏、改写或合成。
- 反例要明确给出正确处理方式，例如 `need_more_info`、`refuse` 或 `confirmation_required`，不能只展示“这是错的”。
- 如果模型输出变得过度模板化，检查示例是否太单一、太长或风格过强。
- 示例命中效果要通过回归验证，不要凭单次对话判断。

## Verify
- 对比有无示例时的准确率和格式稳定性。
- 检查示例是否覆盖主要分支。
- 让业务或领域专家审查示例正确性。
- 检查示例是否和当前 schema、工具参数、业务规则一致。
- 从线上失败中挑选代表性案例，判断是否需要新增反例或边界示例。
- 监控示例加入后是否引入新的偏差，例如答案变长、过度拒答或过度调用工具。
