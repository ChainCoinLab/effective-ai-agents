# 大模型工程实践

[返回全局摘要](../README.md)

大模型工程实践和大模型原理是同一级别的能力。原理回答“模型为什么能生成”，工程实践回答“如何把模型调到可用、稳定、可验证，并让外部系统正确调用它”。

从岗位上看，大模型开发更关注模型本体、训练数据、微调、推理参数、模型服务、评测和安全边界；Agent 开发更关注如何把模型接入任务系统、工具系统、状态系统和业务流程。两者有关联，但不是同一个岗位能力。

## 工程实践轮廓

| 模块 | 关注点 | 典型问题 |
| --- | --- | --- |
| 模型调用 | 外部系统如何通过 API、Prompt、上下文和参数调用模型 | 输入过长、指令冲突、温度参数不合适、输出不稳定 |
| 推理调参 | 如何调整 temperature、top_p、max tokens、stop、结构化输出等参数 | 创造性和稳定性如何平衡，长输出如何控制 |
| 微调与对齐 | 什么时候需要 SFT、偏好对齐或领域微调 | 微调是否真的比 Prompt/RAG 更合适，是否引入退化 |
| 数据与样本 | 训练、微调和评测数据如何构造 | 数据分布不一致、脏数据、重复样本、标注标准不清 |
| 模型测评 | 如何验证模型能力、边界、稳定性和回归风险 | 单次样例好不代表整体好，模型升级可能破坏旧能力 |
| 安全与边界 | 如何处理幻觉、越权、敏感信息、拒答和滥用风险 | 模型不能成为权限边界，输出需要被系统约束 |

## 外部调用模型时要理解的问题

大模型被外部系统调用时，调用方不能只把它当成一个普通函数。模型输出具有概率性，会受到上下文、指令顺序、参数、示例、历史消息和检索材料影响。

调用方至少要理解这些风险：

- 模型可能编造事实，所以事实类任务需要证据和引用。
- 模型可能误解指令，所以关键任务需要结构化输入和输出校验。
- 模型不天然知道业务状态，所以状态要由应用系统提供。
- 模型不天然拥有权限判断能力，所以授权要在应用层完成。
- 模型输出可能不稳定，所以要有 eval、回归测试和失败样例库。
- 模型上下文有限，所以要做压缩、排序、去重和优先级控制。

这也是为什么大模型工程和 Agent 工程会相互连接：Agent 调用模型时，必须理解模型的优势和缺陷；大模型工程也要理解外部系统会如何调用模型，以及调用方式会放大哪些问题。

## 调优方法的选择

大模型调优不是一上来就微调。更合理的顺序通常是：

1. 先明确任务定义、输入输出和成功标准。
2. 再调整 Prompt、示例、上下文结构和推理参数。
3. 如果问题来自知识缺失或事实更新，优先考虑 RAG 或外部工具。
4. 如果问题来自领域风格、稳定格式或任务模式，再考虑微调。
5. 每次修改都要通过 eval 和回归测试判断收益。

调优的核心不是让某个样例变好，而是让一类任务在质量、稳定性、成本、延迟和安全上整体更可靠。

## 与 Agent 开发的关系

Agent 开发调用大模型，但不应该把大模型当成万能执行器。大模型擅长理解、生成、归纳、规划和表达调用意图；Agent 系统负责把模型接入工具、记忆、状态、权限和工作流。

两者的关系可以这样理解：

- 大模型开发要知道外界如何调用模型，以及调用方式会导致哪些问题。
- Agent 开发要知道自己调用的模型、工具、RAG、记忆分别有什么优势和缺陷。
- 大模型侧提供能力边界，Agent 侧负责把边界变成工程控制。
- 大模型侧测模型能力，Agent 侧测任务过程、工具轨迹和端到端结果。
