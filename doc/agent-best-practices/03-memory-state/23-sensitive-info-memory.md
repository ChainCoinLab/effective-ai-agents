# 23. 敏感信息不应默认进入长期记忆

[返回全局摘要](../README.md) · [返回本组：记忆与状态管理](README.md)

## Status
Recommended

Category: memory-state

## Rule
敏感信息不默认进入长期记忆。

## Why
敏感信息跨会话保留会扩大泄露、误用和合规风险。即使用户在一次任务中提供，也不代表同意长期保存。

Agent 在一次任务中可能必须处理敏感信息，例如登录凭据、合同、财务数据、健康信息、身份证明、客户名单、未公开代码或生产日志。但“本次任务需要看到”不等于“可以长期记住”。长期记忆会跨会话复用，影响范围远大于单次上下文。

默认不写入敏感信息，是为了控制三个风险：

| 风险 | 说明 |
| --- | --- |
| 泄露 | 未来无关任务检索到敏感记忆并注入上下文 |
| 误用 | 模型基于旧凭据、旧身份或旧财务信息作决策 |
| 合规 | 用户未授权长期保存，或超出数据最小化原则 |

## Optimize
默认排除密钥、凭据、身份标识、健康、财务、未公开业务信息等内容。确需保存时，要求明确目的、最小字段、权限边界和删除路径。

建议建立敏感信息分类：

| 类型 | 默认策略 |
| --- | --- |
| 密钥、Token、密码、私钥 | 永不进入长期记忆，发现后脱敏和告警 |
| 身份证件、地址、电话、邮箱 | 默认不记，除非产品明确需要并经用户授权 |
| 健康、财务、法律、未公开商业信息 | 默认不记，必要时最小化保存 |
| 客户数据、生产数据、日志 | 默认只进入受控存储和 trace，不进入通用记忆 |
| 个人偏好 | 可记，但要允许查看、更正和删除 |

如果确实需要保存敏感相关信息，应保存“最小可用表示”，而不是原文。例如保存“用户偏好用公司邮箱接收通知”通常可以，不应保存邮箱密码；保存“项目使用生产数据库只读账号”通常可以，不应保存账号密钥。

敏感信息处理流程：

```text
输入进入系统
-> 敏感信息检测
-> 本轮上下文按需使用
-> 长期记忆写入前二次检测
-> 默认拒绝或请求显式确认
-> 写入时脱敏、加作用域、加 TTL、可删除
```

## Engineering Notes

- 敏感信息检测不能只靠模型判断，应结合规则、正则、DLP、字段类型和权限上下文。
- 长期记忆、向量索引、摘要、缓存和 trace 都可能成为泄露面，要一起治理。
- 脱敏后仍可能可识别，尤其是小样本用户或企业内部数据，要按场景评估。
- 误写入敏感信息后，需要有删除和索引重建流程。
- 不要把“用户发给了 Agent”理解成“用户同意永久保存”。

## Verify
用包含密码、Token、身份证明和私人偏好的样例测试写入逻辑，确认敏感内容被拒绝或需要显式确认。

还应测试：

- 敏感信息不会进入 embedding、摘要记忆和缓存副本。
- 用户要求删除后，主存储、索引和缓存都不再返回该信息。
- 高风险数据只在有权限的任务作用域中被读取。
- Trace 中敏感字段被脱敏或引用化处理。
