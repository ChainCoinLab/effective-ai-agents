# 21. 记忆应可更新和删除

[返回全局摘要](../README.md) · [返回本组：记忆与状态管理](README.md)

## Status
Recommended

Category: memory-state

## Rule
记忆应支持更新和删除，不应只追加。

## Why
用户偏好、身份信息和项目背景会变化。旧记忆如果无法修正，会让 Agent 持续使用错误前提。

长期记忆不是追加日志，而是可治理的数据。用户今天说“默认用英文”，明天可能改成“默认用中文”；项目今天用 npm，明天迁到 pnpm；组织规则、API、合规要求和业务流程也会变化。如果系统只追加不更新，检索时就会同时拿到新旧记忆，模型只能凭概率猜哪个更可信。

记忆治理要支持四种操作：

| 操作 | 触发场景 |
| --- | --- |
| 更新 | 用户纠正、项目规则变化、事实有新版本 |
| 删除 | 用户要求忘记、误写入敏感信息、数据保留期到期 |
| 失效 | 信息过期、来源不再可信、作用域不再适用 |
| 合并 | 多条记忆表达同一事实或偏好 |

## Optimize
为记忆设置稳定标识、版本或合并策略。允许用户显式更正、删除，也允许系统在发现冲突时标记旧记忆失效。

一个可更新的记忆结构应包含：

```json
{
  "memory_id": "user_output_language_preference",
  "value": "中文",
  "status": "active",
  "version": 3,
  "supersedes": ["memory_v1", "memory_v2"],
  "updated_at": "2026-05-22",
  "source": "user_correction",
  "scope": "user"
}
```

当用户纠正时，不要只追加“用户现在喜欢中文”。应把旧记忆标记为 `superseded` 或更新原条目：

```text
旧记忆：默认输出英文
用户纠正：以后默认中文
处理：旧记忆失效，新记忆生效，后续检索只返回 active 版本
```

删除要区分两类：

- 软删除：标记 `deleted`，用于审计但不再参与检索和上下文注入。
- 硬删除：从存储中移除，适合敏感信息误写入、用户明确要求或合规要求。

具体采用哪种方式取决于产品承诺、合规要求和审计策略，但无论哪种，后续回答都不能继续使用已删除记忆。

## Engineering Notes

- 记忆 ID 要稳定，不能每次重新 embedding 后就失去同一事实的身份。
- 检索时默认只返回 `active` 记忆，除非在审计或复盘场景。
- 冲突记忆不要交给模型自由裁决，应先按来源、时间、作用域和确认级别排序。
- 删除后要处理缓存、向量索引和摘要副本，否则“忘记”只删了主表，模型仍可能从副本读到。
- 用户更正应高优先级写入，并触发相关旧记忆失效。

## Verify
测试“用户改变偏好”和“用户要求忘记”两类路径，确认后续回答不再使用旧内容。

还应测试：

- 删除后向量检索、缓存和摘要层都不再返回旧内容。
- 新旧记忆冲突时，系统使用 active 且来源更可信的版本。
- 用户要求“忘记某件事”后，trace 中能看到删除操作和影响范围。
- 合并重复记忆后，引用和来源仍能追溯。
