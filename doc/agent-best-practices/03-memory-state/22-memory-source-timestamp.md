# 22. 记忆要带来源和时间戳

[返回全局摘要](../README.md) · [返回本组：记忆与状态管理](README.md)

## Status
Recommended

Category: memory-state

## Rule
长期记忆应带来源和时间戳。

## Why
记忆不是事实本身，而是某次交互中记录下来的信息。来源和时间能帮助判断可信度、时效性和冲突处理方式。

没有来源和时间戳的记忆，工程上很难使用。模型可能读到一句“用户使用 React”，但不知道这是用户明确说的、从旧项目文件推断的，还是模型自己总结的；也不知道它是今天记录的，还是三年前记录的。这样的记忆越多，系统越难解释为什么作出某个判断。

来源和时间戳至少解决四个问题：

| 问题 | 需要的元数据 |
| --- | --- |
| 可信度 | 来自用户确认、工具观察、人工审核还是模型推断 |
| 时效性 | 创建时间、更新时间、有效期、过期条件 |
| 冲突处理 | 多条记忆谁更新、谁更权威、作用域是否相同 |
| 审计回放 | 哪次会话、哪个工具、哪个文件导致记忆被写入 |

## Optimize
记录创建时间、更新时间、来源会话或来源系统，以及是否由用户明确确认。展示或使用高影响记忆时优先引用这些元数据。

建议记忆元数据包括：

```json
{
  "memory_id": "project_test_command",
  "content": "该项目的文档构建命令是 npm run docs:build。",
  "source_type": "file_observation",
  "source_ref": "package.json:scripts.docs:build",
  "created_at": "2026-05-22T10:00:00+09:00",
  "updated_at": "2026-05-22T10:00:00+09:00",
  "confirmed_by_user": false,
  "confidence": "observed",
  "scope": "project",
  "expires_at": null
}
```

不同来源应有不同信任级别：

| 来源类型 | 可信度处理 |
| --- | --- |
| 用户明确确认 | 高，但仍可能被用户后续更正 |
| 工具观察 | 高，适合文件、数据库、API 返回的事实 |
| 人工审核 | 高，适合质量标准和业务判断 |
| 模型总结 | 中低，需要来源引用或人工确认 |
| 历史摘要 | 中，需要能回到原始 trace |

时间戳不只是展示字段，还应参与检索排序和冲突裁决。对政策、价格、依赖版本、接口文档、人员职责等容易过期的信息，应该设置刷新条件或 TTL。

## Engineering Notes

- 不要让模型生成“看起来像来源”的引用。来源应由系统写入，例如文件路径、chunk_id、tool_call_id。
- 时间要统一格式和时区，避免跨系统比较出错。
- 来源引用要能追到原始 artifact；如果只能追到摘要，摘要也要有自己的来源链。
- 高影响记忆被用于回答时，最好在 trace 中记录“本轮读取了哪条记忆”。
- 过期记忆不一定要删除，但默认不应进入上下文。

## Verify
随机读取记忆条目，确认能追溯到来源，并能判断是否需要刷新或废弃。

还应测试：

- 两条记忆冲突时，系统能根据来源和更新时间解释选择。
- 过期记忆不会默认注入上下文。
- 模型总结型记忆没有原始来源时不能作为高风险决策依据。
- trace 能还原当前回答读取了哪些记忆。
