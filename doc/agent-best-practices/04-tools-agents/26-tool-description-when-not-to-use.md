# 26. 工具描述要写清何时不用

[返回全局摘要](../README.md) · [返回本组：MCP、工具调用与多 Agent](README.md)

## Status
Recommended

Category: tools-agents

## Rule
工具描述要写清楚何时使用，也要写清楚何时不用。

## Why
只描述能力会让模型过度调用工具。明确排除条件能减少无意义调用、权限请求和错误路径。

工具描述通常只写“这个工具能做什么”，但模型做工具选择时同样需要知道“什么时候不要用”。如果多个工具能力相似，或者用户已经提供了完整信息，缺少排除条件会导致过度调用、重复查询、错误权限请求和额外成本。

例如一个天气工具如果只写“查询天气”，模型可能在用户已经给出天气数据时仍然调用，或者在用户问“天气这个词是什么意思”时也调用。更好的描述要写出适用边界：

```text
用于查询指定城市的实时或未来天气。
仅当用户需要当前/未来天气，且输入中没有足够天气数据时使用。
不要用于解释天气概念、总结用户提供的天气文本，或查询历史气候统计。
```

## Optimize
在描述中加入适用场景、禁止场景、前置条件和替代方式。例如“仅在需要实时数据时使用；不应用于用户已经提供完整数据的情况”。

工具描述建议包含五段：

| 字段 | 内容 |
| --- | --- |
| 能力 | 工具具体做什么 |
| 适用场景 | 什么用户意图下应该调用 |
| 不适用场景 | 哪些场景不要调用 |
| 前置条件 | 调用前必须有哪些参数或权限 |
| 副作用/风险 | 是否写入、发送、删除、花钱或影响生产 |

对于相似工具，要显式写差异：

```text
search_docs: 用于检索项目文档和知识库，不查询实时业务状态。
query_order_status: 用于查询指定订单的实时状态，必须提供 order_id。
```

对于需要澄清的工具，要写清不要猜：

```text
如果缺少 order_id，不要调用 query_order_status；先向用户请求订单号。
```

对于高风险工具，要写清确认要求：

```text
send_email 会向外部收件人发送邮件。没有 confirmation_token 时不得执行。
```

## Engineering Notes

- 工具描述不是越长越好，要短、具体、可区分。
- `do_not_use_when` 最好进入工具 manifest，而不只是自然语言段落。
- 工具描述要和权限策略一致。不能描述里说可用，执行层却总是拒绝。
- 工具选择失败经常是描述边界失败，不要只调 Prompt。
- 工具说明变更会改变行为，应进入版本管理和回归。

## Verify
用不需要工具的样例提示测试，确认模型不会为了确认常识、重复已有信息或执行低价值操作而调用工具。

还应测试：

- 用户已提供足够数据时，模型是否直接回答而不是调用工具。
- 缺少必填参数时，模型是否澄清而不是猜。
- 多个相似工具同时存在时，模型是否选对。
- 高风险工具没有确认令牌时，模型是否停在确认流程。
- 描述变更前后工具调用率是否异常上升或下降。
