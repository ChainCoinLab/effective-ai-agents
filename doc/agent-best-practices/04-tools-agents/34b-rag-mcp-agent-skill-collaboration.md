# 34B. RAG、MCP、Agent、Skill 要工程化协作

[返回全局摘要](../README.md) · [返回本组：MCP、工具调用与多 Agent](README.md)

## Status
Recommended

Category: tools-agents

## Rule
不要把 RAG、MCP、Agent 和 Skill 当作孤立组件分别堆上去。工程上应明确它们的职责边界、调用链路、权限边界和验证方式，让它们围绕同一个任务状态协作。

## Why
很多 AI 应用失败，不是因为缺少某个名词，而是因为几个模块边界混乱：

| 混乱方式 | 典型后果 |
| --- | --- |
| Agent 直接自由调用所有工具 | 死循环、误操作、越权、不可审计 |
| MCP 只做连接，不做权限 | 统一接口变成统一风险入口 |
| Skill 只写概念，不写流程 | Agent 仍然需要临场猜测怎么做 |
| RAG 只做向量检索 | 查不准、证据弱、答案仍然幻觉 |
| 工具和 RAG 混在一起 | 系统分不清是在查知识还是执行动作 |

工程协作的目标，是让每一层只承担自己擅长的职责：

- Agent 负责规划、路由和整合。
- Skill 负责流程、模板、检查清单和经验复用。
- MCP 负责标准化连接资源和工具。
- RAG 负责提供可引用的知识证据。
- Tool 负责执行动作和返回结构化结果。
- Workflow、权限、审计和人审负责控制风险。

## Optimize

### 1. 先定义任务入口和职责边界

每个系统上线前，先写清楚这几个问题：

| 问题 | 设计要点 |
| --- | --- |
| 用户会提出什么目标 | 问答、分析、生成、执行、审核还是自动化 |
| Agent 能做什么 | 规划、选择工具、整合结果，但不能绕过权限 |
| Skill 什么时候加载 | 按任务类型、领域、输入格式或用户意图触发 |
| MCP 暴露什么能力 | 资源、只读工具、写操作工具要分开 |
| RAG 提供什么知识 | 文档范围、更新频率、引用格式和空召回策略 |
| 哪些动作需要人审 | 写库、删除、发布、付款、外发、权限变更 |

边界不清时，优先把高风险能力收回到确定性 workflow 里，只把需要理解、生成和判断的部分交给模型。

### 2. 用 Skill 固化做事方法

Skill 不应该只是“你是某某专家”这种角色设定，而应该沉淀可执行流程。

一个可用 Skill 至少应包含：

- 触发条件：什么输入应该使用它。
- 前置检查：需要哪些信息、文件、权限或环境。
- 执行步骤：先做什么、后做什么、失败后怎么处理。
- 工具映射：哪些步骤要调用 MCP Tool、脚本或本地命令。
- 质量标准：输出如何验收，哪些结果必须带证据。
- 退出条件：什么时候完成、澄清、拒绝或转人工。

这样 Agent 不是凭感觉做事，而是在加载 Skill 后按已沉淀的方法执行。

### 3. 通过 MCP 暴露资源和工具

MCP 的作用不是让 Agent 可以随便调更多工具，而是让工具和资源有标准接口、标准描述和标准控制点。

建议按风险分层暴露能力：

| 能力类型 | 示例 | 控制策略 |
| --- | --- | --- |
| Resource | 文档、配置、只读数据 | 来源标注、范围控制、缓存 |
| Read-only Tool | 搜索、查询、读取日志 | 鉴权、限流、超时 |
| Write Tool | 创建工单、发邮件、改状态 | 参数校验、幂等、审批、审计 |
| High-risk Tool | 删除、付款、授权、发布 | 默认禁止自动执行，必须人工确认 |

工具返回结果应结构化，至少包含状态、结果、错误类型、证据引用和下一步建议。不要只返回一段自然语言。

### 4. 把 RAG 做成可验证的知识服务

RAG 可以作为 MCP Resource 或 Tool 暴露给 Agent，但它的输出必须可验证。

RAG 服务建议返回：

```json
{
  "query": "用户问题或改写后的查询",
  "hits": [
    {
      "chunk_id": "policy:refund:003",
      "title": "退款政策",
      "source": "kb/refund-policy.md",
      "score": 0.86,
      "text": "可引用的证据片段"
    }
  ],
  "empty_reason": null,
  "confidence": "medium"
}
```

Agent 在回答时应引用 `chunk_id`、文档来源或行号。没有证据时，应澄清、扩大检索、降级或明确说明依据不足，而不是自由发挥。

### 5. 用统一任务状态串联模块

多模块协作不能只靠对话历史。应该有统一任务状态：

| 字段 | 作用 |
| --- | --- |
| `task_id` | 串联用户请求、检索、工具调用和审批 |
| `goal` | 当前任务目标 |
| `selected_skill` | 当前加载的 Skill |
| `plan` | Agent 当前计划 |
| `evidence_refs` | RAG 返回的证据引用 |
| `tool_calls` | MCP Tool 调用记录 |
| `risk_level` | 当前任务风险等级 |
| `approval_status` | 是否需要或已经通过人工确认 |
| `final_status` | completed、failed、needs_review、cancelled |

这样即使 Agent 上下文被压缩、会话中断或工具失败，系统仍然能恢复和审计。

### 6. 典型协作流

```text
用户提出目标
  -> Agent 识别任务类型和风险等级
  -> Agent 选择或加载 Skill
  -> Skill 给出流程、检查项和输出标准
  -> Agent 通过 MCP 发现可用资源和工具
  -> 需要知识时调用 RAG，获取证据和引用
  -> 需要动作时调用 Tool，获取结构化结果
  -> Agent 基于证据和工具结果继续推进
  -> 高风险动作进入人工确认
  -> 记录 trace、状态、证据和最终结论
```

### 7. 三种常见协作模式

知识问答型：

```text
Agent 判断用户在问知识
  -> Skill 提供回答格式和证据要求
  -> MCP 调用 RAG 服务
  -> RAG 返回证据
  -> Agent 基于证据回答并附来源
```

工具执行型：

```text
Agent 拆解任务
  -> Skill 给出步骤和参数要求
  -> MCP 暴露可调用工具
  -> Agent 调用 Tool
  -> Tool 返回结构化结果
  -> Agent 汇总或进入下一步
```

长流程自动化型：

```text
Agent 制定计划
  -> Skill 约束流程和检查点
  -> MCP 连接多个系统
  -> RAG 补充领域知识
  -> Tools 执行具体动作
  -> Workflow 记录状态
  -> 高风险节点人工确认
```

## Verify

验证这类系统时，不要只看最终回答，要检查协作链路是否受控：

| 验证项 | 检查方式 |
| --- | --- |
| Agent 是否越权 | 构造无权限工具调用，确认应用层拒绝执行 |
| Skill 是否真的生效 | 检查 trace 中是否按 Skill 流程执行，有无跳过关键检查 |
| MCP 权限是否正确 | 分角色测试 Resource、只读工具和写工具可见性 |
| RAG 是否有证据 | 检查回答中的结论是否能回查到 `chunk_id` 或来源 |
| 工具参数是否可靠 | 注入错误参数，确认工具校验和错误反馈清晰 |
| 高风险动作是否拦截 | 测试删除、发布、付款、外发等动作是否触发确认 |
| 状态是否可恢复 | 中断任务后用 `task_id` 恢复，确认不会重复执行高风险动作 |
