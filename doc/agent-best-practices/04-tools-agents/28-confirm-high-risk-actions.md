# 28. 高风险动作应确认

[返回全局摘要](../README.md) · [返回本组：MCP、工具调用与多 Agent](README.md)

## Status
Recommended

Category: tools-agents

## Rule
高风险动作执行前应确认。

## Why
删除、付款、发送外部消息、修改生产数据等动作一旦执行可能难以恢复。确认步骤能降低误解、提示注入和模型误判造成的损失。

高风险动作的共同点是：一旦执行，会影响用户资产、外部关系、生产数据、合规责任或不可逆资源。模型可以帮助准备动作，但不能仅凭自然语言判断就执行。

需要确认的动作通常包括：

| 类型 | 示例 |
| --- | --- |
| 数据破坏 | 删除文件、清空表、覆盖配置 |
| 金钱资产 | 付款、退款、转账、下单 |
| 外部发送 | 发邮件、发短信、发社交媒体、提交表单 |
| 生产变更 | 发布、改权限、改数据库、改 DNS |
| 隐私安全 | 导出用户数据、分享日志、读取敏感文件 |

## Optimize
按风险分级定义确认策略。确认内容应包含具体动作、目标对象、影响范围和不可逆后果，不使用含糊的“是否继续”。

确认要绑定具体参数，而不是给 Agent 一次通用授权：

```json
{
  "action": "delete_file",
  "target": "output/tmp-report.md",
  "risk": "destructive",
  "irreversible": true,
  "confirmation_text": "确认删除 output/tmp-report.md",
  "expires_at": "2026-05-22T11:00:00+09:00"
}
```

用户确认后，执行器应生成一次性确认令牌，并绑定：

- 工具名。
- 完整参数 hash。
- 当前用户和租户。
- 任务 ID。
- 过期时间。
- 风险等级。

如果模型确认后改了参数，原确认令牌必须失效。例如用户确认删除 `tmp/a.txt`，模型不能用同一个确认去删除 `tmp/b.txt`。

风险分级可以这样设计：

| 风险等级 | 策略 |
| --- | --- |
| 只读 | 可自动执行，仍记录 trace |
| 低风险写入 | 可执行，但需要幂等和回滚 |
| 中风险写入 | 需要明确提示影响范围 |
| 高风险/不可逆 | 必须人工确认和确认令牌 |
| 禁止动作 | 无论模型如何请求都拒绝 |

## Engineering Notes

- 确认必须在应用层实现，不能只让模型问一句“是否继续”。
- 确认文案要具体到资源和影响，避免用户在不知情下同意。
- 批量操作要展示样本、数量和过滤条件，避免“删除所有”这类模糊表达。
- 生产写操作要考虑幂等、回滚和审计，不只是确认。
- 提示注入可能诱导模型跳过确认，因此执行器必须独立校验确认令牌。

## Verify
测试删除、覆盖、转账、发信和生产发布路径，确认没有确认令牌或用户确认时无法执行。

还应测试：

- 确认后参数改变，执行是否被拒绝。
- 确认令牌过期后是否失效。
- 模型尝试伪造确认令牌是否被拒绝。
- 批量操作是否展示数量、目标和不可逆影响。
- 取消确认后任务是否进入安全停止状态。
