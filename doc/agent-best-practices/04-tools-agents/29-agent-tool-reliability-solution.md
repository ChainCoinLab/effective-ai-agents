# 29. Agent 调用工具的可靠性解决方案

[返回全局摘要](../README.md) · [返回本组：MCP、工具调用与多 Agent](README.md)

## Status
Recommended

Category: tools-agents

## Rule
Agent 调用工具时，不能只靠“把 prompt 写好”。可靠性要按四层处理：结构化定义层、推理策略层、执行护栏层、自愈修复层。

![ReAct 循环控制](../assets/diagrams/react-loop-control.svg)

## Why
Agent 调用工具的可靠性问题，本质上不是“模型会不会写对 JSON”，而是模型、工具、权限、业务规则和失败恢复之间的链路问题。风险点可以拆成以下几类：

| 问题 | 表现 | 风险 |
| --- | --- | --- |
| 用户意图没分析清楚 | 用户说“订明天的票”“帮我处理订单”，模型直接选工具和填参 | 调错工具、漏掉关键信息、把模糊自然语言当成可执行参数 |
| 工具语义描述太弱 | 函数描述只写“查询订单”“更新用户”，没有说明何时用、何时不用、参数含义 | 模型无法区分相似工具，容易误选或过度调用 |
| 参数缺少结构化约束 | 日期、金额、枚举、范围、单位只靠自然语言约定 | 后端报错、脏数据写入、业务规则被绕过 |
| 调用前没有推理检查 | 模型还没想清楚就直接输出 JSON | 参数看似合法但业务逻辑错，缺字段、错字段、错工具一起出现 |
| 工具暴露过多 | 一次把几十个、上百个工具交给模型 | 上下文噪声变大，相似工具互相干扰，正确工具被淹没 |
| 模型输出直连执行 | 模型生成 JSON 后直接调用 API | 幻觉参数、越权操作和高风险副作用进入生产 |
| 工具失败没有闭环 | 网络、权限、配额、输入、依赖服务和用户取消都可能失败 | Agent 编造结果、卡在循环重试，或把内部错误直接抛给用户 |
| 执行后不做状态反思 | 工具成功返回就认为任务完成 | 返回数据没有解决用户目标，系统仍然结单 |

## Optimize
解决方案按四层落地。不要把所有内容塞进一个宽表里；每一层只回答“解决什么问题”和“怎么处理”。

### L1. 结构化定义层

这一层解决“工具和参数没有规矩”的问题。目标是先把工具调用变成机器可理解、可校验的契约。

- 强类型约束：用 JSON Schema 定义参数类型、必填字段、枚举值、范围、格式、单位、默认值和是否可为空。
- 语义描述优化：工具名、函数 description、参数 description 要像 prompt 一样认真写，说明适用场景、不适用场景、参数含义、副作用和错误返回。
- 模糊输入处理：用户说“明天”“处理一下订单”这类表达时，不要直接塞进 API；先规范化、澄清或转换成标准字段。

### L2. 推理策略层

这一层解决“模型还没想清楚就调用工具”的问题。目标是在工具执行前，让模型先完成语义判断、调用理由和工具选择。

- 思维链 / 调用前推理：要求模型在调用工具前输出可审计的思考摘要、调用理由、参数依据和检查项，说明为什么调用这个工具、关键参数从哪里来、还缺什么信息。
- 示例引导（Few-shot）：给模型少量高质量样例，覆盖正确调用、错误调用、边界参数、拒绝调用和需要澄清的场景。
- 工具检索（RAG）：工具很多时，不把全部工具塞给模型；先根据用户意图、权限和风险召回 Top-K 相关工具，减少相似工具干扰。

调用前推理要谨慎落地：不要把完整私有 chain-of-thought 当成审计材料，而是保留可公开的调用理由摘要、参数依据和检查清单。审计系统需要回答的是“为什么调用这个工具、用了哪些参数、谁批准、结果是什么”。

### L3. 执行护栏层

这一层解决“模型输出直接进入生产系统”的问题。目标是让应用层成为真正的执行边界。

- 自动格式校验：用 Pydantic、JSON Schema validator 或业务 DTO 校验模型输出；格式不符合、字段缺失、枚举非法、范围异常时直接拦截，不进入执行环节。
- 业务规则校验：检查库存、金额、时间、状态流转、租户边界、幂等键和速率限制，不把这些判断交给模型自由发挥。
- 人机交互（HITL）：删除、付款、转账、发信、改密、生产写入等高风险动作必须要求确认令牌或人工确认。

### L4. 自愈修复层

这一层解决“失败后编造结果或死循环”的问题。目标是把错误和结果反馈变成下一轮修复输入。

- 错误回传机制：把工具错误转成结构化 observation，包含错误类型、字段级错误、可重试标志、用户可操作信息和建议下一步，再让模型基于错误修正参数或重新规划。
- 状态反思：工具返回后检查任务状态、结果完整性、剩余风险和用户目标是否满足；不满足就继续规划、请求补充、降级或明确失败。
- 重试与熔断：限制最大重试次数；连续同类错误、成本超限、风险升高或修复无进展时停止自动执行，转为澄清、降级或人工接管。

工具失败要按正常路径设计，不要当成异常边角。超时、403、404、限流、无效参数、空结果和用户取消都应有明确分支。

## Flow

```text
用户目标
  -> L1 结构化定义：工具 schema、参数约束、语义描述、模糊输入规范化
  -> L2 推理策略：调用前推理、few-shot 引导、Top-K 工具检索
  -> L3 执行护栏：格式校验、业务规则校验、权限校验、高风险确认
  -> Tool 执行动作并返回结构化结果或错误
  -> L4 自愈修复：错误回传、状态反思、重试熔断、降级或人工接管
  -> trace 进入回放、评测和回归
```

在 ReAct 循环里，这条链路必须被 Loop Controller 约束：

| 控制项 | 作用 |
| --- | --- |
| 最大轮次 | 防止无限循环 |
| 最大工具调用次数 | 控制成本和风险 |
| 重复调用检测 | 防止同一工具同一参数反复失败 |
| 错误类型分流 | 区分可重试、需澄清、需授权和不可恢复错误 |
| 完成前验证 | 工具成功不等于用户目标完成 |
| 熔断和转人工 | 成本超限、风险升高或多次失败时暂停自动执行 |

工具错误不要只提示“再试一次”。如果错误原因没变，重试只会重复失败。应把错误转成结构化 observation，并让下一步策略发生变化：修正参数、换工具、请求用户补充、降级或停止。

## Verify
验证 Agent 工具调用链路时，不只看最终回答，还要检查：

- 工具 schema 是否覆盖类型、必填、枚举、范围、格式、单位和默认值。
- 工具描述是否写清语义边界：何时调用、何时不用、参数含义和副作用。
- 调用前是否有可审计的调用理由摘要、参数依据和检查项。
- few-shot 是否覆盖正确调用、错误调用、边界参数、拒绝调用和需要澄清的场景。
- 相似工具、无需工具、多意图请求是否能通过工具检索稳定选对或请求澄清。
- 模型输出参数是否经过 schema、业务规则、权限和风险校验。
- 删除、付款、发信、改密、生产写入等动作是否必须确认后才能执行。
- 超时、403、404、限流、无效参数、空结果和用户取消是否返回结构化 observation。
- 自动修复是否有最大重试次数，失败后是否会停止、解释、澄清或转人工。
- 工具返回后是否验证结果真的满足用户目标，而不是只看 API 调用成功。
- trace 是否能还原语义分析、工具选择、参数、校验、确认、执行、错误修复和最终响应。

## Summary

Agent 调用工具的可靠性解决方案，可以概括为一个公式：可靠性 = (高质量数据 + 严格约束) x 闭环反馈机制。预防胜于治疗，L1 和 L2 通过严格 schema、清晰语义、调用前推理、few-shot 和工具检索，在源头降低误调用；工程逻辑负责兜底，L3 用 Pydantic、JSON Schema、业务规则、权限和人工确认约束模型的概率输出；闭环反馈负责自愈，L4 让 Agent 基于结构化错误修正参数、重新规划、验证结果，并在必要时熔断或交给人工。
