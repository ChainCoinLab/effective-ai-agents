# 34A. 长文本多轮执行要工程化闭环

[返回全局摘要](../README.md) · [返回本组：工具调用与多 Agent](README.md)

## Status
Recommended

Category: tools-agents

## Rule
长文本任务只要需要多轮处理、反复执行或持续修正，就不能只靠一次性 Prompt。系统必须把它设计成可分块、可观察、可恢复、可熔断、可结单的工程闭环。

## Why
长文本任务的问题不只是“文本很长”，而是它通常同时具备三个特征：

- 输入长：文档、日志、代码仓库、转写稿、合同、工单链路或 traceback 可能远超单轮上下文。
- 过程长：需要分段读取、提取、校验、修正、合并，而不是一次生成最终答案。
- 反馈长：每一轮工具执行、模型判断、错误信息和中间结果都会继续增加上下文。

如果把所有内容和所有中间结果都塞进上下文，会触发几个典型问题：

| 问题 | 产生原因 | 后果 |
| --- | --- | --- |
| 上下文爆炸 | 原文、历史、工具结果、错误日志持续叠加 | token 成本升高，系统指令和任务目标被挤出 |
| 迷失中间 | 模型对长上下文中间部分关注变弱 | 中间证据被忽略，结论只依赖开头或结尾 |
| 死循环 | 多轮修复没有进展检测和退出条件 | 一直重试、一直改、一直错，任务无法结束 |
| 幻觉修复 | 模型为了推进任务编造事实、API、代码或引用 | 错误越修越多，结果看似完整但不可验证 |
| 无法结单 | 没有完成标准、覆盖率和剩余风险记录 | 不知道任务是否真的完成，也无法交接人工 |

长文本多轮任务的核心不是“让模型读更多”，而是把模型放进一个受控执行系统里：模型负责局部判断和候选生成，工程系统负责分块、状态、验证、熔断和结单。

## Optimize

### 1. 先把长文本拆成可执行单元

不要让模型直接面对整份长文本。先按任务目标把文本拆成可处理单元：

- 文档：按章节、标题、表格、条款、页码拆分。
- 日志：按时间窗口、错误类型、请求 ID、trace ID 拆分。
- 代码仓库：按模块、文件、调用链、测试范围拆分。
- 转写稿：按主题段落、说话人、时间轴拆分。
- traceback：按异常类型、最后 3-5 行关键栈帧、业务栈帧和框架栈帧拆分。

每个单元都要有稳定 ID，例如 `chunk_id`、`task_id`、`trace_id` 或 `file_path:line`。没有稳定 ID，后续就无法追踪“哪一段处理过、哪一段失败、哪一段需要重试”。

### 2. 用状态表管理多轮进度

多轮处理不能只靠聊天历史记住进度。应该有一张确定性状态表：

| 字段 | 作用 |
| --- | --- |
| `unit_id` | 当前处理的文本块、文件、日志段或子任务 |
| `status` | pending、running、passed、failed、needs_review、skipped |
| `attempts` | 已尝试次数 |
| `last_observation` | 最近一次工具结果、错误摘要或验证反馈 |
| `evidence_refs` | 本轮结论依赖的原文位置、chunk、行号或工具输出 |
| `open_issues` | 未解决问题和阻塞点 |
| `next_action` | 下一轮要执行的动作 |

模型可以读取状态表的必要部分，但状态表本身应由应用或工作流系统维护。这样即使上下文被压缩、会话中断或模型切换，任务也能恢复。

### 3. 每轮只给模型必要上下文

长文本任务最容易犯的错，是每轮都把全文、全历史和全错误日志重新塞给模型。

更稳的上下文结构是：

```text
稳定规则: 任务目标、输出格式、权限边界、停止条件
当前单元: 本轮要处理的 chunk / 文件 / 日志片段
必要记忆: 已确认事实、全局约束、前几轮摘要
观察结果: 上一轮工具输出、错误摘要、验证反馈
下一步要求: 本轮只做什么，不做什么
```

这里要显式处理“迷失中间”现象：如果证据在长上下文中间，模型可能忽略它。工程上不要指望模型在超长输入中自然抓住中间证据，而应使用索引、摘要层、检索或任务队列，把当前要处理的证据放到本轮上下文的显著位置，并要求输出引用具体 `unit_id` 或原文位置。

### 4. 把工具错误变成 observation

长文本多轮任务往往会调用工具：代码解释器、搜索、数据库、解析器、linter、测试、文档检索等。工具失败时，不要直接把原始错误全部塞回上下文，也不要直接重跑。

应该由 Error Handler 生成结构化 observation：

```json
{
  "unit_id": "file:src/report.py",
  "tool": "python_interpreter",
  "status": "failed",
  "error_type": "ZeroDivisionError",
  "traceback_excerpt": [
    "File \"report.py\", line 42",
    "rate = total / count",
    "ZeroDivisionError: division by zero"
  ],
  "attempt": 2,
  "max_attempts": 3,
  "suggested_next_action": "检查 count 为 0 的分支，不要重写无关逻辑。"
}
```

Observation 的目标是让模型知道“上一轮为什么失败、失败在哪里、下一轮应该修什么”，而不是把所有日志当作上下文垃圾堆进去。

### 5. 对死循环做熔断

多轮任务必须有熔断条件。常见熔断信号包括：

| 熔断信号 | 说明 | 处理方式 |
| --- | --- | --- |
| `attempts >= max_attempts` | 同一单元超过最大尝试次数 | 停止自动修复，标记 `needs_review` |
| 错误类型连续相同 | 多次修复没有改变根因 | 要求换策略，或转人工 |
| 输出 diff 很小但错误不变 | 模型在原地打转 | 禁止继续微调，要求重新分析原因 |
| 新错误数量增加 | 修复引入更多问题 | 回滚到上一个可用版本 |
| 成本或时间超限 | 任务不再值得自动继续 | 结单并说明未完成部分 |

熔断不是失败，而是工程边界。没有熔断，Agent 会把“不确定”伪装成“继续努力”，最后变成无限循环。

### 6. 对幻觉做验证和约束

长文本多轮任务里的幻觉通常有三类：

- 事实幻觉：总结了原文没有的结论。
- 引用幻觉：声称引用了某段文字，但 `chunk_id` 或行号并不支持结论。
- 修复幻觉：编造不存在的函数、参数、库、政策或 API。

处理方式：

| 幻觉类型 | 工程约束 |
| --- | --- |
| 事实幻觉 | 输出必须绑定原文位置、chunk、页码或行号 |
| 引用幻觉 | 引用必须能被程序回查，不能只写自然语言来源 |
| API / 代码幻觉 | 接官方文档 RAG、linter、类型检查、单元测试或运行验证 |
| 策略幻觉 | 高风险动作必须走人工确认或确定性规则 |

对长文本任务，最好把“生成答案”和“验证答案”拆开：第一步让模型生成候选结论，第二步用检索、规则、测试或另一个 judge 检查每条结论是否有证据。

### 7. 结单要有完成标准

长文本多轮任务不能只输出一个“完成了”。结单时至少要给出：

- 已处理范围：哪些 `unit_id` 已完成，覆盖率是多少。
- 关键结论：每条结论绑定证据位置。
- 未处理范围：哪些块跳过、失败或需要人工审核。
- 重试记录：哪些单元触发过错误、重试和熔断。
- 剩余风险：哪些结论置信度低，哪些动作不能自动执行。
- 下一步建议：继续自动处理、人工复核、补充数据或停止。

结单的本质是把多轮过程收口成可审计结果。没有结单，长任务即使看似输出了答案，也无法判断它是不是遗漏了中间部分、跳过了失败块，或者在最后一轮产生了新幻觉。

## Flow

```text
长文本输入
  -> 分块 / 建索引 / 生成 unit_id
  -> 初始化状态表
  -> 选择下一批 pending 单元
  -> 给模型本轮必要上下文
  -> 调用工具或生成局部结果
  -> 记录 observation
  -> 验证证据、格式、工具结果
  -> 更新状态表
  -> 判断是否继续、换策略、熔断或结单
  -> 输出结单报告
```

## Verify

验证这类系统时，不要只看最终答案，要看多轮过程是否受控：

| 验证项 | 检查方式 |
| --- | --- |
| 分块是否完整 | 抽查 `unit_id` 覆盖率，确认没有漏段 |
| 是否迷失中间 | 构造答案位于中间 chunk 的样例，检查能否引用正确证据 |
| 状态是否可恢复 | 中断任务后从状态表恢复，确认不会重复或跳过单元 |
| 熔断是否生效 | 注入无法修复的错误，确认达到次数后停止并标记 `needs_review` |
| 死循环是否被识别 | 连续返回相同错误，检查系统是否换策略或停止 |
| 幻觉是否被拦截 | 构造不存在的 API、条款、引用，检查 RAG、linter、测试或证据校验是否拦截 |
| 结单是否可审计 | 检查结单报告是否包含覆盖率、失败块、证据引用和剩余风险 |
