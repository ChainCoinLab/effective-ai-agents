# 36 Eval 数据覆盖真实分布和边界

[返回全局摘要](../README.md) · [返回本组：测试、评测与验证](README.md)

## Rule
Eval 数据集应同时覆盖真实生产分布、高频场景、长尾边界、异常输入和高风险任务。

## Why
只用理想样例会高估系统能力。真实用户输入常包含歧义、缺失信息、噪声、冲突目标和超出预期的边界条件。

Eval 数据决定评测结论是否可信。如果样例只来自开发者手写的“标准问题”，系统在线上一定会被真实输入打穿。真实用户会输入错别字、模糊代词、半句话、截图、粘贴日志、过期信息、恶意指令，也会提出互相冲突的目标。

数据集应覆盖几个维度：

| 维度 | 示例 |
| --- | --- |
| 高频正常路径 | 最常见的客服问题、文档问答、代码修改 |
| 长尾边界 | 少见产品、旧版本、特殊地区、特殊权限 |
| 缺失信息 | 没有订单号、没有文件路径、没有时间范围 |
| 冲突信息 | 用户说法和数据库不一致、文档版本冲突 |
| 攻击输入 | 提示注入、越权、泄露请求、危险工具诱导 |
| 系统失败 | 工具超时、检索为空、限流、权限不足 |

## Optimize
从生产日志、客服问题、失败案例和领域专家样例中采样，并为边界样例单独打标签，避免被平均分掩盖。

Eval 数据可以分层维护：

```text
core_set: 每次变更都跑，覆盖最高价值任务
regression_set: 历史失败和修复样例
boundary_set: 长尾、缺字段、冲突和高风险场景
attack_set: 注入、越权、泄露和恶意工具调用
shadow_set: 从生产抽样但暂不用于发布门禁
```

每条样例至少要包含：

- 输入。
- 任务类型和风险等级。
- 期望行为，不一定是唯一标准答案。
- 必须使用或禁止使用的证据/工具。
- 评分标准。
- 来源和版本。

对 Agent 任务，期望行为要覆盖中间过程。例如“必须先读取 README.md”“不得调用 write_file”“检索为空时返回 insufficient_evidence”。只写最终答案会漏掉过程风险。

## Engineering Notes

- 不要让训练/调参样例和最终评测样例混在一起，否则会高估效果。
- 数据集要去重，避免同一模式重复出现让分数虚高。
- 高风险样例要单独报告，通过率不能被大量低风险样例平均掉。
- 生产日志进入 eval 前要脱敏和授权。
- 样例标签要版本化，业务标准变化后需要记录口径变化。

## Verify
每次评测报告都按场景类型拆分结果，确认高频样例和边界样例都有独立通过率。

还应检查：

- 是否包含真实生产输入，而不只是人工理想输入。
- 是否覆盖缺字段、冲突、空检索、工具失败和攻击样例。
- 是否按风险等级报告结果。
- 历史线上事故是否都进入 regression_set。
