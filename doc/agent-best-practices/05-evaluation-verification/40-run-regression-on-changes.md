# 40 Prompt/模型/知识库/工具变更跑回归

[返回全局摘要](../README.md) · [返回本组：测试、评测与验证](README.md)

## Rule
任何 prompt、模型、知识库、工具 schema、权限策略或编排逻辑变更，都应触发相关回归评测。

## Why
AI 系统依赖多个可变部件，小改动可能改变推理路径、检索命中、工具选择或输出风格。没有回归评测会让质量退化隐性进入生产。

Agent 系统里，很多看似局部的改动都会影响整体行为：

| 变更 | 可能影响 |
| --- | --- |
| Prompt 改写 | 输出风格、拒答边界、工具调用倾向 |
| 模型升级 | 推理路径、格式稳定性、成本和延迟 |
| 知识库更新 | 召回结果、引用、事实新鲜度 |
| chunk 策略变更 | context recall、证据完整性 |
| 工具 schema 变更 | 参数填充、校验失败、权限判断 |
| 权限策略变更 | 自动执行范围、人工确认比例 |
| 编排逻辑变更 | 轮次、handoff、失败恢复 |

## Optimize
按变更类型维护 eval 子集：prompt 变更跑核心任务，知识库变更跑检索和引用，工具变更跑参数和权限。

推荐建立变更到回归集的映射：

| 变更类型 | 必跑回归 |
| --- | --- |
| Prompt | 核心任务、拒答、格式、工具选择 |
| Model | 核心任务、成本延迟、格式稳定、judge 校准 |
| RAG 数据 | context recall、citation、空检索、权限过滤 |
| Tool schema | 参数合法性、错误返回、确认流程 |
| Workflow | 状态恢复、熔断、handoff、端到端任务 |
| Safety policy | 注入、越权、敏感信息、红线样例 |

CI 可以跑小集合，发布前跑完整集合，灰度后用线上 trace 验证真实分布。关键是每次变更都有“为什么跑这些测试”的映射，而不是只跑固定一小批理想样例。

## Engineering Notes

- 回归要保存失败 diff：是最终答案变了，还是检索、工具、状态、权限路径变了。
- 对概率输出，评测应允许合理表达差异，但不能放过事实、格式、权限和证据错误。
- 模型升级要和成本、延迟、上下文窗口、工具能力一起评估。
- 知识库更新要检查旧引用是否失效。
- 回归通过不代表可以全量发布，高风险系统仍应灰度。

## Verify
CI 或发布流程中检查评测记录，确认变更对应的回归集已通过并可追溯到版本。

还应检查：

- 失败样例是否被归因并关联到变更。
- 评测报告是否记录 Prompt、模型、索引、工具和代码版本。
- 变更回滚时是否能回滚相关配置，而不是只回滚代码。
- 灰度指标是否验证了离线回归结论。
