# 39 评测指标和业务风险绑定

[返回全局摘要](../README.md) · [返回本组：测试、评测与验证](README.md)

## Rule
评测指标应映射到业务风险，而不是只报告通用准确率、平均分或主观满意度。

## Why
不同错误的代价不同。低风险任务的小错误和高风险任务的误导、越权、泄露或错误执行不应被同等平均。

一个总体准确率可能掩盖关键风险：1000 个低风险摘要任务全对，1 个生产删除动作误执行，整体分数仍然很好，但业务上不可接受。Agent 系统必须按风险看指标。

风险绑定要回答：

| 任务类型 | 主要风险 | 指标重点 |
| --- | --- | --- |
| 知识问答 | 幻觉、引用错误、过时信息 | faithfulness、citation accuracy、拒答率 |
| 工具执行 | 错工具、错参数、越权 | tool accuracy、permission violation、confirmation rate |
| 代码修改 | 引入 bug、破坏无关文件 | 测试通过率、diff 范围、回归失败 |
| 客服/金融/医疗 | 误导、合规、安全 | 红线违规率、人工接管率、审计通过率 |
| 长任务 Agent | 死循环、成本失控、状态丢失 | step count、tool calls、恢复成功率 |

## Optimize
为每类任务定义风险等级、失败代价和阻断阈值；对安全、合规、金钱、权限相关错误设置单独红线指标。

指标设计不要只追求“越高越好”。有些指标需要平衡：

- 拒答率太低，可能说明系统在无证据时乱答。
- 拒答率太高，可能说明系统过度保守。
- 工具调用率太低，可能漏查实时数据。
- 工具调用率太高，可能过度调用和成本浪费。
- 人工接管率太低，可能高风险动作没有正确升级。

建议为每个风险等级设置发布门禁：

| 风险等级 | 发布要求 |
| --- | --- |
| 低 | 总体质量和成本不退化 |
| 中 | 场景通过率、格式错误率、工具失败率达标 |
| 高 | 红线违规为 0，权限和确认测试全通过 |
| 禁止 | 不允许自动执行，只能拒绝或转人工 |

## Engineering Notes

- 总体均值只能做概览，不能作为高风险发布依据。
- 指标要和 trace 关联，否则只能知道坏了，不知道坏在哪里。
- 业务指标和模型指标要同时看：答案质量提升但成本翻倍，也可能不可接受。
- 指标阈值要随着产品阶段调整，但调整必须有记录。
- 高风险红线优先于平均分提升。

## Verify
发布前检查评测报告是否包含风险分层结果，并确认高风险指标未被总体均值掩盖。

还应检查：

- 每个关键任务是否定义失败代价和阻断阈值。
- 红线指标是否单独展示。
- 指标变化是否能追溯到 Prompt、模型、工具或数据版本。
- 是否存在质量提升但安全、成本或延迟退化的情况。
