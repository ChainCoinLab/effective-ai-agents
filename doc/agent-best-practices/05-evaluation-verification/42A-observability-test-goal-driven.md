# 42A. 可观测性要区分测试驱动和目标驱动

[返回全局摘要](../README.md) · [返回本组：测试、评测与验证](README.md)

## Status
Recommended

Category: evaluation-verification

## Rule
可观测性不是先堆日志，而是先明确观察模式：测试驱动观测和目标驱动观测。

## Why
AI 系统的失败经常不是单点错误，而是目标、上下文、工具、权限、模型输出和恢复策略之间的链路偏差。只记录请求和响应，无法回答“为什么偏了”“偏离哪个标准”“下一步该修什么”。

测试驱动观测从已知断言出发，适合验证系统是否按预期工作。目标驱动观测从用户目标、业务目标或 SLO 出发，适合判断系统是否真正完成任务，以及瓶颈在哪一层。

## Optimize
建立两种互补的观测模式。

| 观测模式 | 起点 | 代表意思 | 常见实践 | 适用场景 |
| --- | --- | --- | --- | --- |
| 测试驱动观测 | 测试、eval、断言、回归样例 | 先定义“应该发生什么”，再收集能证明它发生或没发生的信号 | 为每个关键任务写 eval；在 trace 中记录步骤、输入、输出、工具参数、权限判断和错误类型；失败样例进入回归集 | 发布前验证、回归测试、修复确认、过程正确性检查 |
| 目标驱动观测 | 用户目标、业务目标、任务成功标准、SLO | 先定义“要达成什么目标”，再反推要观察哪些链路指标 | 把目标拆成任务成功率、人工接管率、拒答率、成本、延迟、工具失败率、安全拦截率、投诉率；按目标分层看 trace 和指标 | 线上监控、产品质量、业务风险、长期优化 |

两种模式要连起来：测试驱动观测回答“这条链路有没有按设计运行”，目标驱动观测回答“这个设计有没有真正服务目标”。

## Flow

```text
目标驱动观测
  -> 定义用户目标 / 业务目标 / SLO
  -> 拆成可观测指标和关键链路
  -> 找到偏离目标的场景
  -> 沉淀为 eval / regression case
  -> 测试驱动观测验证修复
  -> 回到线上目标指标继续观察
```

## Verify
检查一个关键 AI 工作流是否能同时回答两组问题：

- 测试驱动：预期步骤是什么？每步是否发生？参数是否符合约束？失败是否进入回归样例？
- 目标驱动：这个任务的成功标准是什么？线上指标是否支持这个标准？失败集中在哪类目标、用户、工具或成本区间？

如果只能看到日志，但无法关联测试、目标和修复动作，说明还没有形成可观测性闭环。
