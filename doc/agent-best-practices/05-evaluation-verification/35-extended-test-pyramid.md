# 35 AI 系统需要扩展测试金字塔

[返回全局摘要](../README.md) · [返回本组：测试、评测与验证](README.md)

## Rule
AI 系统测试不应只停留在单元测试，需要覆盖 prompt、检索、工具调用、模型输出、端到端任务和线上监控。

## Why
LLM 行为具有概率性，失败可能来自上下文、工具、模型版本或任务编排。传统测试金字塔不足以发现这些组合风险。

传统测试金字塔主要覆盖确定性代码：单元测试、集成测试、端到端测试。Agent 系统还多了几类不确定因素：模型输出、Prompt、RAG、工具选择、权限策略、上下文裁剪、外部服务和人工确认。只测业务代码通过，不代表 Agent 行为可靠。

扩展后的测试金字塔可以这样看：

| 层级 | 测什么 | 示例 |
| --- | --- | --- |
| 单元测试 | 确定性函数、schema、权限规则 | 参数校验、路径过滤、状态机转移 |
| 组件测试 | 检索、Prompt Builder、工具执行器 | chunk 召回、上下文拼装、工具错误返回 |
| Agent 过程测试 | 中间步骤是否正确 | 是否读取必要文件、是否先确认再写入 |
| Eval | 语义输出和任务完成质量 | 回答忠实性、引用准确性、任务成功率 |
| 端到端测试 | 用户任务完整链路 | 从输入到工具调用、状态更新、最终响应 |
| 线上监控 | 真实分布下的质量、成本、延迟、安全 | 人工接管率、P95 延迟、工具失败率 |

## Optimize
把测试分层：确定性代码用单元测试，Agent 流程用集成测试，关键任务用 eval，生产行为用监控和抽样复核。

不同层级不要互相替代。单元测试保证执行器不会越权，但不能保证模型会选对工具；eval 能判断答案质量，但不能证明确认令牌有效；线上监控能发现生产退化，但不能替代发布前回归。

一个实用安排：

- PR 阶段：跑确定性单元测试、schema 测试和少量核心 eval。
- 发布前：跑任务级 eval、反例样例、工具权限样例和回归集。
- 灰度阶段：监控任务成功率、人工接管、拒答、成本、延迟和安全拦截。
- 生产阶段：抽样 trace，失败样例回流到 eval。

## Engineering Notes

- Eval 不是测试金字塔的替代品，而是新增的一层。
- 对高风险动作，确定性权限测试优先级高于模型评测。
- Agent 测试要记录中间 trace，否则无法定位失败层。
- 测试数据要分场景统计，不要只看总体平均分。
- 模型版本和 Prompt 版本变化要触发相关测试子集。

## Verify
检查每个关键用户任务是否至少有一条端到端 eval，并确认工具调用、检索结果和最终输出都有可观测记录。

还应检查：

- 每个高风险工具是否有权限和确认测试。
- 每个关键 RAG 场景是否有检索和生成拆分评测。
- 每个 Prompt 变更是否有回归记录。
- 线上失败是否能回流成测试样例。
