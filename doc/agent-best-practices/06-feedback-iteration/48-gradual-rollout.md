# 48 灰度发布

[返回全局摘要](../README.md) · [返回本组：反馈闭环与迭代](README.md)

## Rule
Agent 能力、模型、prompt、工具和知识库更新应优先灰度发布，逐步扩大流量。

## Why
离线评测无法覆盖所有真实输入。灰度发布能在影响范围受控的情况下发现质量、成本、延迟和安全问题。

AI 系统的行为受模型、Prompt、上下文、工具、知识库和用户输入共同影响。即使离线 eval 全通过，真实环境仍可能出现新的输入分布、权限组合、工具故障和成本峰值。一次性全量切换会把未知风险直接推给所有用户。

## Optimize
按用户、任务类型、风险等级或流量比例分阶段放量，并设置自动回滚条件和人工停止开关。

灰度策略可以按风险设计：

| 阶段 | 范围 | 目标 |
| --- | --- | --- |
| Shadow | 只旁路运行，不影响用户 | 比较输出和成本 |
| Internal | 内部用户或测试账号 | 验证真实交互和 trace |
| Low-risk | 低风险任务、小流量 | 观察质量、成本、延迟 |
| Expanded | 扩大用户和任务范围 | 验证稳定性和边界 |
| Full | 全量 | 持续监控和回滚准备 |

回滚条件要预先定义，例如：

- 红线安全样例失败。
- P95 延迟超过阈值。
- 单任务成本超过预算。
- 工具失败率或人工接管率异常上升。
- 高风险投诉或人工审核失败增加。

## Engineering Notes

- 灰度开关要能按模型、Prompt、工具、知识库和用户分组控制。
- 回滚不能只回滚代码，Prompt、模型路由、索引版本和工具 schema 也要可回滚。
- 高风险能力优先 shadow 或内部灰度，不应直接开放。
- 灰度期间要抽样 trace，而不只看聚合指标。
- 灰度样本量不足时，不要过早得出“没问题”的结论。

## Verify
灰度期间检查关键指标和抽样 trace，确认达到放量标准后再进入下一阶段。

还应检查：

- 是否有明确放量和停止标准。
- 版本差异是否能从 trace 中识别。
- 回滚后指标是否恢复。
- 灰度中发现的问题是否进入 eval 和回归。
