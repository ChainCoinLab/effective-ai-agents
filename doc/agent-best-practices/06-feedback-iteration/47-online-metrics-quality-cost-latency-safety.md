# 47 线上指标同时看质量成本延迟安全

[返回全局摘要](../README.md) · [返回本组：反馈闭环与迭代](README.md)

## Rule
线上监控应同时覆盖质量、成本、延迟和安全，不应只看调用成功率或用户满意度。

## Why
Agent 改进常存在权衡：质量提高可能带来成本和延迟上升，工具更多可能增加安全风险。单一指标会误导决策。

线上指标要同时看“能不能完成任务”和“以什么代价完成”。一个新 Prompt 可能让答案更完整，但 token 翻倍、P95 延迟上升、工具调用暴增；一个新模型可能提高平均质量，但高风险拒答下降；一个新 RAG 策略可能提高召回，但引入更多过期证据。

## Optimize
建立发布看板，包含任务成功率、人工接管率、拒答率、成本、P95 延迟、首 token 延迟、缓存命中率、工具失败率、安全拦截和投诉率。

建议指标分四组：

| 维度 | 指标 |
| --- | --- |
| 质量 | 任务成功率、首轮解决率、人工审核通过率、引用准确率 |
| 成本 | 输入/输出 token、工具调用次数、单任务成本、缓存命中率 |
| 延迟 | P50/P95/P99、首 token 延迟、工具等待时间 |
| 安全 | 拒答率、安全拦截率、越权尝试、确认触发率、敏感信息泄露 |

指标要按任务类型、用户群、风险等级、模型版本和 Prompt 版本切分。只看全局平均值，会掩盖某个高风险子场景的退化。

## Engineering Notes

- 质量提升不能自动抵消安全退化。
- 成本指标要按完成任务计，而不是只按单次请求计；多轮 Agent 会放大成本。
- 延迟要拆分模型、检索、工具、rerank、验证各段。
- 拒答率要结合准确性看，过低和过高都可能有问题。
- 指标看板要能跳转到 trace，否则无法定位原因。

## Verify
每次发布后比较新旧版本指标，确认没有在成本、延迟、缓存命中或安全上换取不可接受的质量提升。

还应检查：

- 灰度用户和对照组是否按同一口径比较。
- P95/P99 是否退化，即使平均延迟没变。
- 工具失败率和重试次数是否上升。
- 安全拦截下降是否源于策略变弱。
- 指标异常是否能追溯到版本和 trace。
