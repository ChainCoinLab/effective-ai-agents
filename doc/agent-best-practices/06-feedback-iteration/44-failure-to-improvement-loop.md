# 44 从失败到改进闭环

[返回全局摘要](../README.md) · [返回本组：反馈闭环与迭代](README.md)


## Rule
每个重要失败都应经过复现、归因、修复、验证、发布和监控的完整闭环。

## Why
只修表面输出容易让问题换一种形式复发。闭环处理能确保团队理解失败机制，并验证改动确实降低了风险。

Agent 失败要按工程缺陷处理，而不是只改一两句 Prompt。一个错误答案可能来自检索、工具、状态、权限、Prompt、模型、用户交互或业务规则。没有闭环，团队很容易修表象：把某个答案调对了，但同类问题换个说法又失败。

## Optimize
为失败处理建立固定模板：现象、影响、根因、修复方案、回归样例、发布版本和线上观察指标。

建议固定流程：

```text
1. 复现：拿到输入、上下文、工具结果和模型输出
2. 定级：判断用户影响和风险等级
3. 归因：定位主因和次因
4. 修复：选择 Prompt、RAG、工具、权限、状态或产品流程改动
5. 验证：新增或更新 eval，跑相关回归
6. 发布：灰度放量，保留回滚路径
7. 观察：跟踪线上指标和同类反馈
8. 沉淀：更新规范、模板或检查清单
```

失败修复要匹配根因：

| 根因 | 修复方向 |
| --- | --- |
| 检索没召回 | 改 chunk、query、索引、rerank |
| 证据被忽略 | 改生成约束、引用验证、verifier |
| 工具参数错 | 改 schema、描述、few-shot、校验 |
| 越权或高风险 | 改权限层、确认流程、红队样例 |
| 状态丢失 | 改状态机、checkpoint、幂等 |
| 用户目标不清 | 改澄清策略和退出路径 |

## Engineering Notes

- 复现优先于修复。不能复现的问题很难证明已修好。
- 失败要记录主因和次因，避免所有问题都变成“Prompt 不好”。
- 修复要带回归样例，否则下一次变更会再次破坏。
- 发布后要看同类指标是否下降，而不是只确认单个样例通过。
- 无法自动修复的问题也要明确降级或人工接管策略。

## Verify
关闭问题前确认失败样例已加入 eval，修复已通过回归，线上指标没有出现新的退化。

还应检查：

- 是否能从 trace 证明根因。
- 修复方案是否改在正确层级。
- 是否有灰度和回滚记录。
- 同类失败是否被聚合分析。
