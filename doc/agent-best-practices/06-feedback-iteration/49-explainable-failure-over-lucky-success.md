# 49 可解释失败比偶然成功更有价值

[返回全局摘要](../README.md) · [返回本组：反馈闭环与迭代](README.md)

## Rule
调试和评估时，应优先追求可解释、可复现、可定位的失败，而不是依赖偶然成功样例证明系统可用。

## Why
偶然成功无法说明系统稳定性。可解释失败能暴露模型、上下文、工具或策略的真实短板，是持续改进的入口。

在概率系统里，单次成功很容易误导团队。模型可能碰巧答对、碰巧选对工具、碰巧引用了正确证据，但下一次换个表达就失败。相比之下，一个可复现、可解释的失败能明确告诉团队该修哪一层。

可解释失败至少要保留：

- 原始输入。
- Prompt 和上下文快照。
- 检索候选和最终注入内容。
- 工具调用参数和结果。
- 权限和确认决策。
- 模型输出。
- verifier 结果。
- 失败分类和根因。

## Optimize
保留失败 trace、输入、检索结果、工具参数和输出版本；对非确定性任务记录多次运行结果和差异。

调试时建议做多次重放：

```text
同一输入 + 同一版本 + 固定采样参数
-> 看是否稳定复现

同一输入 + 新修复版本
-> 看失败是否消失

相似输入变体
-> 看修复是否泛化
```

如果失败不能稳定复现，也要记录差异：不同运行的工具选择、引用证据、输出结构和安全判断是否不同。非确定性差异本身就是工程风险。

## Engineering Notes

- 不要用“这次跑通了”关闭问题，要证明失败机制被修复。
- 成功样例也要看过程，答案对但绕过权限仍然是失败。
- 对偶然成功要警惕过拟合 Prompt：只修了一个表达，没有修一类问题。
- 失败 trace 要能脱敏共享给团队，否则知识无法沉淀。
- 解释失败时要分清主因和次因，避免修错层。

## Verify
复盘时确认关键失败能被复现并归因，且修复后对应样例进入回归集。

还应检查：

- 修复是否通过相似变体，而不只是原样例。
- 是否记录失败前后的 trace 差异。
- 是否能解释为什么新版本不会再走旧失败路径。
- 是否把经验更新到规范或检查清单。
