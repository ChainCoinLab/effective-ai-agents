# 45 反馈不等于直接训练模型

[返回全局摘要](../README.md) · [返回本组：反馈闭环与迭代](README.md)


## Rule
用户反馈不应未经筛选就直接用于训练或微调模型，应先完成清洗、标注、授权、隐私和质量审查。

## Why
原始反馈可能包含隐私数据、恶意输入、错误偏好、噪声和版权风险。直接训练会把问题固化进模型行为。

用户反馈是原材料，不是训练数据。一个 thumbs down 可能表示事实错、语气不喜欢、产品流程不符合预期、用户自己输入有误，或者模型本来应该拒绝但用户不满意。未经分析直接训练，会把噪声、攻击、敏感信息和错误偏好放大。

## Optimize
先把反馈用于错误分析、eval 扩充、prompt 改进和知识库修正；只有高质量、合规、代表性数据才进入训练流程。

反馈使用优先级通常是：

| 阶段 | 用法 |
| --- | --- |
| 立刻可用 | 归因、修 bug、补 eval、补反例 |
| 短期改进 | 改 Prompt、改工具描述、改知识库、改权限 |
| 中期治理 | 改数据标注、rubric、LLM-as-judge 校准 |
| 长期训练 | 经过授权、脱敏、标注和质量审查后再微调或偏好优化 |

进入训练前至少要检查：

- 用户是否授权用于训练。
- 是否含敏感信息或版权风险。
- 标签是否准确，是否有人工审核。
- 样例是否代表目标分布，而不是极端噪声。
- 是否会强化错误偏好或规避安全策略。

## Engineering Notes

- 负反馈不能直接当“模型错”。需要看 trace 和业务标准。
- 恶意输入、提示注入和越权请求不能作为“用户想要的偏好”训练进去。
- 训练数据要和 eval 数据分开，避免污染评测。
- 很多问题不需要训练：知识更新用 RAG，权限问题用策略，流程问题用 workflow。
- 训练是高成本低可逆动作，应该在有足够样例和明确收益时再做。

## Verify
检查训练数据来源是否有授权、脱敏、标注质量和采样标准记录。

还应检查：

- 反馈是否先进入错误分类和 eval，而不是直接进训练集。
- 训练集是否排除了敏感信息和攻击样例。
- 微调前后是否在独立评测集上验证收益和副作用。
- 是否记录数据版本、模型版本和回滚方案。
