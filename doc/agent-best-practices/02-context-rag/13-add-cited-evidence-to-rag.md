# 13. RAG 优化要可观测

[返回全局摘要](../README.md) · [返回本组：上下文工程与 RAG](README.md)

## Rule
不要用“整体满意度”笼统评价 RAG。RAG 优化必须围绕可观测指标展开：检索是否找到了答案、生成是否忠实于证据、用户是否首轮解决、每一步证据和置信度是否可追踪。

## Why
RAG 准确率从 60% 提到 85%，通常不是靠换一个更大的模型，而是靠链路级工程优化。

一个 RAG 请求至少包含这些环节：

```text
文档解析 -> chunk 切分 -> query 改写 -> 多路召回 -> 重排 -> 上下文组装 -> 生成 -> 评估反馈
```

如果只看最终满意度，就无法判断失败来自哪里：

- 资料根本没被召回，是检索问题。
- 资料被召回了但排在后面，是排序问题。
- 资料进了上下文但模型胡编，是生成忠实度问题。
- 答案正确但用户还要追问，是业务流程或交互问题。

RAG 优化的第一原则是：先让链路可观测，再把失败拆开，最后决定优化哪一层。

## Key Metrics

| 指标 | 检测什么 | 说明什么 |
| --- | --- | --- |
| Context Recall | 正确答案是否出现在召回 chunk 里 | 召回率低时，优先查切分、query、索引和召回策略 |
| Faithfulness | 最终回答是否被上下文证据支持 | 忠实度低时，说明模型在忽略证据或产生幻觉 |
| 首轮解决率 | 用户第一轮是否得到可用答案 | 首轮低时，可能是召回、生成、澄清或产品流程共同问题 |
| Citation Accuracy | 引用是否真实支持答案 | 引用错位时，说明证据绑定和上下文选择有问题 |
| Latency / Cost | 召回、rerank、生成各段耗时和成本 | 优化不能只看准确率，还要看线上吞吐和成本 |

推荐日志至少保存：

- 原始 query。
- 改写后的 query。
- 命中的 top-k chunk 及其稳定 `chunk_id`。
- rerank 前后排序。
- 注入模型的最终上下文。
- 最终答案。
- 答案引用的 `chunk_id` 和证据片段。
- 检索置信度、生成忠实度、最终答案可信度。
- 用户反馈和人工标注。

没有这些指标和 trace，RAG 优化只能靠感觉；有了可观测性，才能判断下一步该优化切分、query、召回、排序、生成，还是产品流程。

## Optimize

### 1. 用动态切分和适当重合替代暴力切分

固定 token 切分是 RAG 早期最常见的错误。比如每 500 token 切一刀，看起来简单，但可能把关键句、表格、标题和上下文关系切断。

更稳的做法：

- 先按文档结构解析：标题、段落、列表、表格、代码块。
- 再按语义边界切分：句子边界、主题边界、问答对边界。
- 语义边界可以用传统 NLP 方法识别，例如分句、段落解析、标题层级、表格解析；也可以用小模型判断主题是否切换、问答是否完整、当前片段是否需要和前后文合并。
- 对相邻 chunk 保留适当 overlap，例如 100-200 token，避免答案线索被切在两个片段之间。
- 给每个 chunk 生成稳定 `chunk_id`。
- 保留 chunk 的元数据：标题层级、章节、来源、页码、更新时间、版本号、权限范围。

这样做解决的是 Context Recall。答案原本在文档里，但因为切分把语义破坏了，检索阶段就找不到正确片段。动态切分负责保证边界合理，overlap 负责保证上下文连续；二者配合，才能让召回材料既不碎裂，也不丢失关键前后文。

`chunk_id` 不只是技术字段，它是 RAG 可检测性的基础：

- 生成答案时可以要求模型引用具体 `chunk_id`。
- 人工审核可以标注某个问题应该命中哪些 `chunk_id`。
- 回归测试可以比较改版前后命中的 chunk 是否变化。
- 线上反馈可以追踪“哪个 chunk 经常导致错误回答”。
- 文档更新后可以判断旧引用是否失效。

没有稳定 chunk ID，RAG 系统只能看“回答大概对不对”；有了 chunk ID，才能定位“哪个证据被召回、被使用、被误用或被遗漏”。

### 2. Query 改写后必须做语义校验和噪声处理

真实用户经常输入很短的问题：

```text
怎么退款？
保修多久？
能报销吗？
```

短 query 信息量不足，可以用小模型做 query rewrite，把它扩写成更完整的检索表达，或生成多个变体做多路检索。

但 query rewrite 会引入新风险：模型可能把问题改歪。比如把“怎么退款”改成“怎么赚钱”，召回方向就完全错了。

所以改写后要做语义校验：

```text
original_query -> rewrite_model -> rewritten_query
original_query + rewritten_query -> embedding similarity check
similarity < threshold -> discard rewritten_query
```

工程上可以设置一个阈值，例如 0.8。低于阈值说明改写偏离原意，应丢弃或回退到原 query。

这一步解决的是噪声引入。Query 扩写不是越多越好，只有语义一致、没有引入额外意图的扩写才应该进入召回。

常见噪声包括：

- 意图漂移：把“怎么退款”改成“怎么赚钱”。
- 范围扩大：用户只问某个产品，改写后变成全站政策。
- 条件丢失：原 query 里有地区、版本、时间、身份限制，改写后被删掉。
- 重复变体：生成了多个表达不同但语义高度重复的 query，浪费召回和 rerank 成本。
- 伪关键词：小模型补了用户没有表达过的业务词，导致召回跑偏。

噪声处理可以放在改写后、召回前：

```text
原始 query
  -> 小模型扩写
  -> 语义一致度校验
  -> 去重、去漂移、保留关键约束
  -> 合格 query 进入多路召回
```

### 3. 用混合检索补齐召回短板

单一路径检索很容易有盲区。向量检索、关键词检索、FAQ 索引和结构化数据库解决的问题不同，不应该互相替代。

| 召回路径 | 擅长解决 | 典型风险 |
| --- | --- | --- |
| 向量检索 | 同义表达、语义相近问题 | 漏掉编号、错误码、专有名词 |
| BM25 / 关键词 | 精确词、字段名、人名、型号、错误码 | 不理解改写和语义近似 |
| FAQ / 手册索引 | 高频标准问题和权威答案 | 覆盖范围有限，容易过期 |
| 结构化数据库 | 订单状态、库存、价格、权限等确定性字段 | 需要明确字段和查询条件 |

所以混合检索的第一步不是“统一成一种检索”，而是让不同召回路径各自把候选找出来：

```text
query
  -> 向量召回候选
  -> BM25 召回候选
  -> FAQ / 手册索引召回候选
  -> 结构化数据库查询候选
  -> 合并去重
  -> 统一排序
```

第二步才是融合。这里容易犯的错是直接把分数相加：向量分通常在 0-1，BM25 分可能是 10 或 20，FAQ 命中又可能是布尔值，直接相加会让高量纲分数淹没其他信号。

更稳的融合方式是：

- 先对多路候选做去重和权限过滤。
- 把向量分、BM25 分、FAQ 命中、标题匹配、文档权威度、时间新鲜度、用户点击反馈等保留下来作为排序特征。
- 用 LambdaMART 做统一排序，把不同召回路径的分数和业务特征统一交给排序模型处理；在数据不足时，可以先用规则或通用 reranker 过渡。
- 把最终进入上下文的 chunk 及其排序原因写入 trace。

这里的关键不是把所有资料强行放进同一个向量空间，而是把不同来源的候选放进同一个 LambdaMART / Learning-to-Rank 排序框架。向量空间负责语义相似，关键词负责精确匹配，业务索引和数据库负责确定性事实，排序层负责决定哪些证据最值得进入上下文。

### 4. Rerank 要做策略路由

Rerank 能提高相关性，但会增加延迟和成本。如果所有请求都走重排序，高并发下系统会被拖慢。

可以做策略路由：

| 请求类型 | 路由策略 |
| --- | --- |
| 简单事实问答 | 向量/BM25 召回后直接取 top-k |
| 中等复杂问题 | 多路召回后轻量 rerank |
| 多跳、长文、合规、高价值问题 | 召回更多候选，再用强 reranker 精排 |
| 低置信结果 | 触发澄清、扩大检索或人工转交 |

策略路由解决的是成本和准确率的平衡。不是每个问题都值得花 200ms 做重排，也不是每个问题都能只靠向量 top-3。

### 5. 增加可信度度量

RAG 的答案不应该只有文本，还应该带可信度信号。可信度不是让模型自己说“我很确定”，而是由检索、证据和生成过程共同计算。

可以拆成三层：

| 可信度 | 来源 | 低分时的处理 |
| --- | --- | --- |
| 检索可信度 | top-k 分数、rerank 分数、命中文档权威度、chunk 新鲜度 | 扩大检索、改写 query、触发澄清 |
| 证据可信度 | 引用 chunk 是否覆盖答案关键结论，证据是否来自权威来源 | 要求补引用、降级为“不确定”、人工复核 |
| 生成可信度 | 回答是否逐条被引用支持，是否出现无证据扩展 | 删除无证据内容、重新生成、拒答 |

工程上可以输出一个结构化结果：

```json
{
  "answer": "退款通常需要在订单页提交申请，具体到账时间以支付渠道为准。",
  "citations": ["refund-policy:v3:chunk_0182", "refund-faq:v7:chunk_0041"],
  "context_recall": 0.92,
  "faithfulness": 0.88,
  "answer_confidence": "medium",
  "needs_human_review": false
}
```

可信度的作用不是装饰 UI，而是驱动策略：

- 高可信：直接回答。
- 中可信：回答时带来源和限制条件。
- 低可信：先澄清、扩大检索或回答“不确定”。
- 高风险低可信：进入人工审核。

## Verify

上线前准备一组带标注的 RAG eval：

- 每个问题标注应该命中的文档或 chunk。
- 标注应该命中的 `chunk_id`。
- 标注答案是否需要多跳推理。
- 标注是否允许模型回答“不知道”。
- 标注标准答案和必要引用。

每次改动切分、索引、embedding、rewrite、rerank、prompt 或模型版本，都跑回归。验证不要只看总分，要把指标异常映射到工程动作：

| 指标异常 | 说明什么 | 优先检查 | 处理方式 |
| --- | --- | --- | --- |
| Context Recall 低 | 正确证据没有被召回 | chunk 切分、overlap、query rewrite、索引、召回 top-k | 调整动态切分和重合区，修正 query 改写，增加混合召回路径 |
| Recall 高但 Faithfulness 低 | 证据进了上下文，但答案没有忠实使用 | prompt、引用约束、上下文压缩、生成模型 | 强制引用 `chunk_id`，删除无证据内容，必要时重新生成或拒答 |
| Citation Accuracy 低 | 引用存在但不能支持结论 | 引用绑定、chunk 粒度、上下文排序 | 要求结论逐条绑定证据，修正 chunk ID 和证据片段 |
| 首轮解决率低 | 答案可能正确但没有解决用户任务 | 答案结构、澄清策略、业务动作闭环 | 补充下一步动作，触发澄清，接入工具或工单流程 |
| 低可信答案直接输出 | 风险控制没有生效 | 可信度阈值、人工审核、拒答策略 | 按风险等级降级为澄清、不确定或人工复核 |
| P95 延迟或成本高 | 质量提升不可线上承受 | top-k、rerank 路由、缓存、模型调用链 | 给复杂问题才启用强 reranker，减少候选数，增加缓存 |
| 总分提升但长尾失败增加 | 优化只覆盖了主流样本 | 边界样例、权限样例、攻击样例 | 扩充 eval，按问题类型分桶看指标 |

这张表的作用是把评测结果变成工程决策。不要把所有失败都归结为“模型不行”；RAG 里大多数问题都能定位到具体链路层。

## Example

一个“怎么退款？”的请求可以这样处理：

```text
1. 原始 query: 怎么退款？
2. Query rewrite: 用户如何申请退款？退款流程、条件和到账时间是什么？
3. 语义校验: rewrite 与原 query embedding similarity = 0.86，通过。
4. 多路召回:
   - 向量召回退款流程相关段落
   - BM25 召回包含“退款”“到账”“申请”的政策条款
   - FAQ 召回退款常见问题
5. Rerank:
   - 综合语义分、关键词分、文档权威度和更新时间排序
6. 生成:
   - 只基于 top evidence 回答，并附 chunk_id 引用
7. 评估:
   - Context Recall: 正确政策是否被召回
   - Faithfulness: 回答是否忠实于政策
   - 首轮解决率: 用户是否还需要继续追问
   - Confidence: 是否达到直接回答阈值
```
