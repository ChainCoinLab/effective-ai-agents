# 检索为空策略

[返回全局摘要](../README.md) · [返回本组：上下文工程与 RAG](README.md)

## Rule
定义检索为空或低置信度时的固定处理方式。

## Why
没有空检索策略时，模型容易用常识或猜测填补知识库缺口，造成不可追溯答案。

RAG 系统的一个基本原则是：没有证据，不要假装有证据。检索为空不一定代表答案不存在，也可能是 query 表达不清、索引没覆盖、权限过滤过严、chunk 切分失败或文档过期。但无论原因是什么，模型都不应该把训练记忆或常识包装成知识库答案。

空检索要区分几种状态：

| 状态 | 含义 | 处理 |
| --- | --- | --- |
| `no_result` | 没有命中任何候选 | 改写查询、扩大范围或说明未找到 |
| `low_confidence` | 有候选但分数低 | 要求澄清或只给低置信建议 |
| `permission_filtered` | 有资料但当前用户无权访问 | 不泄露资料存在性，提示权限不足 |
| `conflicting_evidence` | 命中资料互相冲突 | 展示冲突来源并转人工或请求确认 |
| `stale_evidence` | 资料过期或版本不明 | 提示需要刷新或查实时系统 |

## Optimize
- 设置最低召回阈值和低置信度判断。
- 返回“未找到足够证据”而不是编造答案。
- 提供改写查询、扩大范围或转人工的路径。

空检索策略可以写成固定流程：

```text
检索为空或低置信
-> 检查是否 query 太短或有歧义
-> 尝试安全的 query rewrite
-> 扩大检索范围或切换召回通道
-> 仍无证据时返回 insufficient_evidence
-> 给出用户可执行下一步
```

返回给模型和用户的内容要分开。给模型的 observation 应结构化：

```json
{
  "status": "insufficient_evidence",
  "retrieval": {
    "query": "退款",
    "top_k": 5,
    "max_score": 0.31,
    "threshold": 0.65
  },
  "allowed_next_actions": ["ask_clarifying_question", "broaden_search", "escalate_to_human"]
}
```

给用户的表达可以更自然：

```text
我没有在当前知识库中找到足够可靠的退款政策证据。请补充产品类型或订单地区，或让我转人工确认。
```

## Engineering Notes

- 不要把“检索为空”交给模型自由发挥。空结果本身就是一个工具结果，应该进入 trace。
- 阈值要按任务调。高风险任务宁可拒答，低风险探索任务可以给出不确定建议。
- 权限过滤后的空结果要谨慎表达，避免泄露用户无权访问的资源名称。
- 低置信不等于不能回答，但必须把不确定性暴露出来，并禁止给出强结论。
- 空检索样例应进入 eval，否则系统会在知识缺口处持续幻觉。

## Verify
- 使用知识库不存在的问题测试。
- 检查模型是否明确说明无证据。
- 监控空检索后的用户追问和人工升级率。
- 测试 query 改写、扩大范围和转人工是否按策略触发。
- 检查低置信结果是否不会被模型包装成确定答案。
- 对权限过滤导致的空结果做安全测试，确认不会泄露受限文档。
