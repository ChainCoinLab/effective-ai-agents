# 检索 chunk 和生成 chunk 可以不同

[返回全局摘要](../README.md) · [返回本组：上下文工程与 RAG](README.md)

## Rule
允许使用较小 chunk 做检索，再扩展为更完整的上下文给生成模型。

## Why
小 chunk 有利于精准召回，但生成答案常需要前后文、定义、表格说明或完整流程。

检索和生成的目标不同。检索阶段要快速定位“可能相关的位置”，因此更喜欢小而清楚的索引单元；生成阶段要形成完整、准确、可解释的答案，常常需要命中片段周围的定义、限制、例外、示例或上级标题。

如果两阶段共用同一 chunk，容易出现两种问题：

| 做法 | 问题 |
| --- | --- |
| 用很小 chunk 同时检索和生成 | 命中了关键句，但模型看不到条件、例外和上下文 |
| 用很大 chunk 同时检索和生成 | 检索不够精准，命中后带入大量无关内容 |

更合理的方式是“精细检索，按需扩展”。

## Optimize
- 检索阶段使用精细粒度索引。
- 生成阶段按命中位置扩展相邻段落或父级章节。
- 保留命中片段和扩展片段的对应关系。

常见实现流程：

```text
用户问题
-> 小 chunk 检索 top-k
-> rerank 选出高置信命中
-> 根据 chunk 元数据扩展上下文
-> 去重、权限过滤、token 预算裁剪
-> 注入生成模型
```

扩展策略可以按文档类型设计：

| 命中对象 | 扩展方式 |
| --- | --- |
| 段落 | 加入前后相邻段落和所在标题 |
| FAQ 答案 | 加入问题、答案、适用范围和更新时间 |
| 表格单元格 | 加入表头、单位、行名和表格说明 |
| 代码函数 | 加入函数签名、注释、相关 import 和调用关系 |
| 政策条款 | 加入定义、例外、适用范围和生效时间 |

扩展后要保留映射：

```json
{
  "matched_chunk_id": "refund_policy_v3_p2",
  "expanded_context_ids": [
    "refund_policy_v3_title",
    "refund_policy_v3_p1",
    "refund_policy_v3_p2",
    "refund_policy_v3_p3"
  ],
  "expansion_reason": "include_parent_heading_and_adjacent_exception"
}
```

这个映射对调试很重要。没有它，后续只知道模型看到了某段上下文，却不知道最初是哪个命中触发了扩展。

## Engineering Notes

- 扩展不是把整篇文档塞进去。扩展仍然要受相关性、权限和 token 预算约束。
- 扩展前后都要去重。同一父章节可能由多个命中 chunk 触发，不能重复注入。
- 扩展内容要标记“命中片段”和“补充上下文”，否则引用时可能把补充背景误当直接证据。
- 如果扩展后上下文冲突，要保留来源、时间和版本，让 verifier 或业务规则决定可信度。
- 对多跳问题，可以先扩展，再做第二轮检索或结构化查询，但要限制轮次和成本。

## Verify
- 检查扩展后上下文是否仍与问题相关。
- 评估小 chunk 检索和扩展上下文生成的组合效果。
- 监控扩展带来的 token 成本。
- 抽查引用是否来自直接命中证据，而不是仅来自弱相关扩展内容。
- 测试表格、代码、政策条款等特殊文档是否能保留必要上下文。
- 检查扩展策略变更后，最终答案质量和成本是否都有记录。
