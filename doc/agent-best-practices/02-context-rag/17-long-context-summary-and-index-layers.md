# 长上下文摘要层、索引层和缓存友好布局

[返回全局摘要](../README.md) · [返回本组：上下文工程与 RAG](README.md)


## Rule
长上下文系统应建立原文、摘要和索引层，按任务逐层定位信息；对长对话 Agent，还应按缓存友好的顺序组织上下文，保持稳定前缀不变。

## Why
直接在长文中检索容易慢、贵且不稳定。分层结构能先定位主题，再回到原文取证。

长对话 Agent 还有一个额外问题：每轮请求都会带上系统指令、工具定义、项目上下文、历史消息和新输入。如果这些内容每轮都重新计算，成本和首 token 延迟会迅速上升。Prompt Cache 通常依赖前缀匹配，稳定前缀被时间、工具顺序、模型切换或系统提示词改动破坏后，后续缓存会失效。

因此，长上下文设计不只是“怎么塞得下”，还包括“怎么让稳定内容持续复用”。

## Optimize
- 为文档生成章节级摘要和实体索引。
- 使用摘要层做粗筛，原文层做证据确认。
- 保持摘要到原文位置的可追溯链接。
- 按稳定性组织长对话上下文：静态系统提示词和工具定义放最前，项目文档放其次，会话上下文再往后，逐轮增长的聊天消息放最后。
- 不要把当前时间、随机 ID、临时文件状态写进静态系统提示词；这类动态信息应通过下一轮消息、工具结果或 system reminder 注入。
- 不要在主会话中途切换模型或增删工具。需要小模型处理局部任务时，用子任务或 handoff；需要表达规划/执行模式时，用消息或工具表示状态转换。
- 工具很多时使用延迟加载：前缀中保留稳定、轻量、顺序固定的工具占位符，需要具体工具时再加载完整 schema。
- 上下文压缩应做缓存安全分岔：压缩请求复用主对话相同的系统提示词、上下文、工具定义和历史消息，只在末尾追加压缩指令。
- 为长会话预留压缩缓冲区，不要等上下文窗口完全填满才开始摘要压缩。

## Flow

```text
长对话请求
  |
  v
[稳定前缀: 尽量不变]
  1. 系统提示词
  2. 工具定义 / 工具占位符
  3. 项目文档 / CLAUDE.md
  |
  v
[会话层: 本轮会话内相对稳定]
  4. 会话摘要
  5. 关键索引
  6. 已确认事实
  |
  v
[动态消息: 允许变化]
  7. 用户最新输入
  8. 工具结果
  9. 时间、状态、模式提醒
  |
  v
模型响应

上下文快满时:
主对话相同前缀 + 历史消息 + 末尾追加“请压缩摘要”
  -> 生成会话摘要
  -> 替换旧历史，继续后续对话
```

## Verify
- 检查摘要结论是否能回溯到原文。
- 测试跨章节问题是否能定位正确原文。
- 监控分层检索的延迟和召回率。
- 回放连续多轮长会话，检查系统提示词、工具定义、工具顺序和项目文档是否保持稳定。
- 对比上下文压缩前后的答案质量、输入 token 成本、首 token 延迟和缓存命中率。
- 测试动态信息是否通过消息或工具结果进入上下文，而不是修改稳定前缀。
- 检查摘要、压缩、子任务和 handoff 是否共享主会话前缀，避免另起一套系统提示词和工具定义。
