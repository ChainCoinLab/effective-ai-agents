# 上下文去重压缩

[返回全局摘要](../README.md) · [返回本组：上下文工程与 RAG](README.md)

## Rule
在送入模型前去除重复、冲突和低价值上下文，并保留必要信息。

## Why
重复内容浪费 token，冲突内容会增加模型选择错误证据的概率。

去重和压缩的目标不是让文本更短，而是在有限上下文预算里保留对当前任务最有用、最可信、最可追溯的信息。尤其在长对话、RAG、多工具和多 Agent 系统中，同一事实可能来自历史摘要、检索文档、工具结果和用户补充。如果不处理，模型会看到大量重复甚至冲突的材料。

需要区分三类问题：

| 问题 | 例子 | 处理 |
| --- | --- | --- |
| 完全重复 | 同一 chunk 被多路召回重复命中 | 合并，保留一次 |
| 近重复 | 多篇文档表达同一政策 | 合并摘要，保留来源列表 |
| 冲突 | 旧政策说 7 天，新政策说 30 天 | 不简单合并，保留版本、时间和来源 |

## Optimize
- 合并重复文档和近重复段落。
- 对长文档提取与任务相关的事实。
- 对冲突信息保留来源、时间和版本。

压缩可以按信息类型分层：

| 信息类型 | 压缩方式 |
| --- | --- |
| 最近用户目标 | 不压缩或只做结构化提取 |
| 工具结果 | 保留状态、关键字段、错误类型和 artifact 引用 |
| 检索证据 | 保留直接相关句子、标题、来源和 chunk_id |
| 历史对话 | 压成目标、约束、决策、开放问题 |
| 长文档 | 先章节摘要，再按需回原文取证 |
| 冲突资料 | 不压成单一结论，保留对照表 |

一个压缩后的上下文片段应保留可追溯性：

```json
{
  "summary": "退款政策在 v3 中规定普通商品可在 30 天内申请退款。",
  "source_refs": ["refund_policy_v3_sec_2_1"],
  "dropped_refs": ["refund_policy_v2_sec_2_1"],
  "compression_reason": "v3 is newer than v2",
  "risk": "policy_version_conflict_resolved_by_newer_version"
}
```

不要把冲突直接压成“最终真相”，除非有明确规则能决定可信来源。例如按最新版本、最高权限来源、用户当前地区、产品线或人工确认结果裁决。没有裁决规则时，应把冲突显式交给模型、verifier 或人工处理。

## Engineering Notes

- 摘要会丢信息。高风险结论必须能回到原文或工具结果，不要只引用摘要。
- 压缩前要先做权限过滤，避免把用户无权访问的资料混进摘要。
- 去重不能只看文本相似度，还要看版本、地区、产品和适用范围。
- 对工具错误日志要压缩为结构化 observation，不要把完整堆栈长期塞进上下文。
- 被删除或合并的内容要记录在 trace 中，否则失败复盘时无法解释为什么证据缺失。

## Verify
- 对比压缩前后的答案质量和 token 成本。
- 检查压缩是否丢失关键事实。
- 记录被删除或合并的上下文来源。
- 针对冲突资料测试系统是否保留来源、时间和版本，而不是盲目合并。
- 检查摘要结论是否能回溯到原始 artifact。
- 测试权限过滤后压缩，确认摘要没有泄露受限内容。
