# 上下文不是越多越好

[返回全局摘要](../README.md) · [返回本组：上下文工程与 RAG](README.md)

## Rule
只放入完成当前任务所需的上下文，避免把大量低相关内容塞给模型。Skill、工具说明和 few-shot 示例也属于上下文，不应默认全量注入。

## Why
过多上下文会稀释关键信息，增加成本、延迟和错误引用概率。

当系统有很多 Skill 时，全量注入 Skill 说明会出现和长文档一样的问题。大规模实现见 [大量 Skill 共存解决方案](../04-tools-agents/large-scale-skill-engineering.md)。

模型并不是阅读器越满越好。上下文窗口里的每个 token 都会消耗预算，也会参与注意力分配。低相关材料越多，关键事实越容易被埋在中间；相似但不一致的材料越多，模型越容易选错依据；无关工具和 Skill 越多，模型越容易误选能力。

“多放一点以防万一”在 Agent 系统里会带来四类成本：

| 成本 | 表现 |
| --- | --- |
| 质量成本 | 关键信息被稀释，回答引用低相关证据 |
| 延迟成本 | 输入 token 增加，首 token 延迟和总耗时上升 |
| 经济成本 | 每轮请求携带大量重复内容，成本随轮次增长 |
| 安全成本 | 更多外部内容进入模型，提示注入和敏感信息泄露面扩大 |

## Optimize
- 按任务目标筛选上下文。
- 为每段上下文保留来源和相关性理由。
- 设置最大 token、最大文档数和最低相关度阈值。
- 对 Skill、工具说明和示例设置注入预算，只放入与当前任务相关的片段。

上下文筛选应围绕“当前决策”而不是“当前会话全部历史”。例如代码审查任务当前只需要某个文件和相关测试，就不要把整个仓库说明、所有历史对话和所有工具说明都塞进去。

推荐给上下文建立优先级：

| 优先级 | 内容 | 处理方式 |
| --- | --- | --- |
| P0 | 系统规则、权限边界、用户最新目标 | 必须保留，不应被裁剪 |
| P1 | 当前任务状态、成功标准、已确认事实 | 高优先保留 |
| P2 | 与问题直接相关的证据和工具结果 | 按相关性和可信度筛选 |
| P3 | 历史摘要、长期记忆、相邻上下文 | 按需注入 |
| P4 | 背景资料、低相关示例、完整 Skill 说明 | 默认不注入或延迟加载 |

Context Builder 应做预算分配，而不是最后简单截断：

```text
总预算 = 模型上下文上限 - 输出预留 - 安全余量
稳定规则预算
任务状态预算
证据预算
历史摘要预算
工具/Skill 预算
```

超过预算时，应该先删除低相关、重复和可回查内容，而不是裁掉最新用户输入、成功标准或权限规则。对于长文档，应保留引用和摘要，同时把原文放在 artifact 或检索层，需要时再取。

## Engineering Notes

- 上下文不是存储层。完整历史、原始文件和工具结果应该保存在 trace、数据库或 artifact 中。
- 大上下文模型不能替代筛选。窗口变大只延后问题，不解决噪声、冲突、成本和安全。
- 工具 schema、Skill 文档、few-shot 示例也会占上下文预算，应按任务动态加载。
- 对同一资料多次注入时要去重，并记录来源，避免模型把重复出现误判为高置信事实。
- 动态内容不要破坏稳定前缀，否则缓存命中率和延迟会明显变差。

## Verify
- 比较不同上下文规模下的准确率和延迟。
- 检查错误答案是否来自低相关上下文。
- 监控上下文命中率和使用率。
- 对比全量上下文和按需上下文的 token 成本、延迟和错误率。
- 抽样检查最终答案引用的证据是否来自 P1/P2 高相关材料。
- 构造包含大量无关资料的测试集，确认系统不会被噪声带偏。
- 检查 token 超预算时被裁剪的是否是低优先级内容。
