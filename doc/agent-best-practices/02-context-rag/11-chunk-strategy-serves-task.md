# chunk 策略服务任务

[返回全局摘要](../README.md) · [返回本组：上下文工程与 RAG](README.md)

## Rule
chunk 大小、边界和元数据应服务具体任务，而不是使用固定默认值。

## Why
不同任务需要不同粒度。问答需要可定位证据，摘要需要完整段落，流程任务需要保留步骤顺序。

Chunk 不是单纯的技术切片，它决定检索系统“看见”的知识单位。如果把一个完整流程切断，模型会漏步骤；如果把多个主题塞在同一个 chunk 里，检索命中后会带入噪声；如果没有元数据，答案就无法解释来源、版本和权限。

常见固定切分方式是“每 500 token 切一刀”。这种方式实现简单，但对很多业务文档并不可靠：

| 文档类型 | 错误切分风险 | 更合适的边界 |
| --- | --- | --- |
| FAQ | 问题和答案分离 | 一组问答作为一个 chunk |
| 操作手册 | 步骤被拆散 | 一个流程段或子步骤组 |
| 合同/政策 | 条款上下文丢失 | 条款、章节、定义和例外一起保留 |
| 表格 | 表头和行分离 | 表头、单位、行记录和说明绑定 |
| 代码 | 函数或类被切断 | 函数、类、文件结构和 import 关系 |

## Optimize
- 按标题、段落、表格、代码块或业务对象切分。
- 保留文档层级、时间、版本和权限元数据。
- 避免把一个完整语义单元切断。

设计 chunk 策略时先回答任务问题：

| 任务 | 推荐粒度 | 关键元数据 |
| --- | --- | --- |
| 精确问答 | 小到中等 chunk，保留直接证据 | `chunk_id`、标题、页码、更新时间 |
| 长文摘要 | 章节级 chunk，加摘要层 | 章节层级、父子关系、原文位置 |
| 合规审查 | 条款级 chunk，保留例外和定义 | 生效时间、版本、适用范围、权限 |
| 客服知识库 | 问答对或问题簇 | 产品、地区、用户类型、有效期 |
| 代码问答 | 函数/类/文件段落 | 文件路径、行号、语言、符号名 |

每个 chunk 至少要有：

```json
{
  "chunk_id": "policy_refund_v3_sec_2_1",
  "source_id": "refund-policy-v3",
  "title_path": ["退款政策", "特殊商品", "不可退款条件"],
  "content": "...",
  "created_at": "2026-05-01",
  "updated_at": "2026-05-12",
  "version": "v3",
  "permission_scope": "support_internal",
  "parent_id": "policy_refund_v3_sec_2"
}
```

`chunk_id` 要稳定。文档重建索引后，如果同一段内容的 ID 大量变化，历史引用、人工标注、回归样例和线上反馈都会失去定位能力。

## Engineering Notes

- chunk 太小会提高召回精度，但可能丢上下文；chunk 太大会保留上下文，但降低检索精度并增加 token 成本。
- overlap 不是越大越好。过大 overlap 会造成重复证据和成本浪费，应根据句子、段落或业务对象边界设置。
- 表格、代码、图片 OCR、PDF 页眉页脚需要专门解析，不要和普通段落一刀切。
- 权限元数据必须在索引阶段保留，不能等生成阶段再靠模型判断用户能不能看。
- chunk 策略变更会影响所有检索结果，应视为系统行为变更并跑回归。

## Verify
- 抽样检查 chunk 是否语义完整。
- 用目标任务查询测试召回效果。
- 统计答案所需信息是否跨越过多 chunk。
- 检查 chunk 是否保留来源、版本、时间和权限字段。
- 用标准查询确认正确 chunk 能进入 top-k，且相邻扩展不会带入大量无关内容。
- 对索引重建前后的 `chunk_id` 稳定性做检查。
