# 09. 语言模型为什么预测下一个 token

[返回本章](README.md)

![大模型 next-token 预测循环](../assets/diagrams/next-token-loop.svg)

图解导读：next-token prediction 依赖 token 表示、概率分布和逐步推理；这些图把输入、能力来源和推理阶段连起来。

## 核心问题

为什么大模型的核心任务是 next-token prediction？

上一节已经把文字拆成了 token，并把 token 变成了 embedding。现在问题变成：有了一串可以计算的 token 向量以后，模型到底要学什么？

现代语言模型选择了一个看起来很小、但覆盖面极大的任务：

> 给定前面的 token，预测下一个 token 的概率分布。

这不是因为研究者只关心“续写”，而是因为语言本身天然就是按顺序展开的。一个词、一个字、一个标点是否合理，几乎总要依赖它前面的上下文。把语言建模成“下一个 token 的条件概率”，就把模糊的语言理解问题变成了一个可以训练、可以计算、可以优化的机器学习问题。

## 推导线索

```text
语言天然是序列
→ 当前 token 和前面的上下文有关
→ 可以把语言建模成条件概率
→ P(下一个 token | 前面的 tokens)
→ 模型输出的是所有候选 token 的概率分布
→ 生成就是不断选择 token 并接回上下文
```

## 本节目标

- 语言模型是什么
- 条件概率是什么
- logits 和 probability 是什么
- 为什么输出是概率分布
- 为什么生成是一个循环过程
- 为什么采样会带来随机性，贪心解码会带来确定性倾向
- 为什么语言模型不是查数据库

第一次读，本节先带走三件事：

- 语言模型每一步输出的是“下一个 token 的概率分布”，不是直接输出真理。
- logits 只是原始分数，softmax 把它们变成可比较的概率。
- 生成完整答案是逐 token 自回归循环，所以早期错误、采样参数和停止条件都会影响结果。

## 1. 从哪里来：语言为什么适合被看成序列概率

### 直觉层

人读一句话时，经常能猜到后面会出现什么。

例如：

```text
我今天早上喝了一杯热腾腾的 ____
```

常见续写可能是：

```text
咖啡
牛奶
豆浆
茶
```

但不太可能是：

```text
操作系统
平方根
红绿灯
```

不是因为我们查了一个数据库，而是因为前文给出了很多限制：

- “喝了一杯”暗示后面大概率是饮品。
- “热腾腾的”暗示它有温度和日常生活属性。
- “早上”让咖啡、牛奶、豆浆这类词更常见。

语言理解的一个重要部分，就是根据上下文缩小“下一步合理表达”的范围。

### 机制层

如果把一句话拆成 token：

```text
x1, x2, x3, ..., xt
```

那么第 `t+1` 个 token 通常不是独立出现的，而是依赖前面的 token：

```text
x(t+1) 依赖 x1...xt
```

这就是语言模型的基本入口：模型不直接预测整篇文章，而是在每一个位置上学习“前文给定时，下一个 token 更可能是什么”。

这种建模方式有三个好处：

- 训练样本天然存在：任何文本都能切成大量“前文 -> 下一个 token”的训练对。
- 目标清晰：预测错了就产生损失，预测对了就降低损失。
- 可以扩展：从短句到长文，从自然语言到代码、表格、JSON，都可以统一成 token 序列。

### 形式层

给定 token 序列：

```text
x1, x2, ..., xn
```

语言模型关心的是联合概率：

```text
P(x1, x2, ..., xn)
```

根据概率链式法则，它可以拆成一连串条件概率：

```text
P(x1, x2, ..., xn)
= P(x1) · P(x2 | x1) · P(x3 | x1, x2) · ... · P(xn | x1, ..., x(n-1))
```

所以，只要模型能学会：

```text
P(下一个 token | 前面的 tokens)
```

它就能给任何一段文本分配概率，也能从一个上下文开始逐步生成文本。

这就是 next-token prediction 的形式基础。

### 工程层

这个视角会直接影响工程判断：

- Prompt 的本质不是“给模型下命令”，而是改变条件概率里的上下文。
- 上下文越清晰，模型对下一个 token 的概率分布越集中。
- 模糊、冲突、缺少约束的 Prompt，会让多个候选答案概率接近，输出更容易漂移。
- 结构化输出不是靠“模型天生守规矩”，而是靠在上下文里持续强化格式约束，并在工程侧校验。

## 2. 语言模型是什么：从上下文到概率分布的函数

### 直觉层

可以先把语言模型想成一个“续写可能性评估器”。

输入：

```text
请把下面句子翻译成英文：我喜欢学习机器学习。
英文：
```

模型不是直接从某个表里拿出唯一答案，而是对词表里的每个候选 token 打分：

```text
I       分数很高
The     分数较低
Apple   分数很低
{       分数很低
```

然后模型把这些分数转换成概率，选择其中一个 token 作为输出。生成第一个 token 后，它再把这个 token 接回上下文，继续预测下一个 token。

### 机制层

一个语言模型可以抽象成函数：

```text
f(context_tokens) -> scores_for_next_token
```

其中 `context_tokens` 是前文 token，`scores_for_next_token` 是对整个词表的打分。

假设词表大小是 `V`，模型每一步都会输出长度为 `V` 的向量：

```text
z = [z1, z2, ..., zV]
```

这个向量里的每个元素对应一个候选 token 的原始分数。这个原始分数叫 logit。

logit 还不是概率。它可以是任意实数：

```text
咖啡: 12.4
牛奶: 10.9
平方根: -3.2
```

logit 的意义是相对偏好：数值越大，模型越倾向于把这个 token 作为下一个 token。

### 形式层

为了把 logits 转成概率分布，通常使用 softmax：

```text
P(token_i | context) = exp(z_i) / Σ_j exp(z_j)
```

其中：

- `z_i` 是第 `i` 个 token 的 logit。
- `exp(z_i)` 把分数变成正数。
- `Σ_j exp(z_j)` 是所有候选 token 的归一化总和。
- 最终所有 token 的概率相加为 `1`。

下面这个表只保留了少量候选 token，用来说明 logits 如何被 softmax 变成可比较的概率。真实模型会对整个词表做同样的归一化。

| 候选 token | 原始 logit | softmax 后概率（示意） | 在当前上下文中的含义 |
| --- | ---: | ---: | --- |
| 咖啡 | 4.2 | 0.60 | 最符合“喝了一杯热腾腾的” |
| 牛奶 | 3.1 | 0.20 | 合理但偏好较低 |
| 豆浆 | 2.7 | 0.13 | 仍是饮品候选 |
| 茶 | 1.9 | 0.06 | 合理但更弱 |
| 平方根 | -0.4 | 小于 0.01 | 语义不匹配，概率很低 |

如果不想算公式，只看趋势也可以：logit 越高，经过 `exp` 后会变成更大的正数；再除以所有候选的总和，就得到更大的概率。真实模型不是只在这 5 个词里选，而是对整个词表做同样的归一化。

这个表也说明了一个关键点：模型不是只给一个答案打分，而是在所有候选 token 之间分配概率质量。

例如模型输出：

```text
咖啡: 0.55
牛奶: 0.20
豆浆: 0.15
茶:   0.08
其他: 0.02
```

这表示模型认为在当前上下文下，“咖啡”最可能，但不是唯一可能。

训练时，真实文本里的下一个 token 会作为目标答案。模型希望把真实 token 的概率提高，把不合适 token 的概率降低。常见损失是交叉熵：

```text
loss = -log P(真实下一个 token | context)
```

如果真实 token 的概率越高，loss 越小；如果概率越低，loss 越大。

### 工程层

这解释了很多工程现象：

- 模型输出的不是“真理”，而是基于上下文的概率偏好。
- 同一个问题可能有多个合理答案，因为多个 token 序列都可能有较高概率。
- 模型越确信，概率分布通常越尖锐；模型越不确定，概率分布越分散。
- 推理参数本质上是在控制如何从概率分布里选 token，而不是改变模型已经学到的参数。

## 3. 自回归生成：为什么生成是一个循环

### 直觉层

语言模型一次只预测一个下一个 token。完整答案不是一次性吐出来的，而是像这样一步步长出来：

```text
上下文: 中国的首都是
预测: 北京

上下文: 中国的首都是 北京
预测: 。
```

写代码时也是这样：

```text
上下文: function add(a, b) {
预测: return

上下文: function add(a, b) { return
预测: a

上下文: function add(a, b) { return a
预测: +
```

### 机制层

这种“把刚生成的 token 接回输入，再继续预测”的方式叫自回归生成。

最小流程是：

```text
1. 用户输入 Prompt
2. tokenizer 把 Prompt 变成 token ids
3. 模型根据当前上下文输出 logits
4. softmax 把 logits 变成概率分布
5. 解码策略选择一个 token
6. 把这个 token 追加到上下文
7. 重复 3-6，直到遇到停止条件
```

训练时，一段文本也会被拆成大量“前文 -> 下一个 token”的监督信号。下面用词级片段做示意，真实系统会按 tokenizer 的 token 边界切分。

| 原始片段 | 给模型的前文 | 训练目标 | 模型需要学到的约束 |
| --- | --- | --- | --- |
| 我今天早上喝了一杯热腾腾的咖啡 | 我今天早上 | 喝 | 日常事件的动作搭配 |
| 我今天早上喝了一杯热腾腾的咖啡 | 我今天早上喝了一杯 | 热腾腾的 | 数量短语后接形容或名词修饰 |
| 我今天早上喝了一杯热腾腾的咖啡 | 我今天早上喝了一杯热腾腾的 | 咖啡 | 饮品、温度、早晨场景的联合约束 |
| function add(a, b) { return a + b } | function add(a, b) { | return | 代码块中常见的返回语句 |

所以 next-token prediction 不需要额外人工标注任务标签：普通文本本身就能不断产生训练样本。

停止条件可能是：

- 生成了结束 token。
- 达到 `max_tokens`。
- 遇到工程侧设置的 stop sequence。
- 流式生成被用户或系统中断。

### 形式层

自回归生成可以写成：

```text
x(t+1) ~ P(x | x1, x2, ..., xt)
```

这里的 `~` 表示从概率分布中选择或采样。

如果总是选择概率最高的 token：

```text
x(t+1) = argmax_x P(x | x1, ..., xt)
```

这叫贪心解码。它更确定，但可能变得刻板，甚至在某些任务上陷入局部最优。

如果按概率随机采样：

```text
x(t+1) 从 P(x | context) 中抽样
```

输出会更多样，但也更可能偏离严格答案。

### 工程层

自回归生成带来几个重要工程后果：

- 错误会累积：前面生成错了，后面的上下文也会被污染。
- 长输出更难稳定：每一步都有小概率偏差，步数越多，整体偏差越可能出现。
- 流式输出可行：因为模型本来就是逐 token 生成，前端可以边生成边展示。
- 延迟和成本与输出长度相关：生成越长，解码步骤越多。
- 上下文窗口是硬约束：模型只能基于当前窗口里的 token 预测，窗口外的信息不会自动存在。

如果把这个循环放到真实推理服务里看，输入 Prompt 会先进入 prefill，然后输出阶段逐 token decode。第 14 节会展开性能和参数，这里先看生成机制所在的位置。

## 4. 采样与确定性的边界

同一个 Prompt，模型有时会给出不同答案。这不是模型“情绪变了”，而是因为下一 token 的概率分布里通常有多个可选项。

例如：

```text
请给这个函数起一个变量名：用户注册时间
```

合理输出可能是：

```text
registeredAt
signupTime
createdAt
registrationTime
```

它们都不是绝对错误，只是风格和语境不同。

本节只需要抓住一件事：模型先给出概率分布，解码策略再决定从这个分布里选哪个 token。贪心解码会偏向最高概率项，采样会允许多个合理候选参与竞争。它们改变的是“选择方式”，不是模型参数本身。

到这里先不要陷入参数细节。`temperature`、`top_p`、`top_k`、`max_tokens`、`stop` 和流式输出的工程取值，会在第 14 节统一处理。第 09 节只需要知道：解码策略会影响输出稳定性、多样性和格式风险。

确定性也有边界。即使把采样调得很保守，模型仍然不是传统意义上的确定性程序：

- 底层推理服务可能有并行计算和数值差异。
- 不同模型版本的 logits 会变化。
- Prompt 中微小措辞变化会改变概率分布。
- 多轮对话中历史上下文变化会影响后续输出。

所以工程上不能把大模型当作“同输入永远同输出”的普通函数使用，而要把它当作概率组件来设计。

## 5. 为什么这不是查数据库

### 直觉层

当模型回答：

```text
法国的首都是巴黎。
```

它看起来像在数据库里查到了“法国 -> 巴黎”。但 next-token prediction 的机制不是查表，而是在当前上下文下生成高概率 token。

如果输入：

```text
法国的首都是
```

在训练数据中，“巴黎”经常与“法国首都”相关，因此模型学到的参数会让“巴黎”这个 token 序列概率很高。

这更像“从大量文本中压缩出的统计关联和语义结构”，不是一条可精确定位、可事务更新的数据库记录。

### 机制层

数据库查询通常具有这些特征：

- 有明确数据表、字段和索引。
- 查询结果来自当前存储的确定性记录。
- 数据更新后，查询结果立刻改变。
- 可以追踪记录来源和权限边界。

语言模型不同：

- 知识被压缩在参数中，不是以原始文档形式存储。
- 生成时输出的是概率最高或被采样选中的 token。
- 模型训练后，参数不会因为外部事实变化自动更新。
- 它不能天然给出可靠来源，除非上下文或工具提供了来源。

### 形式层

数据库查询可以抽象成：

```text
SELECT value FROM table WHERE key = condition
```

语言模型生成更接近：

```text
argmax 或 sample from P(next_token | context, parameters)
```

前者返回记录，后者产生概率生成结果。

这两个系统都能输出文字，但机制完全不同。

### 工程层

这个区别会影响很多架构选择：

- 需要实时事实时，不要只问模型，要接搜索、数据库或 API。
- 需要可追溯答案时，要把来源文档放进上下文，并要求引用。
- 需要权限控制时，权限必须在业务系统和工具层实现，不能交给模型“自觉遵守”。
- 需要确定性状态时，用数据库、状态机、事务和幂等逻辑，而不是让模型记住。
- 需要降低幻觉时，用检索、约束解码、校验器、评测集和人工审核，而不是只调整措辞。

这也是后面 Agent 工程的根基：模型负责语言理解和候选生成，外部系统负责事实、状态、权限和执行。

## 6. 常见误解

### 误解一：预测下一个 token 太简单，所以不可能产生智能

next-token prediction 的单步目标确实简单，但训练压力非常强。为了在海量文本中预测好下一个 token，模型必须学习语法、语义、事实关联、格式、风格和任务模式。下一节会专门解释能力为什么会从这个训练目标中涌现。

### 误解二：概率最高的 token 就一定是正确答案

概率高只表示“在模型参数和当前上下文下更可能”，不等于事实正确。错误事实、过时信息、误导性上下文都会让错误 token 获得高概率。

### 误解三：temperature 设为 0 就能保证完全可靠

低 temperature 可以减少随机性，但不能让模型拥有不存在的事实、权限、计算能力或验证能力。可靠性来自系统设计，不只来自解码参数。

### 误解四：模型是在复制训练数据

模型可能记住训练数据中的片段，但主机制不是逐条检索原文，而是用参数表示大量统计规律。它既可能生成训练数据中见过的句式，也可能组合出训练数据中没有出现过的新表达。

### 误解五：Prompt 写得好就不需要工程约束

Prompt 能改变概率分布，但不能替代 schema、数据库、权限、重试、评测和监控。越是生产系统，越要把模型输出放进可验证的工程边界里。

## 7. 连接到下一节：先解释能力来源，再追问上下文关系

现在已经知道：语言模型的训练目标是预测下一个 token。下一步先要回答一个更自然的问题：只是预测下一个 token，为什么会产生翻译、总结、写代码、遵循格式这些能力？

这张图可以先建立一个预期：能力不是独立手写模块，而是预测压力在语法、事实、格式、上下文和规模训练中逐步逼出来的。

![预测下一个 token 如何逼出能力](../assets/diagrams/prediction-capability-stack.svg)

这个问题会在下一节展开。等理解了“预测压力如何逼迫模型学习语言、知识和任务模式”之后，还会继续追问：模型要预测得好，必须知道前文里哪些信息重要，这就会引出 Attention。

例如：

```text
小李把钥匙放进抽屉，然后去了厨房。后来他回到房间，打开了 ____
```

要预测“抽屉”，模型需要把“钥匙放进抽屉”和“打开了”联系起来，而不是只看最近几个 token。

这会自然引出下一类问题：

```text
当前 token 该参考前文里的哪些 token？
远处的信息如何影响当前预测？
多个词之间的关系如何被同时建模？
```

Attention 就是为了解决“在上下文中选择相关信息”的问题。next-token prediction 定义了训练目标，Attention 提供了让模型利用上下文关系的关键机制。

## 工程小结

- 把 Prompt 当作条件概率的输入来设计：减少歧义，增加约束，给出示例。
- 把模型输出当作概率生成结果来处理：需要校验、重试和失败路径。
- 事实类任务要接外部知识源：RAG、数据库、搜索和 API。
- 结构化任务要使用 schema：JSON schema、函数调用、解析器和类型校验。
- 高风险任务要有人或规则兜底：模型不能独立承担最终责任。
- 长任务要拆解：减少长自回归链路中的错误累积。
