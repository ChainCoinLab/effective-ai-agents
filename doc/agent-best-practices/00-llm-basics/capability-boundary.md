# 00.5 大模型能力边界

[返回本章](README.md)

理解工作原理之后，必须明确一个边界：大模型很强，但它不是万能执行器。它适合承担“语言、模式、候选方案和交互式推理”这类概率任务；不适合单独承担“事实真值、权限决策、长期状态和不可逆动作”这类确定性责任。

![大模型能力边界](../assets/diagrams/llm-capability-boundary.svg)

## 1. 能力边界关键词

在讲大模型能力边界时，有几个关键词需要先明确。

### 上下文依赖

大模型的强项在推理、归纳、计划和语言生成，但这些能力建立在“足够且高质量的上下文预测”之上。它不是脱离上下文凭空稳定推理，而是在当前输入、历史消息、系统提示词、工具结果和检索材料共同构成的上下文里，计算更可能的下一步。

因此，同一个模型在上下文充分、结构清楚、证据可靠时会表现很强；在上下文缺失、噪声多、指令冲突时会明显退化。

### 上下文焦虑

上下文焦虑指的是：因为担心模型不知道，工程上把太多历史、文档、规则和工具结果都塞进上下文。

这会带来反效果：

- 成本和延迟上升。
- 关键信息被噪声稀释。
- 模型更容易引用错误片段。
- 指令、历史和文档之间更容易冲突。

上下文工程的目标不是“尽量多给”，而是“给正确、必要、排序合理、可追踪的上下文”。

### 迷失中间

迷失中间指的是：上下文很长时，模型对开头和结尾的信息通常更敏感，中间部分的关键事实可能被忽略或弱化。

这不是某个应用的偶然问题，而是长上下文使用中的常见风险。因此，重要约束不能随便埋在长文中间，应该通过摘要、索引、重复锚点、结构化字段、引用和检索排序来提高可见度。

### 能力锯齿

能力锯齿指的是：大模型能力不是平滑边界。它可能在一些看似很难的任务上表现很好，比如复杂总结、代码解释、跨文档归纳；却在某些看似简单的任务上出错，比如精确计数、日期边界、格式细节、否定条件、单位换算。

所以不能用“它能做难题”推导出“它一定能稳定做简单题”。生产系统必须用 eval、回归测试和边界样例确认具体任务的可靠性。

### 随机性

大模型输出带有随机性。即使输入相同，不同解码参数、模型版本、并发环境或底层推理实现也可能导致输出差异。

temperature、top-p、top-k 等参数会直接影响输出稳定性。高风险任务应降低随机性，并加入结构化输出、工具验证和人工确认。

### 幻觉

幻觉指的是模型生成了流畅、看似合理、但事实错误或无法验证的内容。

它的根源不是模型“故意撒谎”，而是模型参数保存的是训练中形成的模式和关联，不是可查询、可审计、可更新的事实数据库。当上下文里缺少可靠证据时，模型仍然会按语言概率补全一个合理答案。

幻觉更容易出现在这些场景：

- 问题涉及训练后发生的新信息。
- 问题涉及企业内部、私有文档、低频领域或长尾事实。
- 用户要求具体数字、论文、链接、法律条款、API 参数、版本差异。
- 上下文里混入错误材料，模型没有独立事实判断来源。
- 多个实体或概念相似，容易张冠李戴。
- 提示词暗示“必须回答”，但没有给模型拒答或澄清路径。

所以事实类任务不能只靠模型参数，必须给外部证据、引用、检索结果、数据库查询或人工审核。

### 快思考偏差

大模型经常表现得像“系统一”：很快给出直觉式答案。它擅长模式匹配、类比和常见推理，但不天然保证每一步推理都严密。

快思考偏差会导致：

- 中间步骤跳过。
- 长链推理前面对了，后面逐步偏移。
- 看似合理的方案没有验证关键约束。
- 对隐藏条件、否定条件、边界条件不敏感。

这就是为什么复杂推理、规划、数学、代码和高风险决策不能只看最终答案，还要检查中间过程、使用工具验证，并在必要时引入人工复核。

### 角色约定的概率偏置

给模型约定角色，例如“你是资深财务审核员”“你是严格的代码审查员”，并不会修改模型参数，也不会给模型真正授予权限。

但角色约定会改变本轮上下文，让相关行为模式、术语、判断标准和输出风格在概率分布中更容易被激活。换句话说，它会影响模型在当前上下文里的注意力和输出倾向。

这就是 Prompt 工程有用的原因，也是它的边界：角色能提高相关模式的权重，但不能替代事实来源、权限系统、测试和审核。

## 2. 大模型擅长什么

大模型适合处理语义空间大、答案形态灵活、需要综合上下文的任务：

- **语言理解与生成**：总结、改写、翻译、润色、问答、解释复杂概念。
- **结构化抽取**：从自然语言中抽取字段、分类意图、识别实体、生成 JSON 草案。
- **模式归纳**：从样例中总结规则，发现文本、代码、流程中的相似模式。
- **代码辅助**：阅读代码、解释错误、生成草稿、提出重构方案、补测试建议。
- **任务拆解**：把复杂目标拆成步骤，给出计划、风险点和检查清单。
- **交互式修正**：根据用户反馈不断调整答案、方案或代码。
- **工具选择建议**：判断当前任务可能需要搜索、数据库、计算器、代码执行或其他工具。

这些能力的共同点是：模型可以给出高质量候选，但候选结果仍然需要验证。

## 3. 大模型不适合单独承担什么

以下能力不能只交给模型本身：

- **实时事实判断**：模型内置知识可能过期，最新政策、价格、版本、新闻、库存、接口行为都需要外部来源。
- **权威事实确认**：法律、医疗、财务、合规、安全等高风险结论需要权威资料、专业审核或确定性规则。
- **精确计算**：复杂算术、财务计算、统计分析、日期边界和单位换算应交给计算器、代码或数据库。
- **长期记忆一致性**：模型没有真正的持续对话记忆，长期偏好、用户资料、业务状态不能只靠历史消息拼接。
- **权限和身份判断**：模型不能作为权限系统，不能凭自然语言决定用户是否有权执行动作。
- **不可逆动作决策**：删除数据、付款、发邮件、发布上线、改生产配置必须有确认、审计和回滚设计。
- **稳定执行长链路任务**：长任务容易出现目标漂移、遗漏步骤、重复工具调用和错误累积。
- **安全边界维护**：模型可能受 prompt injection、间接注入、恶意上下文和越权请求影响。

这些限制不是模型“坏”，而是概率预测机制的自然结果。模型生成的是最可能的文本或行动参数，不是天然可审计的事实系统、权限系统或事务系统。

## 4. 工程系统应该如何补位

能力边界确定之后，工程系统要承担这些责任：

- **事实交给来源**：用 RAG、搜索、数据库、API、引用和证据约束解决事实可靠性。
- **计算交给工具**：用计算器、代码执行、测试、SQL 和规则引擎处理精确结果。
- **状态交给系统**：用数据库、状态机、任务队列和工作流系统管理长期状态。
- **记忆交给存储**：用可更新、可删除、可审计的记忆系统管理长期偏好和稳定事实。
- **权限交给应用**：用账号体系、权限校验、审计日志、人工确认和风险分级控制外部副作用。
- **质量交给评测**：用 eval 数据集、回归测试、trace grading 和线上监控衡量真实表现。
- **失败交给恢复机制**：用重试、降级、回滚、checkpoint、resume 和人工转交处理异常路径。

一句话总结：模型负责生成候选，工程系统负责边界、验证、执行和恢复。

## 5. 常见问题与工程处理方式

从工作原理推导工程解法，可以得到下面这张表：

| 问题 | 原因 | 工程处理方式 | 适用场景 |
| --- | --- | --- | --- |
| 输出不稳定，同一问题有时好有时坏 | 模型微观上是概率预测，受上下文、提示和采样参数影响 | 降低 temperature，固定输出 schema，使用少量高质量 few-shot 示例，建立 eval 和回归测试 | 分类、抽取、固定格式输出、客服话术 |
| 格式漂移，输出不符合约定 | 模型生成的是概率文本，不是强类型对象 | JSON schema、函数调用、工具参数校验、解析失败重试 | 结构化抽取、API 参数生成、报表生成 |
| 编造事实、引用、数字或版本 | 参数是有损压缩，不是事实数据库 | RAG、搜索、数据库查询、引用约束、事实校验器、允许回答“不知道” | 企业知识库、政策条款、价格、版本、论文、API 文档 |
| 知识过期或缺少私有知识 | 训练数据有截止时间，模型看不到企业内部系统 | 检索最新资料，接业务数据库/API，把私有知识作为上下文或工具结果注入 | 内部制度、工单、库存、订单、线上日志 |
| 常见任务很强，低频边界任务突然失败 | 能力是锯齿状，不是平滑边界 | 用真实分布和边界样例做 eval，按任务拆分提示和流程，不用泛化印象替代验证 | 面试题、风控、合同审查、代码迁移 |
| 多步推理中间走偏 | 模型偏快思考，隐式推理不可见 | 分步推理、scratchpad、计划-执行-验证、代码执行器、单元测试、计算器 | 数学、规划、代码、复杂问答、多跳分析 |
| 长任务忘记目标或状态 | 上下文窗口有限，模型没有可靠长期状态 | 状态机、工作流、任务状态表、checkpoint、长期记忆与短期上下文分离 | Agent、长流程自动化、多轮项目任务 |
| 工具调用参数错误 | 模型输出文本，不天然理解外部系统约束 | 小而清晰的工具接口、OpenAPI/schema 描述、参数校验、错误反馈、重试和降级 | 搜索、数据库、代码执行、业务 API |
| 越权或高风险动作 | 模型不能作为权限系统，也不承担真实后果 | RBAC、最小权限、人工确认、审计日志、幂等、回滚和风险分级 | 删除、付款、发邮件、发布、改生产配置 |
| 被恶意上下文诱导 | 模型会把上下文当作输入信号，可能受注入影响 | 分隔指令和资料，做上下文注入检测，限制工具权限，引用来源可追踪 | RAG、网页浏览、邮件处理、外部文档读取 |

要特别区分三类常被混用的技术：

- **Few-shot**：解决“按什么模式回答”。它通过少量高质量示例激活目标格式、语气、分类标准或抽取方式。
- **RAG**：解决“依据什么事实回答”。它把外部知识和证据放入上下文，降低幻觉和知识过期风险。
- **CoT / 分步推理 / 验证器**：解决“怎么把思考过程展开并检查”。它适合推理、规划、数学、代码和多步骤任务。

一个简单判断：

```text
输出风格和格式不稳定 -> few-shot + schema + 低温度
事实来源不可靠 -> RAG + 数据库/API + 引用
推理过程容易跳步 -> 分步推理 + 工具验证 + 测试
执行动作有风险 -> 权限 + 审批 + 审计 + 回滚
```

## 6. 为什么这会引出工程实践

理解大模型是概率预测机器之后，后面的工程实践就不是技巧清单，而是必然要求。

### 因为输出不确定，所以需要评测

传统函数更接近：

```text
input -> deterministic output
```

大模型更接近：

```text
context -> probability distribution -> sampled output
```

因此，AI 系统不能只靠少量人工试用判断质量。它需要 eval 数据集、回归测试、失败分类和线上监控。

### 因为上下文决定输出，所以需要上下文工程

Prompt、检索结果、历史消息、工具返回、业务规则都会改变输出概率。上下文不是附属材料，而是运行时数据层。

这就是为什么要做 RAG、chunk 策略、引用约束、上下文压缩、防注入和长上下文管理。

### 因为模型会补全，所以需要退出路径

如果不给模型“信息不足时可以说不知道”的路径，它很可能继续生成一个流畅答案。

这就是为什么 Prompt 里要定义澄清、拒答、降级、人工转交和事实验证策略。

### 因为模型不负责权限，所以需要工具管控

模型可以判断“也许应该调用某个工具”，但真正执行删除、付款、发邮件、发布、改配置等动作时，权限、审计、幂等、回滚必须由确定性系统控制。

这就是工具 schema、权限确认、风险分级和 trace 的必要性。

### 因为真实环境持续变化，所以需要反馈闭环

用户问题会变，知识库会变，模型版本会变，业务规则会变。一次上线不能保证长期正确。

这就是为什么生产 AI 系统必须收集反馈、分析失败、更新 eval、灰度发布，并把成熟实践固化成团队规范。
