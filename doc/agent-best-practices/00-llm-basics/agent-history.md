# 00.2 Agent 的发展历史

[返回本章](README.md)

大模型能力增强之后，工程重点并不是一步到位变成“全自动 Agent”。真实的发展路径更像一层一层给概率预测机器加约束、加上下文、加工具、加状态、加恢复机制。

![Agent 工程范式演进](../assets/diagrams/agent-engineering-evolution.svg)

## 1. Prompt 优化：先解决“怎么问”

早期使用大模型时，工程重点主要是 Prompt engineering：怎样写角色、任务、格式、步骤和示例，才能让模型给出更好的回答。

这一阶段的典型问题是：

- 角色设定怎么写。
- 指令要不要分步骤。
- 输出格式怎么约束。
- 要不要给 few-shot 示例。
- 信息不足时怎么让模型不要编。

Prompt 优化解决的是“把任务说清楚”。但它很快会遇到边界：如果知识不在模型上下文里，Prompt 写得再好也可能答错；如果任务很长，模型也容易丢失关键条件。

## 2. 上下文工程：再解决“给它看什么”

后来工程重点从单纯写 Prompt，转向管理上下文。因为模型的输出不是只由问题决定，而是由完整上下文决定。

上下文包括：

- 系统指令。
- 用户输入。
- 历史对话。
- 检索出来的文档。
- 工具返回结果。
- 业务规则。
- 安全策略。

这就引出了 RAG、chunk、rerank、引用、长上下文压缩和上下文防注入。工程目标从“让模型听懂指令”，变成“让模型在正确材料上做概率预测”。

## 3. 记忆与状态：解决“长期任务怎么连续”

当任务从一次问答变成长期协作时，只靠上下文窗口就不够了。窗口会满，历史会被截断，模型也不适合承担可靠状态存储。

于是需要把信息分层：

- 短期上下文：当前对话里马上要用的信息。
- 长期记忆：用户偏好、稳定事实、长期项目背景。
- 业务状态：订单状态、审批进度、任务阶段、工具执行结果。

这里的关键是：记忆和状态不能只靠模型“记得”。长期事实要可更新、可删除、可追踪；任务状态要放在数据库、状态机、任务队列或工作流系统里。

## 4. 工具调用：解决“只会说，不能做”

大模型本身只能生成文本。要完成真实任务，它需要搜索、读文件、查数据库、运行代码、发请求、生成报告、提交 PR 或调用业务 API。

这就进入 Tool Calling 阶段。模型负责判断意图和生成参数，应用系统负责执行工具。

关键边界是：

```text
模型提出要做什么 -> 确定性系统判断能不能做 -> 工具执行 -> 结果回到上下文
```

删除、付款、发布、改配置这类动作不能只靠模型自己决定。权限、审计、确认、幂等和回滚必须由工程系统控制。

## 5. 角色与职责管理：解决“复杂任务怎么分工”

任务变复杂后，一个模型上下文里同时塞规划、检索、执行、审核、写作、测试，很容易互相干扰。于是出现了角色管理和多 Agent 编排。

常见拆分方式包括：

- Planner：拆解目标和步骤。
- Researcher：查资料、找证据。
- Executor：调用工具或改代码。
- Reviewer：检查风险、事实和质量。
- Verifier：跑测试、验证输出。

这里的核心不是角色越多越好，而是职责边界清楚：每个角色要有明确输入、输出、权限和验收标准。

## 6. 错误恢复：解决“失败后怎么办”

Agent 一旦能调用工具和执行动作，失败就会成为正常路径，而不是异常事件。

常见失败包括：

- 检索为空。
- 工具超时。
- 参数错误。
- 权限不足。
- 代码测试失败。
- 外部 API 返回异常。
- 模型理解错目标。
- 长链路执行中间偏航。

因此，Agent 工程必须设计恢复路径：重试、澄清、降级、回滚、人工确认、切换工具、重新规划、保留现场和生成失败报告。

## 7. 长时间运行：解决“怎么稳定完成长任务”

短对话可以靠一次上下文完成，长任务不能。长时间运行的 Agent 需要像生产系统一样管理生命周期。

关键机制包括：

- checkpoint：关键阶段保存状态。
- trace：记录每一步输入、输出、工具调用和决策。
- task state：用确定性状态机记录任务进度。
- budget：控制 token、时间、工具调用次数和成本。
- heartbeat：确认任务仍在推进。
- timeout：长时间无进展时停止或转人工。
- resume：中断后能从上次状态继续。
- verifier：阶段性验证结果是否满足目标。

这一步的目标，是让 Agent 不只是“能跑一会儿”，而是能在可观测、可恢复、可验证的轨道里长期运行。
