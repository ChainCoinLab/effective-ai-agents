# 00.3 上下文与上下文窗口

[返回全局摘要](../README.md) · [返回本组：AI 工程基础知识与原理](README.md)

上下文是每次请求传给模型的全部信息。模型不会天然知道你的业务数据、历史状态和工具结果，只有放进上下文或通过工具/RAG重新取回的信息，才会影响本轮输出。

## 上下文包含什么

一次模型调用的上下文通常包括：

- 系统指令：角色、边界、优先级和安全要求。
- 开发者指令：工程策略、工具使用规则和输出要求。
- 用户输入：用户这轮提出的问题或目标。
- 历史消息：多轮对话中的必要内容。
- RAG 证据：检索出的文档片段、来源和引用。
- 工具结果：API、数据库、命令行、浏览器等返回的 observation。
- 结构化状态：任务进度、审批状态、已确认事实。

## 上下文窗口是什么

上下文窗口是模型一次调用能接收的最大 token 范围。窗口越大，不等于效果越好。上下文太多会带来几个问题：

| 问题 | 说明 |
| --- | --- |
| 成本上升 | 输入越长，调用成本和延迟越高 |
| 重点稀释 | 关键证据被大量噪声淹没 |
| 迷失中间 | 模型可能忽略长上下文中间部分的信息 |
| 指令冲突 | 外部文档和用户输入可能污染系统规则 |
| 历史负担 | 旧信息、错误信息和无关信息继续影响输出 |

## 上下文工程的目标

上下文工程不是“尽量多塞内容”，而是“把本轮任务需要的信息，以正确优先级、正确结构、正确来源放进去”。

好的上下文应满足：

- 只包含当前任务需要的信息。
- 关键规则和证据位置靠前或结构突出。
- 外部内容和系统指令明确分隔。
- 证据有来源、时间和可信度。
- 长任务用摘要、索引和状态表，而不是无限堆聊天记录。

## 和记忆、RAG 的关系

- 上下文是本轮模型实际看到的内容。
- 记忆是系统保存的长期事实或偏好，需要在合适时重新注入上下文。
- RAG 是从知识库检索证据，并把证据注入上下文。
- 状态是确定性系统记录的流程进度，不应该只放在自然语言历史里。
