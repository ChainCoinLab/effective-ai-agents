# 永续合约订单簿 L1 验证测试方案

本文是 [perp-orderbook-l1-architecture.md](./perp-orderbook-l1-architecture.md) 的配套验证文档。主文档回答“为什么这么设计、怎么分阶段做”，本文回答“如何证明它真的达到了目标”。

验证目标不是只跑功能测试，而是证明：

```text
同一批交易可以确定性重放
订单簿、仓位、保证金和资金费率状态一致
MEV 和排序风险被识别、量化和缓解
极端行情下清算和保险基金不会失控
性能能支撑目标订单量
共识和节点故障不会破坏已提交成交
```

## 1. 验证范围

| 范围 | 要证明什么 |
| --- | --- |
| 确定性 | 所有节点执行同一区块得到相同状态根 |
| 订单状态机 | 下单、撤单、改单、过期、成交、部分成交状态转换正确 |
| 撮合引擎 | 价格优先、时间优先、IOC/FOK/GTC、post-only、reduce-only 正确 |
| 市价保护 | 市价单不会无界滑点，必须转成带保护价的 IOC 限价单 |
| 保证金 | 初始保证金、维持保证金、可用余额、仓位价值正确 |
| 资金费率 | funding index 和 funding payment 正确、封顶、不可瞬时操纵 |
| 预言机 | 新鲜度、偏离、异常状态、只减仓模式正确 |
| 清算 | 部分清算、保险基金、ADL、坏账处理正确 |
| MEV | 抢跑、撤单审查、插队、清算抢跑等有复现和缓解评估 |
| 性能 | 下单、撤单、撮合、批量撤单、索引追块满足目标 |
| 共识 | 停机、分区、提议者作恶、最终性假设被验证 |

## 2. 确定性验证

### 2.1 多节点重放

目标：

- 同一区块交易序列在不同节点、不同机器、不同执行次数下得到相同状态根。

方法：

```text
生成交易集
  -> 在节点 A 执行
  -> 在节点 B 执行
  -> 在节点 C 执行
  -> 比较 app hash、orderbook root、position root、margin root
```

通过标准：

- app hash 完全一致。
- 每个市场订单簿 root 完全一致。
- 每个账户仓位和保证金完全一致。
- 事件序列完全一致。

### 2.2 非确定性扫描

重点检查：

- 不使用浮点数。
- 不依赖本地系统时间。
- 不依赖 map 非确定性迭代顺序。
- 不依赖节点本地接收交易时间。
- 所有舍入规则一致。
- 所有排序 key 显式定义。

## 3. 订单和撮合测试

### 3.1 基础订单类型

| 用例 | 预期 |
| --- | --- |
| 限价买单低于卖一 | 进入买方订单簿 |
| 限价买单高于卖一 | 按卖方 maker 价格成交 |
| 限价卖单低于买一 | 按买方 maker 价格成交 |
| 市价买单 | 转成带 max_price 的 IOC 限价单 |
| 市价卖单 | 转成带 min_price 的 IOC 限价单 |
| IOC 部分成交 | 未成交部分取消 |
| FOK 可全部成交 | 全部成交 |
| FOK 不可全部成交 | 整单拒绝 |
| GTC 部分成交 | 剩余部分挂单 |
| post-only 会成交 | 拒绝或取消，按规格执行 |
| reduce-only 会增仓 | 拒绝 |
| 过期订单 | 不进入撮合 |

### 3.2 撤单和改单

| 用例 | 预期 |
| --- | --- |
| 撤销存在订单 | 状态变为 Cancelled |
| 撤销不存在订单 | 返回确定性错误 |
| 撤销已成交订单 | 返回确定性错误 |
| 批量撤单 | 指定市场或方向订单全部取消 |
| 改单 | 旧单取消，新单重新分配队列优先级 |
| 同区块撤单和吃单 | 按规格中的撤单优先规则执行 |

### 3.3 撮合边界

需要覆盖：

- 同价位多订单队列。
- 单笔 taker 吃多个 price levels。
- maker 部分成交。
- taker 部分成交。
- 最小 tick size。
- 最小 lot size。
- 最小订单价值。
- 价格精度非法。
- 数量精度非法。
- 单笔订单撮合次数上限。

### 3.4 撮合引擎风险测试

| 风险 | 测试方式 | 通过标准 |
| --- | --- | --- |
| 非确定性执行 | 多节点重复执行同一批订单 | app hash、trade root、orderbook root 一致 |
| 同价位队列错误 | 同价位插入多笔订单后逐笔成交 | 严格按 `order_sequence` 成交 |
| 市价单无保护 | 构造盘口深度不足的大市价单 | 只在保护价内成交，剩余取消 |
| FOK/IOC 语义错误 | 构造部分可成交场景 | FOK 整单拒绝，IOC 剩余取消 |
| post-only 误成交 | post-only 订单 crossing book | 按规格拒绝或取消，不产生 taker 成交 |
| reduce-only 增仓 | reduce-only 反向超过现有仓位 | 不得增加绝对风险敞口 |
| 部分成交错误 | maker/taker 多轮部分成交 | remaining quantity、余额、仓位一致 |
| 撮合循环过长 | 单笔订单吃大量 price levels | 达到上限后停止或拆分，区块不超时 |
| 并行市场合并错误 | BTC/ETH/SOL 同区块并行撮合 | 合并顺序确定，多节点 root 一致 |
| 撤单撮合竞态 | Bob 撤单和 Alex 吃单同区块 | 按 Protection Queue 规则执行 |
| 状态膨胀 | 大量小订单长期挂单 | 最小订单价值、过期、费用规则生效 |
| 索引器不一致 | 从事件重建盘口并对比 root | read model root 和链上 root 一致 |

## 4. 金融不变量测试

每个区块后都应检查：

```text
总抵押资产守恒
手续费入账守恒
保险基金变动可解释
用户余额不能非法为负
open interest 与仓位汇总一致
long OI / short OI 与市场统计一致
realized PnL + unrealized PnL 计算一致
funding payment 多空相互抵消，除非协议明确收取费用
reduce-only 不增加风险敞口
max leverage 不可绕过
position cap 不可绕过
market open interest cap 不可绕过
```

## 5. 预言机和价格测试

| 场景 | 预期 |
| --- | --- |
| 正常价格更新 | market 保持 Normal |
| 价格过期 | 进入 Degraded 或 ProtectOnly |
| 主价格源和辅助价格源偏离 | 拒绝价格或进入保护状态 |
| 指数价大幅跳变 | 触发熔断或限制增仓 |
| 订单簿成交价偏离指数价 | 不直接用于清算 |
| 价格恢复正常 | 按恢复规则回到 Normal |

关键测试：

- 清算不得只依赖最后成交价。
- 单一预言机失效不得导致错误爆仓。
- ProtectOnly 下只允许撤单、补保证金、减仓和平仓。

## 6. 清算和坏账测试

### 6.1 单账户清算

用例：

- 仓位跌破维持保证金。
- 触发部分清算。
- 清算后账户恢复到健康状态。
- 清算奖励入账。
- 保险基金未受损。

### 6.2 大仓位清算

用例：

- 单一大户满杠杆持仓。
- 指数价格瞬间下跌。
- 部分清算多轮执行。
- 不允许一次性砸穿市场。

### 6.3 坏账处理

验证 waterfall：

```text
账户剩余保证金
  -> 清算罚金
  -> 保险基金
  -> ADL
  -> 社会化损失
```

通过标准：

- 坏账不会静默消失。
- 保险基金余额变化有事件。
- ADL 排序规则确定。
- 社会化损失只在明确条件下触发。

### 6.4 清算引擎风险测试

| 风险 | 测试方式 | 通过标准 |
| --- | --- | --- |
| 使用错误价格清算 | 用最后成交价制造异常插针 | 不触发清算，只使用有效标记价 |
| 预言机价格过期 | 停止价格更新后提交清算 | 拒绝清算或进入 ProtectOnly |
| 预言机偏离 | 主/备价格源偏离超过阈值 | 熔断或限制高风险操作 |
| 清算级联 | 指数价瞬间下跌触发大量爆仓 | 部分清算、节流、保险基金流程正确 |
| 一次性全仓清算 | 大仓位跌破维持保证金 | 只按规则部分清算 |
| 清算抢跑 | 多个 liquidator 同时清算同一账户 | 按确定性清算队列或拍卖规则执行 |
| 补保证金审查 | 补保证金和清算同区块 | Protection Queue 先更新保证金 |
| 清算奖励异常 | 构造高额仓位和极端价格 | 奖励不超过规则上限 |
| 无人清算 | liquidator 缺席 | keeper 或协议后备清算流程可触发 |
| 坏账归属 | 清算后 equity 为负 | 坏账进入保险基金/ADL，不静默消失 |
| ADL 排序争议 | 多个盈利账户可被 ADL | 排名公式确定，事件可重建 |
| 跨市场传染 | 多市场全仓账户爆仓 | 保证金模式和市场风险边界符合规格 |
| 清算撮合并发 | 同账户同区块成交和清算 | 先 trade commit，再基于快照清算 |

## 7. MEV 和排序测试

### 7.1 攻击样例

必须构造以下攻击交易集：

| 攻击 | 样例 |
| --- | --- |
| 抢跑 | 大额市价买单前插入攻击者买单 |
| Sandwich | 用户买单前买入、后卖出 |
| Queue jumping | 同价格档中攻击者插到更早订单前 |
| 撤单审查 | maker 撤单被延迟，taker 吃旧报价 |
| 补保证金审查 | 用户补保证金被延迟后遭清算 |
| 清算抢跑 | 多个 liquidator 争抢同一仓位 |
| 预言机更新抢跑 | 价格更新前后插入开仓或清算 |
| Spam | 大量小额订单占满区块 |

### 7.2 验证输出

每个攻击样例都要输出：

- 攻击是否成功。
- 攻击者收益。
- 受害者损失。
- 协议损失。
- 哪条规则限制了攻击。
- 是否需要下一阶段机制才能缓解。

### 7.3 排序规则验证

需要验证：

- `order_sequence` 唯一且单调。
- 同价位按确定性顺序成交。
- 撤单优先规则只保护历史挂单，不被同区块新挂单滥用。
- 区块内市场处理顺序确定。
- 清算队列处理顺序确定。

### 7.4 多交易队列验证

需要单独验证不同交易队列之间的并行和队内串行：

| 验证项 | 预期 |
| --- | --- |
| Oracle Queue 不与普通订单混排 | 价格先形成确定性快照，再进入风险检查和清算 |
| Protection Queue 不被普通订单挤出 | 撤单、补保证金、reduce-only 先于普通开仓提交 |
| Normal Order Queue 队内串行 | 同一市场、同一价格档按确定性 order_sequence 成交 |
| 不同市场并行撮合 | BTC-PERP 和 ETH-PERP 可以并行执行，但合并结果确定 |
| Liquidation Queue 独立处理 | 清算交易不与普通订单共享同一优先级 |
| System Queue 边界生效 | funding、费用、治理参数只在固定 block boundary 生效 |
| 并行结果确定性合并 | price root、trade root、position root、margin root 在多节点一致 |

攻击测试：

- Oracle 更新和普通订单同区块提交，普通订单不得使用未确定价格。
- Bob 撤单和 Alex 吃单同区块提交，按 Protection Queue 规则执行。
- 补保证金和清算同区块提交，按风险保护规则验证是否先更新保证金。
- 多市场并行撮合后，多节点 app hash 必须一致。

### 7.5 序列号和分类验证

需要验证：

- 每笔交易必须先被分类为 OracleTx、ProtectionTx、NormalOrderTx、LiquidationTx 或 SystemTx。
- `queue_sequence` 在同一队列内唯一且单调。
- `order_sequence` 只用于订单簿 resting order 的时间优先级。
- `trade_sequence` 按成交事件单调递增，索引器可用它生成成交历史和 K 线。
- `oracle_sequence` 生成的价格快照在多节点一致。
- 并行执行不能导致 sequence 冲突或 root 不一致。

## 8. 性能测试

### 8.1 压测场景

| 场景 | 指标 |
| --- | --- |
| 大量限价挂单 | 每秒可接受订单数 |
| 大量撤单 | 批量撤单延迟 |
| 单笔大 taker 单 | 最大撮合 price levels |
| 多市场并发 | block execution time |
| 高频做市 | 下单/改单/撤单 p95 延迟 |
| 索引追块 | indexer lag |
| 节点重启 | 订单簿恢复时间 |
| 状态增长 | 每日状态增量 |
| 索引器重建 | 从区块事件恢复订单簿 read model 的耗时 |
| K 线生成 | 1m/5m/1h candle 聚合延迟 |

### 8.2 初始门槛示例

具体数字应根据目标市场调整。可以先设一个测试网门槛：

```text
单市场 10 万 resting orders
单区块 1 万订单操作
单区块 5 千撤单
单笔订单最多撮合 100 个 resting orders
区块执行 p95 < 500ms
索引延迟 p95 < 2 blocks
盘口 WebSocket 延迟 p95 < 1 block
K 线生成延迟 p95 < 2 blocks
节点重启后 5 分钟内恢复订单簿
```

## 9. 共识和故障测试

测试场景：

- 少于三分之一验证者离线。
- 提议者连续缺席。
- 网络分区。
- 双签。
- 节点崩溃后恢复。
- 状态快照恢复。
- 升级过程中状态迁移。
- IBC 或桥接资产延迟。

通过标准：

- 已提交区块不被普通回滚影响。
- 节点恢复后状态根一致。
- 双签可检测并进入 slashing 流程。
- 状态迁移前后金融不变量不破坏。

### 9.1 共识机制比较验证项

如果评估 PBFT、CometBFT、Tower BFT、HotStuff 或 Fast-HotStuff，需要用同一组指标对比：

| 验证项 | 要看什么 |
| --- | --- |
| 消息轮次 | 一个区块从 proposal 到 final commit 需要几轮网络交互 |
| 消息结构 | all-to-all 投票、gossip 投票，还是 leader 聚合 QC |
| 提交证据 | commit certificate、+2/3 precommit、stake vote、QC chain |
| 最终确认块数 | 成交可视为最终状态前，需要 1 个 committed block、31+ confirmed descendants，还是 2/3-chain |
| leader failure | 提议者离线时是否进入新 round/view，是否影响交易延迟 |
| 应用层语义 | 撮合、撤单、清算在哪个点可以对用户显示为最终 |

订单簿 MVP 的最低要求：

```text
成交、撤单、清算必须绑定到明确的 final commit 条件。
不能只依赖 optimistic confirmation 展示最终成交。
共识提交后，多节点重放区块得到相同 app hash。
```

## 10. 阶段验收标准

### 阶段 1：原型

必须通过：

- 基础订单类型测试。
- 单市场撮合测试。
- API 行为测试。

### 阶段 2：验证者内存订单簿 MVP

必须通过：

- 多节点确定性重放。
- 订单簿 root 对账。
- 撤单优先规则测试。
- 市价保护测试。
- 基础 MEV 攻击样例。

### 阶段 3：永续核心闭环

必须通过：

- 保证金不变量。
- 资金费率测试。
- 预言机异常测试。
- 清算和坏账测试。
- 风控压力测试。

### 阶段 4：可验证订单簿强化

必须通过：

- 订单输入和撮合结果对账。
- 市场快照 hash 恢复。
- 索引器完整重建订单簿。
- MEV 收益量化报告。

### 阶段 5：测试网和上线前

必须通过：

- 第三方安全审计。
- 经济安全审计。
- 长时间压测。
- 清算演练。
- 预言机故障演练。
- 验证者停机演练。
- 升级回滚预案演练。
