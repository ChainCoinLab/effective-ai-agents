# 永续合约订单簿 L1 分阶段执行路线

本文单独说明订单簿和撮合能力如何分阶段落地。主文档 [perp-orderbook-l1-architecture.md](./perp-orderbook-l1-architecture.md) 负责从一笔订单的处理流程推导整体架构；本文负责回答“先做哪一层，后做哪一层，每一阶段牺牲什么、验证什么、补什么”。

## 1. 为什么要分阶段

全链上订单簿是最透明的目标形态，但不适合一开始直接上。

原因：

- 全量 resting orders 上链会带来巨大状态增长。
- 高频下单、撤单、批量改单会给执行和存储带来压力。
- 撮合逻辑、保证金、资金费率、预言机、清算还没有验证稳定前，直接全链上会放大复杂度。
- 做市商首先关心延迟、撤单可靠性和 API 稳定性，不只关心最终透明度。
- 公平排序、加密 mempool、批量拍卖等机制本身也需要单独验证。

因此更合理的路线是：

```text
先验证交易体验和风控闭环
  -> 再增强撮合过程可验证性
  -> 再评估全链上订单簿
  -> 最后增强公平排序和订单隐私
```

## 2. 阶段 0：链下撮合，链上结算原型

形态：

```text
中心化撮合服务
  -> 生成成交结果
  -> 链上或本地状态机结算仓位、保证金、资金费率
```

目标：

- 快速验证产品流程。
- 验证订单类型设计。
- 验证做市商 API。
- 验证保证金、PnL、资金费率和清算公式。

支持能力：

- 限价单。
- 市价单保护价。
- IOC/FOK/GTC。
- post-only。
- reduce-only。
- 撤单、批量撤单。
- 单市场或少量市场。

优点：

- 实现最快。
- 性能最好。
- 便于快速调整产品细节。

缺点：

- 撮合不可被链上完整验证。
- 用户需要信任撮合服务。
- 不解决验证者排序和 mempool MEV。

退出标准：

- 订单类型和 API 基本稳定。
- 做市商能完成挂单、撤单、批量改单。
- 保证金和清算公式通过离线测试。

## 3. 阶段 1：验证者内存订单簿 + 链上确定性结算

形态：

```text
验证者运行内存订单簿
  -> 区块中包含多交易队列
  -> Oracle / Protection / Normal Order / Liquidation 分队列执行
  -> 队列间并行校验，队内串行处理
  -> 应用状态机按确定性屏障提交撮合和风控结果
  -> 仓位、保证金、资金费率、清算状态上链
```

这一阶段不是最终完全透明形态，但它是最重要的 MVP 阶段。

目标：

- 验证 BFT 最终性对成交确认是否足够。
- 验证验证者内存订单簿能否支撑下单、撤单、撮合吞吐。
- 验证订单状态机和区块执行状态机。
- 验证撮合结果可以被重放。
- 验证做市商能接受撤单和批量改单延迟。
- 验证永续风控闭环。

链上需要提交：

- Oracle Queue 的价格更新。
- Protection Queue 的撤单、补保证金、reduce-only。
- 订单操作交易。
- 撤单和批量撤单交易。
- Normal Order Queue 的普通下单和撮合结果。
- Liquidation Queue 的清算操作。
- 成交事件。
- 仓位变化。
- 保证金变化。
- 资金费率状态。
- 清算事件。

建议额外提交：

- 每个市场的 orderbook root。
- position root。
- margin root。
- trade root。
- 周期性订单簿快照 hash。
- 订单簿 delta 事件。

展示和行情服务：

```text
验证者内存订单簿
  -> 区块事件和订单簿 delta
  -> Indexer 重建盘口
  -> Market Data API
  -> WebSocket 推送 L2 depth、trades、ticker、funding
  -> Kline Service 聚合 1m/5m/1h K 线
```

这一阶段前端展示不直接读取验证者内存。前端读取索引器生成的 read model，索引器用区块事件、订单簿 delta 和快照 root 对账。

优点：

- 性能和体验接近真实交易系统。
- 不必一开始把每个订单都作为昂贵持久状态处理。
- 已经能通过共识获得最终成交状态。

风险：

- 如果只提交撮合结果而不提交订单输入，其他节点难以验证公平性。
- 验证者可能在 mempool 中观察订单并插入交易。
- 内存订单簿的快照、恢复和节点重启必须严格设计。
- 如果不同节点的内存数据结构存在非确定性，状态根会分叉。

缓解：

- 区块中提交订单操作序列，而不是只提交最终成交。
- 使用确定性 order_sequence。
- 定期输出订单簿 root 和市场快照 hash。
- 所有成交事件包含 maker、taker、价格、数量、费用和成交序号。
- 做多节点重放测试。

退出标准：

- 多节点重放同一区块得到相同 app hash。
- 每个市场 orderbook root 一致。
- 做市商撤单和批量撤单满足延迟目标。
- 基础 MEV 攻击样例被复现并有缓解策略。

## 4. 阶段 2：订单承诺和撮合证明上链

形态：

```text
订单仍可在内存结构中执行
  -> 区块提交订单输入承诺
  -> 区块提交撮合结果
  -> 区块提交订单簿 root / 成交 root
  -> 节点或挑战者可重放验证
```

目标：

- 提高撮合过程透明度。
- 让索引器和审计节点可从链上数据恢复订单簿。
- 为欺诈证明、挑战机制或抽样验证打基础。

新增能力：

- 订单输入可追溯。
- 撮合结果可验证。
- 订单簿快照可对账。
- 历史市场状态可重建。

取舍：

| 维度 | 阶段 1 | 阶段 2 |
| --- | --- | --- |
| 性能 | 更高 | 略低 |
| 透明度 | 中等 | 更高 |
| 状态成本 | 低 | 中等 |
| 可审计性 | 依赖事件 | 依赖承诺和 root |
| 公平排序 | 仍需额外设计 | 仍需额外设计 |

退出标准：

- 独立重放工具能从区块数据恢复订单簿。
- trade root 和 orderbook root 可对账。
- 索引器能完整重建行情和订单状态。
- 异常撮合可以被发现。

## 5. 阶段 3：全链上订单簿 + 确定性撮合

形态：

```text
订单状态、价格档、队列、撮合和成交都在链上状态机维护
```

目标：

- 最大化透明度。
- 所有节点完整重放即可验证订单簿状态。
- 状态根完整反映订单簿、仓位、保证金和风险状态。

需要解决：

- 价格档数据结构。
- 同价位订单队列。
- 大量撤单的存储清理。
- 状态数据库读写优化。
- 每笔订单最大撮合次数。
- 每个市场最大 resting orders。
- 最小订单价值。
- 订单过期和状态租金。

优点：

- 透明度最高。
- 可验证性最强。
- 对第三方索引和审计最友好。

缺点：

- 状态增长大。
- 执行成本高。
- 性能压力最大。
- 对 spam 防护要求高。

适用条件：

- 核心市场数量有限。
- 订单簿和撮合逻辑已稳定。
- 性能压测达到目标。
- 有明确状态增长控制方案。

退出标准：

- 全链上订单簿 PoC 通过压测。
- 状态增长可控。
- 节点重启和快照恢复达标。
- 多市场撮合不会超过区块执行预算。

## 6. 阶段 4：公平排序和订单隐私增强

前几个阶段主要解决确定性、风控和可验证性。成熟阶段再增强公平排序和订单隐私。

候选方案：

| 方案 | 作用 | 代价 |
| --- | --- | --- |
| 区块级批量撮合 | 降低精确插队价值 | 改变连续撮合体验 |
| 频繁批量拍卖 | 增强公平性 | 产品体验变化更大 |
| commit-reveal | 隐藏订单内容 | 增加交互轮次和延迟 |
| 阈值加密 mempool | 抗抢跑更强 | 密钥管理和 liveness 复杂 |
| inclusion list | 降低审查风险 | 共识和 mempool 复杂度增加 |
| 跨验证者接收证明 | 证明订单曾被多个节点接收 | 需要额外网络协议 |

建议顺序：

```text
先做 MEV 监控和攻击复现
  -> 再做区块级批量撮合 PoC
  -> 再评估 commit-reveal
  -> 最后评估阈值加密 mempool
```

原因：

- 阈值加密和公平排序协议会明显增加工程复杂度。
- 如果撮合和清算状态机还不稳定，过早引入会增加排查难度。
- 先量化 MEV，才能判断需要哪种强度的防护。

## 7. 阶段对照表

| 阶段 | 核心目标 | 主要牺牲 | 进入下一阶段的条件 |
| --- | --- | --- | --- |
| 阶段 0 | 快速产品和公式验证 | 去中心化和可验证性弱 | API、订单类型、风控公式稳定 |
| 阶段 1 | 验证者内存订单簿 MVP | 撮合透明度有限 | 多节点重放和风控闭环通过 |
| 阶段 2 | 承诺和 root 增强可验证性 | 成本增加 | 可独立重建订单簿和成交 |
| 阶段 3 | 全链上订单簿 | 性能和状态压力大 | 压测、状态增长、恢复能力达标 |
| 阶段 4 | 公平排序和隐私增强 | 协议复杂度高 | 已量化 MEV，并确认需要更强防护 |
