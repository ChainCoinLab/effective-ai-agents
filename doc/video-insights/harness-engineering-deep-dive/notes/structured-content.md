## 一句话概括

Harness Engineering 的核心不是教模型回答得更漂亮，而是给 Agent 设计一套可控、可恢复、可验证的外部运行体系，让长链路任务能稳定完成。

## 核心论题

作者认为 Agent 落地的竞争点正在从“会不会写 prompt、会不会塞上下文”转向“能否构建模型外部的运行约束系统”。单轮回答可以靠 Prompt Engineering 改善，信息不足可以靠 Context Engineering/RAG 缓解，但长链路、多工具、高风险、可恢复的生产任务需要更外层的流程治理。

## 问题

- 单轮 demo 顺滑不等于复杂任务可商用；长链路任务会出现上下文耗尽、逻辑断裂、过早结单和任务遗忘。
- 单步成功率看似高，组合成长任务后会快速衰减。视频用 `0.95^20` 说明 20 步任务的总体成功率可能只剩约 36%。
- 只换更强模型无法解决流程状态、权限边界、工具误用、失败恢复和人工审批问题。
- Prompt 和 Context 解决的是“怎么说”和“看什么”，Harness 解决的是“如何按规则把整件事做完”。

## 方法

视频把成熟的 Harness Engineering 拆成六个模块：

1. 上下文工程：用项目级规则、上下文隔离和动态摘要控制 Agent 该知道什么、不该知道什么。
2. 工具编排：按任务裁剪工具集，用标准协议接入工具，并为工具调用配置隔离箱。
3. 验证机制：用确定性规则、lint、pre-commit、结构测试和独立评估 Agent 约束模型输出。
4. 状态管理：把任务清单、进度台账、检查点和快照持久化，不依赖模型内部记忆。
5. 可观测性：记录上下文变化、工具调用、推理摘要、验证结果和失败位置，用 trace 做归因。
6. 人类接管：在数据库写入、支付扣费、正式通知、合规敏感输出等高风险节点暂停自动执行，交回人类确认。

## 论证链

1. 复杂 Agent 的失败主要来自模型外部链路，而不是单次文本生成质量。
2. Prompt Engineering 只能改善单轮表达，Context Engineering 只能改善信息供给。
3. 长任务需要任务拆解、状态持久化、检查点、验证和回滚，否则错误会在链路中累积。
4. 多工具和多 Agent 会带来选择错误、权限越界、协作混乱和成本上升，必须通过 workflow 和边界管理约束。
5. 因此，生产级 Agent 的工程重点应是“模型 + 外部治理系统”的组合，而不是裸模型自治。

## 面试回答模板

我会把 Harness Engineering 理解为 Agent 的外部运行治理体系。Prompt 解决单轮表达，Context 解决信息供给，而 Harness 解决长链路任务如何稳定完成。具体落地时，我会先把业务流程 workflow 化，把任务拆成可验证单元；再为每个单元设计上下文输入、工具权限、结构化状态、验证规则、失败恢复和人工接管点。模型只负责需要语义理解和动态判断的部分，状态、权限、验证、回滚和审计由确定性系统负责。这样可以避免长任务遗忘、工具误用、概率错误累积和高风险动作失控。

## 工程结论

Harness Engineering 可以沉淀为一条已有最佳实践的扩展：优先 workflow，再升级 Agent。所谓 Harness，不应被当成新术语堆叠，而应落到可执行的控制点：上下文、工具、验证、状态、观测和人审。
