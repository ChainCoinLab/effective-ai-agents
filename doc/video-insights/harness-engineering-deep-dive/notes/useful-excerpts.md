# 【B站强推】Harness Engineering深度解析，从概念解析到落地指南一次性讲透，小白也能轻松看懂，快速掌握！少走99% 弯路！ 有用摘录

## 筛选标准

只保留能复用、能指导行动、能解释判断标准，或能作为后续写作素材的片段。视频中无法验证的厂商数字只作为作者叙述背景，不进入工程依据。

## 可复用观点

- Harness Engineering 不是让模型回答得更好，而是给模型外部设计一套完整工作流程。
- Prompt 解决“怎么说”，Context 解决“知道什么”，Harness 解决“如何把一整件事稳稳当当做完”。
- 复杂 Agent 的问题通常是系统设计问题：任务拆解、上下文管理、工具编排、权限、状态、验证、回滚、人审。
- 单步成功率不能代表端到端成功率。多步任务必须设计中间检查点，否则错误会连锁放大。
- 工具从来不是越多越好，而是越精准越好。给模型无关工具会增加误选和上下文噪声。
- 外部持久化优先于模型内部记忆。需求文档、进度台账、接口规范、提交历史应由系统保存。
- 可观测性要能追踪每一步的上下文变化、工具调用、验证结果和失败位置。
- 人类接管不是能力不足，而是高风险系统的必要刹车。

## 可复用方法

- `04:53` Harness 的本质不是教模型回答问题，而是设计完整工作流程。
- `05:14` 它管理长任务拆解、上下文窗口、工具编排、权限、状态交接、结果验证、失败回滚和人类接管。
- `06:35` Harness 关注 Agent 全生命周期可靠性：长链路不跑偏、复杂流程不崩溃、高风险操作不闯祸。
- `09:36` 多步骤任务不能只看单步成功率，20 个步骤每步 95% 成功时，端到端成功率会明显下降。
- `10:06` 每隔几步设置安全节点，流程出错时回退到上一个安全节点继续运行。
- `14:13` 在关键决策点生成状态快照，记录任务进度、前置结论、待办事项和校验结果。
- `15:23` 把需求文档、进度台账、接口规范、提交历史持久化，Agent 启动前先读取最新状态。
- `16:21` 成熟体系包含上下文工程、工具编排、验证机制、状态管理、可观测性和人类接管六个模块。
- `17:04` 每个子任务只给对应上下文，避免无关信息污染。
- `17:34` 按需裁剪工具集，只保留当前业务相关工具。
- `18:24` 用 lint、pre-commit hook、结构测试等确定性规则卡住低级错误。
- `18:53` 生成与评估分离，独立评估 Agent 只做校验不做生成。
- `19:28` 用 JSON 格式维护任务清单和进度台账，全程持久化存储。
- `20:28` 失败时根据 trace 追溯 Harness 哪个环节出错，再反向优化系统。
- `21:12` 数据库核心数据变更、资金扣费、正式客户通知、合规敏感输出必须触发暂停和人工确认。

## 可复用操作步骤

1. 为关键 Agent 任务先画 workflow，标出动态判断节点、确定性规则节点、工具节点、验证节点和人工接管节点。
2. 在项目根目录维护 Agent 规则文件，写清项目规则、权责边界、禁止事项和输出标准。
3. 按子任务隔离上下文，只注入当前步骤需要的代码、文档、证据和状态。
4. 为工具建立最小可用工具集，并按只读、可写、高风险、禁止执行分级。
5. 在工具执行前做 schema、权限和业务规则校验；在执行后记录结构化 observation。
6. 用状态表或 JSON 文件持久化任务进度、当前节点、已完成事项、阻塞问题和下一步。
7. 在关键节点创建检查点，失败时回滚到最近有效状态，而不是整条链路重跑。
8. 把生成和评估分离：生成 Agent 负责产出，独立验证器负责 lint、测试、规则校验和验收。
9. 建立可回放 trace，至少记录上下文输入、工具调用、参数、结果、验证反馈和人工确认。
10. 为高风险动作设置强制暂停，人工确认后才能继续执行。

## 值得保留的表达

- “Prompt 教模型怎么说，Context 教模型该知道什么，Harness 教模型按规矩把事情做完。”
- “模型是引擎，Harness 是整车设计。”
- “外部持久化优先于模型内部记忆。”
- “我们要的是 AI 副驾驶，不是失控的自动驾驶。”

## 暂不采纳的内容

- 视频提到的厂商发布时间线、联合标准、成功率提升和异常率数字需要独立来源验证，暂不作为事实沉淀。
- “2026 不会 Harness 就拿不到入场券”属于营销化表达，可转化为“复杂 Agent 落地需要流程治理能力”，不直接采用。
- 只创建 `Agent.md` 不能代表完整 Harness；它只是最低成本的规则入口，真正可靠性还依赖 workflow、状态、验证、观测和权限。
