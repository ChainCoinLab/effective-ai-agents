## 中心思想

Harness Engineering 是把 Agent 从“裸模型调用”变成“受 workflow 约束的生产系统”的工程方法。它关注模型外部的全链路控制：任务如何拆、上下文如何给、工具如何用、状态如何存、结果如何验、失败如何恢复、风险何时交给人。

## 思维导图

```text
Harness Engineering
├─ 1. 为什么出现
│  ├─ 模型能力趋同，单靠换模型拉不开差距
│  ├─ 裸模型长任务容易上下文耗尽、逻辑断裂、过早终止
│  ├─ 多步骤任务存在概率连锁失败
│  └─ 商用竞争转向系统化架构和流程可靠性
├─ 2. 和 Prompt / Context 的区别
│  ├─ Prompt Engineering: 教模型怎么说
│  ├─ Context Engineering: 教模型该知道什么
│  └─ Harness Engineering: 让模型按规矩把整件事做完
├─ 3. 六大模块
│  ├─ 上下文工程: 规则、隔离、摘要和清理
│  ├─ 工具编排: 精准工具集、标准协议、沙箱隔离
│  ├─ 验证机制: 确定性规则、独立评估、交叉审查
│  ├─ 状态管理: 进度台账、检查点、跨会话恢复
│  ├─ 可观测性: trace、归因、指标和迭代闭环
│  └─ 人类接管: 高风险节点暂停并确认
└─ 4. 避坑
   ├─ 不把 Harness 泛化成任何配置文件
   ├─ 不为旧模型能力过度定制复杂架构
   ├─ 不迷信多 Agent，先看任务是否真的需要分工
   └─ 保持轻量、模块化、可插拔
```

## 论点、论据、论证

| 论点 | 视频中的论据 | 论证重点 | 我的判断 |
| --- | --- | --- | --- |
| Harness 的本质是流程治理，不是提示词技巧 | 作者多次强调它不是让模型回答问题，而是设计完整工作流程 | 把模型能力包进外部控制系统 | 采纳，和 workflow-first 实践一致 |
| 长任务不能裸跑 | 视频指出上下文耗尽、过早终止和跨会话遗忘 | 长链路需要拆解、状态和检查点 | 采纳，状态必须外置 |
| 单步成功率会在长链路中衰减 | `0.95^20` 约等于 36% | 多步任务要有中间验证和回滚 | 采纳，适合写进 eval 与 workflow 设计 |
| 工具不是越多越好 | 作者用“工具箱过大反而混乱”的例子说明工具裁剪 | 工具选择也是上下文和权限问题 | 采纳，和工具 Top-K/路由一致 |
| 多 Agent 不是天然更强 | 视频声称多 Agent 异常率更高，并提醒分工会增加协调成本 | 多 Agent 要服务边界清晰的协作，不是炫技 | 采纳原则，不采纳未验证数字 |
| Harness 要轻量可插拔 | 作者提醒模型能力迭代会淘汰过度定制方案 | 外部治理要匹配当前模型能力和业务风险 | 采纳，避免为临时模型缺陷写死复杂架构 |

## 可迁移原则

- 把 Agent 当作 workflow 中的动态判断节点，而不是让它拥有整条流程的自由执行权。
- 把状态、权限、验证、回滚和审计放在确定性系统里，不要放在自然语言记忆里。
- 对每个长任务节点定义输入、输出、依赖、验收标准、失败条件和人工接管条件。
- 复杂度必须和风险匹配：低风险任务保持轻量，高风险任务增加验证、确认和回滚。
