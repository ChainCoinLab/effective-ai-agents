# 面试官：大模型的 function calling 是怎么实现的？ 思维导图提炼

## 中心思想

Function calling 的核心不是“模型会调用代码”，而是“模型会生成可校验的调用意图，应用负责执行与安全边界”。

## 思维导图

```text
Function calling 实现机制
├─ 本质
│  ├─ 模型不是执行器
│  ├─ 模型输出工具调用意图
│  └─ 应用后端执行真实动作
├─ 闭环
│  ├─ 工具 schema 注入上下文
│  ├─ 模型生成工具名和参数
│  ├─ 后端校验并执行 API
│  └─ observation 回填给模型
├─ 底层机制
│  ├─ SFT 学会工具调用样式
│  ├─ special tokens 标记工具调用模式
│  └─ constrained decoding/FSM/GBNF 保证 JSON 语法
├─ 可观测性
│  ├─ 测试驱动观测：链路是否按设计运行
│  ├─ 目标驱动观测：设计是否真正服务目标
│  └─ telemetry：提供运行事实证据
└─ 生产落地
   ├─ 工具检索减少候选工具
   ├─ strict mode 和 Pydantic 做强校验
   ├─ 错误反馈给模型重写
   └─ 权限拦截和 HITL 保护高风险动作
```

## 论点、论据、论证

| 论点 | 论据 | 论证重点 | 我的判断 |
| --- | --- | --- | --- |
| 工具调用不是代码执行 | 模型只生成工具名和 JSON 参数，真实 API 由后端执行 | 区分模型意图和应用执行 | 这是解释 function calling 的第一句话 |
| 格式稳定来自训练与解码约束 | SFT 教会模式，约束解码按 schema 限制 token | 语法正确不等于语义正确 | 需要补一句后端校验 |
| 工具过多会降低选择稳定性 | 视频建议从大量 API 中检索最相关的 3-5 个工具 | 工具检索是 context engineering 的一部分 | 可落到生产 checklist |
| 后端是安全边界 | 参数校验、权限拦截、HITL 都在应用层完成 | 模型不能拥有直接执行敏感指令的权限 | 可合入工具调用最佳实践 |
| 可观测性要区分观测模式 | 测试驱动观测看链路是否按设计运行，目标驱动观测看设计是否真正服务目标 | telemetry 提供证据，但目标和测试决定看什么 | 适合作为视频之外的工程实践延伸 |
