# 面试官：大模型的 function calling 是怎么实现的？ 体验总结

## 我认可的部分

- 把 function calling 解释成“结构化调用意图 + 应用执行闭环”，比“模型调用函数”更准确。
- 把面试回答分成“本质、底层、实战”三段，容易讲清楚，也符合真实工程边界。
- 视频提到工具检索、参数校验、错误反馈、HITL，这些比单纯讲 schema 更接近生产问题。
- 更准确的延伸方向不是把测试/目标相关内容塞进工具调用原理，而是沉淀成可观测性实践：测试驱动观测和目标驱动观测。

## 我存疑的部分

- 视频对 constrained decoding 的表达偏绝对。约束解码能保证语法形状，但不能保证模型选对工具、参数值正确或动作安全。
- Special tokens 是否暴露、如何表示工具调用，取决于具体模型和 serving 框架；面试时应说“可能通过特殊标记或协议字段表达”，不要讲成所有模型都一样。
- “函数定义塞进系统提示词”是易懂说法，但现代 API 往往通过专门的 tools/tool_choice/response_format 字段承载，不一定只是纯文本 prompt。
- 不应把可观测性写成“工具调用链路基础”。更准确的说法是：测试驱动观测从 eval/断言出发，目标驱动观测从用户目标、业务目标和 SLO 出发，telemetry 只是事实载体。

## 可以马上实践的动作

1. 写面试回答时，用“协议闭环、模型机制、工程防线”三段式组织。
2. 设计工具调用系统时，把 schema、工具检索、参数校验、错误反馈、权限拦截列成同一张 checklist。
3. 在最佳实践里单独补充“可观测性的两种观测模式”，不要放在工具调用基础页里。
4. 给关键 AI 工作流同时补齐测试驱动观测和目标驱动观测。

## 后续要验证的问题

- 当前项目文档里是否已经区分“模型调用意图”和“应用执行权限”。
- 工具调用章节是否明确说明 constrained decoding 的边界：语法有效不等于语义正确。
- 是否需要单独补一页“工具调用参数校验与错误自修复”。
- 是否需要把“可观测性观测模式”继续扩展到 RAG、Prompt、Agent 和工具调用的统一模板。

## 我的结论

这条视频适合沉淀为 function calling 基础原理；可观测性部分应作为独立工程实践延伸。它的工程价值在于提醒：function calling 的关键不是让模型“更会调用”，而是把模型输出限定为可校验意图，并把执行、权限和错误处理牢牢放在应用层。
