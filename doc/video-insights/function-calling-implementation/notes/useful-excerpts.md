# 面试官：大模型的 function calling 是怎么实现的？ 有用摘录

## 筛选标准

只保留能复用、能指导行动、能解释判断标准，或能作为后续写作素材的片段；单纯寒暄、重复铺垫和无法验证的泛泛表达不进入核心摘录。

## 可复用观点

- Function calling 的本质不是模型运行代码，而是模型输出受限的结构化调用意图，后端代码执行真实动作。
- 工具 schema 不是装饰，它同时影响模型选择工具、生成参数和推理层约束解码。
- 约束解码可以提升 JSON 语法稳定性，但不能替代业务参数校验、权限控制和安全审计。
- 生产环境的工具调用能力，最终取决于后端错误恢复、参数校验和安全拦截是否扎实。
- 可观测性要先区分观测模式：测试驱动观测看链路是否按设计运行，目标驱动观测看设计是否真正服务用户目标或业务目标。

## 可复用方法

- 用“schema -> 模型决策 -> 后端执行 -> observation 回填 -> 模型回答”解释完整闭环。
- 用“SFT + special tokens + constrained decoding”解释模型为什么会按工具格式输出。
- 用“工具检索、strict mode、强类型校验、错误反馈重试、HITL”解释生产经验。
- 用“测试驱动观测 + 目标驱动观测 + telemetry”解释工程可靠性：先明确要验证什么、要达成什么，再用 traces/logs/metrics 复盘。
- 对大量工具先做检索，只给模型当前任务最相关的少量工具，降低误选和参数幻觉。

## 可复用操作步骤

1. 为每个工具定义清晰名称、用途、参数 schema、必填字段、枚举值和返回结构。
2. 工具数量很多时，先用检索或路由选出当前问题最相关的少量工具。
3. 开启可用的 strict/structured output 机制，减少语法级 JSON 错误。
4. 后端用 Pydantic、Zod 或等价方案做强类型校验，不信任模型参数。
5. 校验失败时，把结构化错误反馈给模型，让模型在约束内重写调用参数。
6. 对删除、转账、发消息、改配置等高风险动作，应用层必须做权限检查和人工确认。
7. 建立测试驱动观测：为关键链路写 eval，覆盖正常路径、无需调用、参数缺失、越权、工具失败和重试恢复。
8. 建立目标驱动观测：围绕任务成功率、人工接管率、成本、延迟、安全拦截和投诉率设计指标。
9. 为每次关键链路写入 trace/span 与结构化日志，记录决策、参数、校验结果、执行状态、错误类型和恢复动作。

## 值得保留的表达

- “模型作为大脑输出指令，代码作为手脚执行。”这句话适合口语化解释，但工程文档里应改成“模型提出调用意图，应用执行真实动作”。
- “受限的结构化参数生成”是面试时最短的本质定义。
- “生产环境好不好用，不只看模型聪不聪明，更看后端错误重试、参数校验和安全拦截。”

## 暂不采纳的内容

- “有了约束解码，模型输出格式才能达到百分之百准确”需要降级理解：只在实现完备、schema 可表达且解码器严格执行时保证语法有效，不能保证工具选择、字段语义和业务安全正确。
