工程界有句老话, 叫缓存统治一切。
到了 AI agent 的时代, 这话还是对的。
Answeropict 工程师, 最近给出了 Cloud Code 提示词
缓存设计的最佳实践。
但聊具体经验之前, 先用一分钟搞懂提示词缓存到底是什么。
每次你给大模型发消息, 后台都要把你发过来的所有文本。
系统指令, 律师对话, 新消息, 从头到尾编码一遍。
这个过程是延迟和花钱的大头。
问题来了。
你跟他聊二十轮, 第二十轮的请求里前十九轮和上次一模一样。
但模型还得从第一个字重新算一遍, 白白做了十九轮重复劳动。
提示词缓存就是来解决这个的。
原理一句话, 你在请求里飙一个断点,
后台就把从开头到这个断点之间的编码结果存下来。
下次前追完全一样, 直接复用, 跳过重复计算。
打个比方, 你每次写论文都要重超目录和前几章再接新内容。
有了缓存相当于超过的部分直接快进, 直写新的那一段。
几个关键属词, 命中缓存的部分, 价格打一折。
首次写入要1.25倍, 多花百分之二十五,
但后面每次审百分之九十, 默认存五分钟。
五分钟内有请求就自动学期, 不额外收钱,
也可以选一小时的付费版本。
不过有个门槛, 内容太短缓存不上,
一般至少要1024个头肯, 新一点的模型要4096个。
短prompt没缓存的粉, 举个实在的例子,
10万字的成对化。
不开缓存, Claude Sonnet每轮要花0.30美金。
开了缓存,首次0.375, 之后每轮只要0.03,
辽时轮省下大约90%的输入成本。
而且不光省钱,延迟也降下来了。
不用重算的部分越多, 第一个字出来的越快。
理解了这个, 下面七条经验就好懂了。
他们都在讲一件事,
怎么让钱坠尽可能多地命中缓存?
anthropic内部,
把缓存命中率当基础设施级别的指标再看。
地位跟服务器在线率差不多, 命中率一调,
触发值班告警, 工程师得当线上事故处理。
原文用的词是宣布分级事故,
意思是走完整的事故响应流程, 比普通告警严重多了。
更关键的是,命中率高,不光省钱, 还直接影响用户体验。
它让anthropic能挤付费用户更宽松的使用额度。
缓存命中率越高, 你在同样的价格下能用得越多。
所以缓存对Cloud Code 来说不是紧上添花的优化,
是整个系统能跑起来的前提。
没有缓存就没有Cloud Code。
为什么?
因为Cloud Code 这种 AI 编程助手是长对话的。
一个绘画几十轮, 每一轮都要把上文全带上重新发,
每次都从头算, 延迟和成本会爆炸。
而缓存的核心原理, 钱坠匹配。
下一次请求的钱坠跟上次一样, 就能附用之前的计算。
最重要的那条经验, 就从这个原理长出来。
既然缓存靠钱坠匹配, 那提示此里东西的排列顺序就至关重要了。
Nsropic 的最佳实践是这样排的。
最前面,放系统指令和工具定义, 这些是固定的。
所有绘画共享。
第二层,放项目文档, 同一个项目内共享。
第三层,放当前绘画的上下文, 只在这一次对话里有效。
最后才是聊天消息, 逐轮增长。
每轮只新增最后一条。
一句话, 越不容易变的东西, 越往前放。
就好比收拾书桌。
常年不动的参考书, 放最底层。
这周要看的资料放中间。
今天写的草稿, 放最上面。
这样你每天坐下来, 才不用把整张桌子翻一遍。
这里有几个特别容易采的坑。
第一个, 在固定指令里欠了当前时间, 每秒都在变,缓存直接肥掉。
第二个,工具定义用无序容器来装。
每次发请求顺序都不一样, 前绘对不上。
第三个,工具参数改了, 哪怕只动一个字短,整条前绘的缓存全失向。
一个小细节没注意, 整条缓存链就断了。
那信息确实过时了怎么办?
比如时间,文件状态这些。
Anthropic的做法是, 别去改系统指令。
把更新塞进下一轮的消息里。
具体怎么做?
在下一条用户消息里附上一段系统提醒, 把要更新的信息加带进去,
这样系统指令稳思不动,缓存缓好无损。
这个分法挺值得记以下。
系统指令当地基,盯死不动。
消息当流水,想怎么改怎么改。
这样一分,缓存就稳了。
下一条,对很多人来说有点反直觉。
你可能会想,简单问题切到小模型省点前,
难题再切回大模型。
多合理啊。
但现实是,缓存是跟模型绑定的。
换模型,等于之前积攒的所有缓存全部作废,从头重建。
重进的成本往往比让大模型直接回答那个简单问题还要高。
所以Cloud Code的策略是,主对化自始至终用同一个模型。
那需要小模型干活的时候怎么办?
派紫任务。
紫任务有自己独立的上下文和缓存,不会污染主对化的缓存链。
具体做法是,让主模型先写个任务交接说明,把上下文浓缩好,
然后传给紫任务去执行。
做完,只把结果传回主对化。
Cloud Code里的探索模式就是这样工作的。
它用小模型在独立的上下文里执行探索任务。
打个比方。
你不会为了审视让实习生做到你工位上,用你的电脑。
而是给它分配一台独立的机器,把任务说明写清楚发过去。
做完,把结果发回来。
这里要给搞中转的朋友提个行。
缓存是按账号隔离的。
我看到有人想用账号吃搞中转。
账号吃一混,命中率过低,钱没赚到,反而把号搞没了。
还有教你喀喀切账号的也要留意,别聊两句就来回钱。
下一条核心一样,对话过程中工具急不要动。
直觉上你可能觉得,当前任务就需要三个工具,把另外三十个移走,不更干净吗?
但工具定义是缓存前置的一部分,加一个,减一个,缓存就断了。
一断,就是整个对话的缓存全部重建。
代价远远超过多放几个工具定义站的那点空间。
看着相优化,结果是添乱。
Cloud Code有个规划模式。
进入后,模型指思考,指规划,不执行操作。
按直觉的做法,进规划模式就把执行类工具移走,退出来再加回来。
但Anthropic没这么干。
他们的做法是保留所有工具不动,另外加了两个特殊工具。
进入规划和退出规划。
模型调用进入规划就切到思考模式。
调用退出规划就回来。
那规划模式下不能执行这个约束怎么传达。
通过在对话中插入一条系统消息,告诉模型你现在在规划。
注意,是在对话流里插一条消息,不是去赶系统指令。
这两个东西要分清。
系统指令是固定的,在缓存前坠里对话消息是流动的,不影响前坠。
这样工具极始终不变,缓存始终有效,而且还带来一个额外好处。
模型可以自己判断什么时候进规划模式。
遇到复杂任务,它自己先想清楚,再动手,不用你手动切换。
Cloud Code可能要介入几十个外部工具。
全部完整定义塞进去,太占空间。
按需加减,又破坏缓存。
Enthropic 找到的折中方案,叫延迟加载。
一开始只放一个轻量的站位符,模型看到的只是工具名字,不含完整的参数定义。
等模型真要用某个工具了,再通过工具搜索功能,去拉取完整定义。
好处是,前坠始终只包含那些轻量站位符。
不会因为加载了某个工具就变化,缓存稳稳的。
相当于图书馆的书目所影,你先翻目录,找到想看的书,再去书架去。
不用把所有书都搬到桌上。
值得一提,这个工具搜索功能已经通过接口对外开放了。
开发者可以直接用,简化自己的工具管理。
最后一条,关于上下文压缩,也是技术上最巧妙的一条。
长对话跑久了,上下文窗口会被填满。
这时候,要把之前的对话压缩成摘药,腾出空间继续了。
但问题来了,如果你另起一个请求做压缩,用了不同的系统指令,没带工具定义,
那从第一个字开始,就跟主对话的缓存对不上。
两条缓存链,互相不负用。
而且,你要把枕端对话发过去做摘药。
这时候,你负的是完整的没有缓存折扣的费用。
对话越长越贵。
Anstropic的解决方案叫缓存安全分岔。
压缩请求必须用跟主对话完全一样的系统指令。
用户上下文,工具定义,把主对话的消息作为历史带上。
然后,在莫韦之家一条压缩指令作为新的用户消息。
从后台视角看,这个请求和上一次几乎一模一样。
相同的前坠,相同的工具,相同的历史。
所以,前坠缓存可以直接负用。
新增成本只有最后那条压缩指令本身。
同时还要预留一个压缩缓充区给摘药输出留过空间。
不能等窗口填满才开始压缩,要提前留余量。
一个压缩操作,能负用主对话记载的全部缓存,几乎不多花钱。
回头看这七条经验,都在说同一件事。
缓存就是前坠匹配。
第一,前坠匹配决定一切。
前坠里任何位置的变化都会让其后所有内容的缓存失效。
第二,用消息代替指令修改。
要切换模式,要更新时间,把这些塞进对话消息。
别去东西同指令。
第三,不要在对话中途切换工具或模型。
用工具来表达状态转换。
用延迟加载代替工具的增山。
第四,像监控载县率一样,监控缓存命中率。
Anthropec对缓存中断发告警,当线上事故处理。
第五,分岔操作必须共享主对话的前坠。
压缩、摘药、紫任务,全部用相同的参数。
所有的设计都要围绕这一个约束来展开。
别改指令,别动工具。
一碰,整条缓存链就断。
换模型、切账号、令起炉灶,同一个道理。
这看着像缓存优化,但讲的也是一种思路。
先认死那条绕不开的限制,再围着它,把整个系统搭起来。
