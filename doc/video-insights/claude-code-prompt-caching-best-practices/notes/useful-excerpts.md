# Claude Code 提示词缓存最佳实践：有用摘录

## 可复用观点

- 缓存对长对话 Agent 不是优化项，而是可用性的前提。
- Prompt Caching 的本质是前缀匹配，所以系统设计的第一目标是保持前缀稳定。
- 越不容易变的内容越应该放在 Prompt 前面，越容易变的内容越应该放到后面的消息流里。
- 不要用“局部更干净”的做法破坏全局缓存，例如中途删工具、换模型、改系统提示词。
- 缓存命中率应该作为基础设施指标监控，而不是只在账单变贵时才关注。
- Agent 系统设计要先认清绕不开的约束，再围绕约束搭架构。

## 可复用方法

### Prompt 排列方法

```text
1. 静态系统提示词和工具定义
2. 项目文档，例如 CLAUDE.md
3. 当前会话上下文
4. 对话消息
```

### 动态信息更新方法

```text
不要修改系统提示词。
把变化通过下一轮用户消息、工具结果或 system reminder 注入。
```

适用信息：

- 当前时间。
- 文件状态。
- 模式状态。
- 用户刚刚改变的约束。
- 工具执行后的上下文变化。

### 模型切换方法

```text
主对话保持同一个模型。
需要小模型时，用子任务/subagent。
主模型生成交接说明，子任务独立执行，只返回结果。
```

### 工具管理方法

```text
不要在会话中途增删工具。
用工具表示状态转换。
用延迟加载和工具搜索管理大量工具。
```

### 上下文压缩方法

```text
压缩请求使用和主对话相同的系统提示词、上下文、工具定义和历史消息。
在末尾追加压缩指令。
提前预留 compaction buffer。
```

## 值得直接摘录的话

- 缓存就是前缀匹配。
- 越不容易变的东西，越往前放。
- 系统指令当地基，消息当流水。
- 别改指令，别动工具；一碰，整条缓存链就断。
- 看着像缓存优化，但讲的也是一种架构思路。
- 先认清绕不开的限制，再围着它把系统搭起来。

## 可以转成自己的工程规范

1. 系统提示词禁止写入秒级时间、随机 ID、临时状态。
2. 工具定义必须排序稳定，不能依赖无序容器遍历结果。
3. 工具参数变更要视为缓存破坏风险，不能随意调整。
4. 长会话默认不切模型。
5. 需要轻量任务时优先使用子任务，而不是切换主模型。
6. 规划模式、只读模式、执行模式应通过消息或工具状态表达。
7. 工具多时优先使用占位符和延迟加载。
8. 摘要、压缩、分支任务要尽量复用主对话前缀。

## 暂不直接采纳的内容

- 视频提到“没有缓存就没有 Claude Code”是为了强调重要性，作为工程判断应理解为“没有高命中缓存，长对话 Agent 的成本和延迟很难维持”。
- 视频里的账号池和中转提醒偏运营风险，不是主线，但可以作为多账号共享缓存不可行的旁证。
