# Claude Code 提示词缓存最佳实践：体验总结

## 我认可的部分

- 这条视频的核心非常清楚：所有实践都围绕“前缀匹配”展开，不是零散技巧。
- 它把 Prompt Caching 从“省钱功能”提升到了“Agent 架构约束”，这个视角有价值。
- “系统提示词当地基，消息当流水”这个表达很适合记忆，也适合团队规范化。
- Plan Mode 的例子很好，说明产品功能应该围绕缓存约束设计，而不是为了交互直觉破坏底层性能。
- 延迟加载工具的思路对 MCP-heavy 的 Agent 系统很有启发。

## 我存疑或需要验证的部分

- 视频没有展开具体 API 参数和代码实现，真正落地还需要看 Anthropic API 文档。
- “中途不切模型”的结论依赖会话长度、模型价格、缓存命中情况；短会话或独立任务未必适用。
- “工具定义始终不变”对安全权限控制有潜在冲突，实际系统里还要结合权限边界设计。
- 本视频是基于官方博客的二次讲解，不是完整工程实现教程。

## 可以马上实践的动作

1. 检查自己的 Agent/Skill 系统提示词，移除时间、随机数、临时状态。
2. 把动态状态改为通过消息注入，而不是改系统提示词。
3. 固定工具定义顺序，避免无序遍历导致缓存失效。
4. 长会话里避免频繁切换模型。
5. 把“子任务/subagent 交接说明”做成固定模板。
6. 给多工具 Agent 设计工具索引或延迟加载策略。
7. 把上下文压缩设计成共享主对话前缀的分岔调用。
8. 记录缓存命中率、首 token 延迟、输入 token 成本，作为体验指标。

## 后续要验证的问题

- 在当前使用的 API/平台中，Prompt Cache 的命中情况能否直接观测？
- 如果使用 OpenAI、Gemini 或本地模型，是否有等价缓存机制？
- 当前 Skill/Agent 目录结构中，哪些内容应该放到稳定前缀，哪些应该作为消息注入？
- MCP 工具数量变多后，是否有现成工具搜索或延迟加载机制？
- 自动压缩上下文时，怎样保证压缩调用和主对话共享前缀？

## 我的结论

这条视频最有用的不是“Claude Code 省钱技巧”，而是一个 Agent 系统设计原则：

```text
稳定的东西前置并保持不动；
变化的东西后置并放进消息流；
分支任务、压缩、工具状态都不要破坏主对话缓存链。
```

它可以直接作为后续设计 AI 工作流、Skills、Agents 和 MCP 工具接入时的底层检查清单。
