# Claude Code 提示词缓存最佳实践：结构化内容

## 一句话概括

Claude Code 的可用性建立在 Prompt Caching 上；要让长对话 Agent 既快又便宜，整个系统必须围绕“缓存按前缀匹配”这个约束来设计。

## 背景

长对话 Agent 每一轮请求通常都要带上系统指令、工具定义、项目上下文、历史对话和新消息。如果每一轮都从头编码，成本和延迟会随上下文长度迅速上升。

视频开头用一个例子说明：第二十轮对话里，前十九轮内容往往和上一次请求相同。如果模型每次都重新计算这些重复内容，就是巨大的浪费。

## 核心概念：Prompt Caching

Prompt Caching 的核心是缓存请求前缀。

```text
请求开头 -> cache_control 断点
这一段内容如果和之前完全一致，就可以复用之前的计算结果。
```

它带来两个直接收益：

- 成本降低：命中缓存的输入 token 成本大幅下降。
- 延迟降低：不用重算的内容越多，首 token 返回越快。

视频中强调的成本示例：

- 不开缓存，10 万 token 对话每轮输入成本约 0.30 美元。
- 开缓存后，首次写入成本略高，后续命中缓存每轮约 0.03 美元。
- 后续轮次约能节省 90% 输入成本。

## 中心问题

所有最佳实践都围绕一个问题：

```text
怎么让尽可能长、尽可能稳定的前缀持续命中缓存？
```

因为 Prompt Caching 是前缀匹配，前缀里任何位置发生变化，都会让变化点之后的缓存失效。

## 经验 1：按稳定程度排列 Prompt

Anthropic 的顺序是：

1. 静态系统提示词和工具定义：全局共享，最稳定。
2. `CLAUDE.md` 或项目文档：项目内稳定。
3. 当前会话上下文：只在本会话稳定。
4. 对话消息：逐轮增长，每轮只新增最后一条。

原则：

```text
越不容易变的东西，越往前放。
越容易变的东西，越往后放。
```

常见破坏缓存的坑：

- 把当前时间写进静态系统提示词。
- 工具定义用无序容器导致顺序不稳定。
- 中途修改工具参数或工具定义。

## 经验 2：用消息更新动态信息，不要改系统提示词

如果时间、文件状态、模式状态等信息变化，不要修改系统提示词。更好的做法是在下一轮用户消息或工具结果中加入系统提醒。

结构上可以理解为：

```text
系统提示词 = 地基，尽量不动
对话消息 = 流水，可以承载变化
```

这样动态信息可以更新，缓存前缀仍然稳定。

## 经验 3：不要在主对话中途切换模型

缓存和模型绑定。即使上下文内容完全相同，换模型也意味着之前积累的缓存不能复用。

直觉上，简单问题切小模型、复杂问题切大模型似乎省钱；但如果主对话已经很长，切到小模型会重建缓存，成本可能比继续让大模型回答更高。

推荐做法：

- 主对话保持同一个模型。
- 需要小模型处理任务时，用子任务或 subagent。
- 主模型先写交接说明，把必要上下文浓缩后交给子任务。
- 子任务独立执行，最后只把结果返回主对话。

## 经验 4：不要在对话中途增删工具

工具定义属于缓存前缀的一部分。中途增加或删除工具，会导致整个对话缓存链断掉。

这条经验反直觉，因为很多人会认为“只给当前任务需要的工具”更干净。但对长对话 Agent 来说，工具集稳定比工具列表短更重要。

## 经验 5：用工具表达状态转换

Claude Code 的 Plan Mode 是典型案例。

直觉做法：

```text
进入规划模式 -> 移除执行工具，只保留只读工具
退出规划模式 -> 再加回执行工具
```

问题是这样会改变工具集，破坏缓存。

Anthropic 的做法：

- 保留所有工具定义不变。
- 增加 `EnterPlanMode` 和 `ExitPlanMode` 两个工具。
- 通过对话消息告诉模型当前处于规划模式。
- 模型在规划模式下只思考和探索，不执行修改。

好处：

- 工具集不变，缓存稳定。
- 模型可以在遇到复杂任务时自主进入规划模式。

## 经验 6：用延迟加载管理大量工具

Claude Code 可能接入几十个 MCP 工具。如果完整工具定义全部塞进 Prompt，成本太高；如果按需增删工具，又破坏缓存。

折中方案是延迟加载：

```text
前缀中只放轻量工具占位符；
模型真正需要某个工具时，再通过工具搜索拉取完整定义。
```

这类似图书馆索引：先看目录，真正需要某本书时再去书架取，不需要把所有书搬到桌上。

## 经验 7：上下文压缩必须缓存安全分岔

长对话跑久后需要压缩历史对话，腾出上下文空间。最容易犯的错是另起一个“摘要请求”，用不同系统提示词、不同工具定义去总结整段对话。

这样会带来两个问题：

- 与主对话前缀不一致，无法复用缓存。
- 越长的对话越需要压缩，但压缩调用越贵。

Anthropic 的做法叫缓存安全分岔：

1. 压缩请求使用和主对话完全相同的系统提示词、用户上下文、系统上下文和工具定义。
2. 把主对话消息作为历史带上。
3. 在末尾追加压缩指令作为新的用户消息。
4. 预留 compaction buffer，不能等上下文窗口完全填满才压缩。

这样从 API 视角看，压缩请求和主对话前一次请求几乎相同，前缀缓存可以复用，新增成本主要是压缩指令本身。

## 总结

视频最终把经验归纳为五条：

1. Prompt Caching 是前缀匹配，前缀任何变化都会让后续缓存失效。
2. 动态信息用消息更新，不要改系统提示词。
3. 不要在对话中途切模型、改工具集。
4. 缓存命中率要像服务在线率一样监控。
5. 压缩、摘要、子任务等分岔操作要共享主对话前缀。

最关键的工程思想：

```text
先接受系统绕不开的约束，再围绕约束设计架构。
```
