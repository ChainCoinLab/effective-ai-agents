# Claude Code 提示词缓存最佳实践：思维导图提炼

## 中心思想

Claude Code 这类长对话 Agent 产品的成本、延迟和可用性，取决于 Prompt Caching 的命中率。因为缓存是前缀匹配，所以整个系统架构都要围绕“保持前缀稳定”来设计。

## 思维导图

```text
Claude Code Prompt Caching
├─ 1. 为什么缓存重要
│  ├─ 长对话每轮都带完整上下文
│  ├─ 重复编码导致成本和延迟爆炸
│  ├─ 缓存命中后输入成本大幅下降
│  └─ 命中率影响用户额度和产品体验
│
├─ 2. 缓存的底层规则
│  ├─ 本质: 前缀匹配
│  ├─ 从请求开头到 cache_control 断点可缓存
│  ├─ 下一次请求前缀完全一致才能复用
│  └─ 前缀中任意变化会让后续缓存失效
│
├─ 3. Prompt 应该怎么排列
│  ├─ 静态系统提示词和工具定义
│  ├─ CLAUDE.md / 项目文档
│  ├─ 当前会话上下文
│  └─ 逐轮增长的聊天消息
│
├─ 4. 动态信息怎么处理
│  ├─ 不要修改系统提示词
│  ├─ 时间、文件状态、模式变化放进消息
│  ├─ 系统提示词当地基
│  └─ 对话消息当流水
│
├─ 5. 模型切换怎么处理
│  ├─ 缓存绑定模型
│  ├─ 主对话不要中途换模型
│  ├─ 简单任务也未必值得切小模型
│  └─ 需要小模型时使用 subagent/子任务
│
├─ 6. 工具集怎么处理
│  ├─ 工具定义属于缓存前缀
│  ├─ 中途增删工具会断缓存
│  ├─ Plan Mode 用工具表示状态转换
│  └─ 大量工具用延迟加载和工具搜索
│
├─ 7. 上下文压缩怎么处理
│  ├─ 普通摘要请求会破坏缓存
│  ├─ 压缩请求必须共享主对话前缀
│  ├─ 末尾追加压缩指令
│  └─ 提前预留 compaction buffer
│
└─ 8. 工程启示
   ├─ 缓存命中率是基础设施指标
   ├─ 缓存中断应该被监控和告警
   ├─ 不要为了局部“干净”破坏全局缓存
   └─ 架构设计要围绕硬约束展开
```

## 论点、论据、论证

| 论点 | 论据 | 论证重点 | 我的判断 |
| --- | --- | --- | --- |
| Prompt Caching 不是锦上添花，而是 Claude Code 能跑起来的前提 | 长对话每轮都带完整上下文；缓存命中能显著降低成本和延迟 | 没有缓存，Agent 产品的成本和体验不可持续 | 这是最重要的底层认知 |
| 缓存的核心规则是前缀匹配 | 请求从开头到断点之间完全一致，才能复用缓存 | 所有设计都要保证前缀尽量稳定 | 这条规则可以指导 Agent 架构设计 |
| Prompt 排列顺序决定缓存效果 | 静态系统提示词、工具定义、项目文档放前面，动态消息放后面 | 越稳定越靠前，越动态越靠后 | 可以直接应用到我们自己的 Agent/Skill 设计 |
| 动态信息应放入消息，而不是修改系统提示词 | 时间、文件状态、规划模式等变化如果改系统提示词会断缓存 | 系统提示词固定，消息承载变化 | 很适合写成工程规范 |
| 不要中途切模型 | 缓存和模型绑定，切模型会重建缓存 | 简单问题切小模型未必省钱 | 对长会话尤其重要 |
| 不要中途增删工具 | 工具定义是缓存前缀的一部分 | 看似减少工具，实际可能导致更大成本 | MCP 工具多时尤其容易踩坑 |
| 延迟加载是工具管理的折中方案 | 前缀只放轻量占位符，需要时用工具搜索拉取完整定义 | 既控制上下文体积，又保持前缀稳定 | 对多工具 Agent 很有启发 |
| 压缩必须缓存安全分岔 | 普通摘要请求无法复用主对话缓存 | 压缩请求要共享主对话系统提示词、工具定义和历史 | 这是长上下文系统的关键设计 |

## 最终提炼

```text
缓存优化不是局部性能技巧，而是 Agent 系统架构约束。
```

如果只记一句：

```text
别改前缀，别动工具，别换模型；把变化放到消息流里。
```
