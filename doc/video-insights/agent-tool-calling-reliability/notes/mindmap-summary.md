# 面试官：如何保证 Agent 调用工具 (Function Calling) 的可靠性？ 思维导图提炼

## 中心思想

工具调用可靠性是一套分层工程体系：前面用定义和工具选择降低错误概率，中间用代码校验和权限确认拦截错误，后面用错误回传、结果反思和轨迹观测恢复错误。

## 思维导图

```text
面试官：如何保证 Agent 调用工具 (Function Calling) 的可靠性？
├─ L1 结构化定义
│  ├─ JSON Schema / 参数类型 / 必填项 / 枚举 / 可空
│  └─ 工具描述写清使用条件、排除条件和业务语义
├─ L2 调用前策略
│  ├─ 先形成可检查的调用计划或理由摘要
│  ├─ Few-shot 覆盖正确、错误和边界调用
│  └─ 工具很多时先检索 Top-K，不把全部工具塞给模型
├─ L3 执行护栏
│  ├─ schema 校验、业务规则校验、权限校验
│  ├─ 高风险动作必须人工确认
│  └─ 校验失败不执行
└─ L4 自愈闭环
   ├─ 结构化错误回传
   ├─ 参数修正和重新规划
   └─ 工具结果反思是否完成用户目标
```

## 论点、论据、论证

| 论点 | 论据 | 论证重点 | 我的判断 |
| --- | --- | --- | --- |
| 可靠性不能只靠 prompt | 视频开头明确反对“把 prompt 写好点”的单点回答。 | 生产风险来自全链路，不只来自模型表达。 | 采纳。应沉淀为工程架构回答。 |
| schema 是第一层约束 | 视频用日期格式、参数类型、枚举值、可空规则说明工具定义的重要性。 | 工具调用先要机器可校验。 | 采纳，并和已有“工具接口要小而清晰”实践合并理解。 |
| 少给工具可以提高正确率 | 视频指出 100 个工具全塞给模型会增加干扰，应该先按语义检索相关工具。 | 工具选择本质是上下文工程和路由问题。 | 采纳。大规模工具系统必须有工具检索或路由层。 |
| 执行前必须由应用拦截 | 视频强调模型输出 JSON 后不能直接塞给 API。 | 模型生成的是意图，执行权在应用层。 | 采纳。和权限、确认、审计规则一致。 |
| 失败要进入闭环修复 | 视频建议把 API 错误回传，让模型重新生成参数，并检查结果是否解决用户问题。 | 错误不是终点，而是下一轮规划输入。 | 采纳，但要限制重试次数并记录 trace。 |
