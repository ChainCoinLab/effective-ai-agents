# 面试官：如何保证 Agent 调用工具 (Function Calling) 的可靠性？ 体验总结

## 我认可的部分

- 主线正确：Function Calling 可靠性是工程链路问题，不是 prompt 写法问题。
- 四层拆法清楚：结构化定义、调用前策略、执行护栏、自愈修复，能直接转成面试回答和架构 checklist。
- “模型输出 JSON 不能直接执行”是关键分界：模型生成意图，应用层负责校验、权限、确认和执行。
- 工具检索/路由的提醒有价值。工具数量一多，全量暴露会显著增加误选和上下文噪声。

## 我存疑的部分

- 不应要求模型暴露完整 chain-of-thought。生产系统应记录调用计划、理由摘要、检查项和 trace，而不是依赖私有推理文本。
- “第二次大概率就是对的”需要配合重试上限、错误分类和回归测试，否则容易变成无限自修复循环。
- 视频偏面试表达，缺少线上监控、SLO、trace 回放、回归 eval 和安全审计这些生产配套。

## 可以马上实践的动作

1. 把工具调用链路拆成定义、选择、计划、校验、确认、执行、恢复、观测八个检查点。
2. 为每个工具补齐 JSON Schema、业务规则校验和结构化错误返回。
3. 建立高风险工具清单，要求确认令牌或人工确认才能执行。
4. 将无效参数、权限失败、超时、空结果、业务规则冲突纳入 eval 和回归集。
5. 为每次工具调用记录 trace：模型调用意图、应用校验结果、权限判断、实际执行结果和错误恢复过程。

## 后续要验证的问题

- 工具检索 Top-K 应如何设置，才能在误选率、召回率和上下文成本之间平衡？
- 哪些工具失败允许模型自动修复，哪些必须交给用户或人工审核？
- 调用前计划、参数校验、结果反思分别能降低哪类错误？需要用 eval 分层验证。
- 高风险确认的用户体验如何设计，既不打断低风险流程，也不放过不可逆动作？

## 我的结论

这个视频适合沉淀为一条最佳实践：把工具调用可靠性做成分层闭环。已有最佳实践里有接口、权限、失败、轨迹等单点规则，但还需要一页把这些点连成完整的 Function Calling 可靠性栈。
