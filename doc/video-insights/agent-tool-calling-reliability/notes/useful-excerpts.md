# 面试官：如何保证 Agent 调用工具 (Function Calling) 的可靠性？ 有用摘录

## 筛选标准

只保留能复用、能指导行动、能解释判断标准，或能作为后续写作素材的片段；单纯寒暄、重复铺垫和无法验证的泛泛表达不进入核心摘录。

## 可复用观点

- 工具调用可靠性不是单点 prompt 优化，而是“预防、拦截、自愈”的链路工程。
- 可靠性的第一步是定规矩：工具 schema、参数类型、枚举值、可空规则和语义描述都要清楚。
- 工具太多会干扰模型选择，应该先按用户意图检索或路由，只给当前任务相关的工具。
- 模型输出的 JSON 不能直接执行；应用层必须先做校验、权限判断和风险分级。
- 高风险动作必须有人机确认，不能让 Agent 独立完成不可逆操作。
- 失败信息应该结构化回传，成为下一次参数修正或重新规划的输入。

## 可复用方法

- `00:20` 用“预防、拦截、自愈”概括生产级工具调用可靠性。
- `00:42` 先定规矩：可靠性的第一步不是怎么调模型，而是怎么定义工具契约。
- `00:46` 用 JSON Schema 固定字段类型、是否可空、枚举值和必填项。
- `00:57` 工具描述是给模型看的说明书，要像写 prompt 一样优化。
- `01:39` 用 few-shot 给出正确和错误调用样例，让模型学到边界。
- `01:47` 工具很多时先做工具检索，只注入最相关的几个工具。
- `02:12` 用 Pydantic 等库做自动校验，先检查格式、类型和业务逻辑。
- `02:23` 校验不过直接拦截，不给执行机会。
- `02:27` 转账、改密码等高风险操作要加人机确认。
- `02:47` API 返回日期格式错误时，把错误信息回传给模型并要求重新生成参数。
- `03:07` 工具执行后做状态反思：结果是否真正解决用户问题。

## 可复用操作步骤

1. 为每个工具写 schema：类型、必填、枚举、默认值、可空、单位、格式、范围。
2. 在工具描述中写清：适用场景、不适用场景、参数含义、副作用和错误返回。
3. 在工具选择前做路由或检索，只给模型当前任务需要的 Top-K 工具。
4. 调用前要求模型输出可检查的调用计划或理由摘要，但不要把私有 chain-of-thought 当成审计依据。
5. 执行前用代码校验模型参数，覆盖 schema、业务规则、权限和风险等级。
6. 对删除、付款、发信、改密、发布、生产写入等动作要求显式确认令牌或人工确认。
7. 将工具错误标准化为 observation，包含错误类型、可重试性、用户可补充信息和安全降级路径。
8. 限制自动修复和重试次数，避免无限循环；每轮记录 trace，方便回放和回归。
9. 工具执行后检查结果是否满足用户目标，不满足时重新规划、请求补充或明确失败。

## 值得保留的表达

- “不能把所有赌注都压在模型的智商上，要靠工程手段兜底。”
- “可靠性 = 高质量定义 + 严格代码约束 + 闭环反思重试机制。”

## 暂不采纳的内容

- 视频把调用前思考称为 COT。工程实践中更推荐记录可公开、可审计的调用计划、理由摘要和关键检查项，不依赖暴露完整 chain-of-thought。
- 视频提到“慢思考能挡掉 80% 低级错误”，这是经验性表达，缺少可验证数据；应在自己的 eval 集上验证。
