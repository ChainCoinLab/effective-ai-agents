# 面试官：如何保证 Agent 调用工具 (Function Calling) 的可靠性？ 结构化内容

## 一句话概括

Agent 工具调用可靠性不是 prompt 技巧，而是一条由工具定义、调用前规划、执行校验、权限确认、错误回传和状态反思组成的工程链路。

## 主题关键词

Agent、Function Calling、工具 schema、JSON Schema、Few-shot、工具检索、参数校验、人机确认、错误回传、状态反思、自愈

## 问题

- 面试里如果只回答“把 prompt 写好”，会显得把可靠性押在模型自觉性上。
- 真实业务中的模型可能幻觉、乱填参数、误选工具，甚至触发删除、转账、改密等高风险动作。
- Function Calling 的风险不只在模型输出阶段，还包括工具定义不清、工具太多、参数格式错误、权限缺失、执行失败和结果不符合用户目标。

## 方法

视频给出四层可靠性框架：

1. 结构化定义层：用 JSON Schema 固定参数类型、必填项、枚举值、可空规则；工具描述要像 prompt 一样说明何时调用、如何填参、何时不用。
2. 推理策略层：在调用前要求模型给出可检查的调用计划或理由摘要；用 few-shot 覆盖正确、错误和边界调用；工具多时先按用户意图检索少量相关工具，减少误选。
3. 执行护栏层：模型只生成调用意图，应用层必须做 schema 校验、业务规则校验、权限校验和高风险确认；校验失败不能执行。
4. 自愈修复层：把结构化错误回传给模型或编排器，让系统修正参数、重新规划或降级；工具执行后再检查结果是否真正解决用户目标。

## 时间线要点

- 00:00-00:24: 提出问题：只靠 prompt 不足以保证工具调用可靠，生产系统需要预防、拦截和自愈。
- 00:29-01:11: 结构化定义层：用强类型 schema 和清晰语义描述约束工具输入，避免“明天”这类自然语言参数直接进入后端。
- 01:15-02:02: 推理策略层：调用前先形成可检查计划，用 few-shot 提供调用样例；工具很多时用语义检索选出相关工具，少给工具反而更准。
- 02:05-02:37: 执行护栏层：模型输出 JSON 后不能直接执行，要用代码做格式、类型、业务规则和权限校验；转账、改密等动作需要用户确认。
- 02:37-03:18: 自愈修复层：校验或执行失败时，把错误信息回传，让模型重新生成参数；工具返回后检查结果是否满足用户目标。
- 03:18-03:46: 总结公式：可靠性来自高质量定义、严格代码约束和闭环反思重试机制，而不是模型“聪明”本身。

## 结论

可复用的工程结论：Function Calling 可靠性要按链路设计，而不是按单点技巧优化。模型负责提出调用意图，应用负责约束、校验、权限、确认、执行、观测和恢复。

面试回答可以压缩成一句话：我不会只靠 prompt，而会从工具 schema、工具选择、调用前计划、执行前校验、高风险确认、错误回传、结果反思和 trace 回放八个环节保证可靠性。
